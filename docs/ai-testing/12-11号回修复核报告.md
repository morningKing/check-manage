## 3. 最重要发现：H7③ 无效，底层 `deliver_one` 忽略投递结果

### 3.1 新增的 `uncertain` 分支生产不可达

代码形态看似完整：`delivery_outbox.py:190-196` 对 `Timeout/ConnectionError` 返回 `'uncertain'`，`:199-221` 传递该信号，`:120-154` 据此把 effect 置 `unknown`。**但该 except 分支永远不会执行**：

```python
# delivery_outbox.py:180-196
try:
    _fire_single_webhook(...)     # ← 返回值被丢弃
    return True                   # ← 无条件成功
except (_requests.exceptions.Timeout,
        _requests.exceptions.ConnectionError) as e:
    return 'uncertain'            # ← 不可达
```

而 `_fire_single_webhook`（`webhook_engine.py:345-370`）**内部把 `requests` 的 `Timeout` 与 `RequestException` 全部捕获并继续**，只在循环结束后返回 dict，从不向调用方抛出。探针实测（假造 `requests.post`，不碰网络、不写库）：

```
HTTP 400 -> True / HTTP 500 -> True / Timeout -> True / ConnectionError -> True
```

### 3.2 两个后果

1. **`unknown` 永不写入** → `batch_engine.py` 的 `has_unknown_effects → needs_review` 仍是死代码，11 号"保护链路真实激活"不成立（dev 库 `ai_execution_effects` 0 行、`status='unknown'` 0 行）。
2. **更严重：outbox 的可靠投递在 HTTP 失败面实质失效** —— 确定性失败（4xx/5xx）被记为 `delivered` + effect `committed`，超时/连接拒绝同样记为成功，**永不退避重试、永不 dead_letter**（dev 库 outbox 153 行全 `delivered`；`max attempt_count=2` 来自非 requests 异常的通用 except 路径）。

### 3.3 引入时点与修法

该 `return True` 在 base（`9b280d5`）就存在（本轮只新增了不可达的 except 分支），属跨轮遗留缺陷；但本轮把它当成"已激活"的依据，因此**判定 H7③ 无效**。修法：读取 `_fire_single_webhook` 返回的 `success`，按 `responseStatus` 区分（4xx/5xx → `False`，超时/连接类 → `'uncertain'`）；修好后需再评估 `unknown` 的粘滞性（见 §4.3）。
