## 4. 本批修复引入的新缺陷

### 4.1 【严重】`continue_child` 计数回滚取到"更新后"状态

PostgreSQL 的 `UPDATE … RETURNING status` 返回**更新后**的值。`batch_repo.py:801-806` 用 `prev_status = landed[0]` 决定回滚哪个计数，而该值恒为 `'pending'`，`if prev_status == 'completed'` 是死分支 → 对 **completed** 子任务执行"继续"时错误 `failed - 1`、`done` 不减。

实测（临时用户/批次，已清理）：

```
batch counters after continue_child(completed child): (done=1, failed=-1, status='pending')
```

`ai_chat_batches` 无 `failed >= 0` 约束（已查 `pg_constraint`）→ 静默变负；该子任务再次跑完 +1 后，批状态经 `_recompute_batch_status_for` 会被算成 `partial`，前端进度与终态全错。

**逃逸原因**：`test_open_api_batches_sessions.py:529-559` 只断言 session 的 status/oc/continue_prompt；`test_reexecute_and_continue_bump_generation` 只 continue 了 **failed** 子任务（`failed-1` 恰好正确），因此测试全绿。

**建议**：先取旧状态再更新（或分两条语句），并补"对 completed 子任务 continue 后 `done/failed` 不变"的断言。

### 4.2 【中】首轮用户消息重复 + 历史排除错位

`_persist_user_prompt` 写 `{sid}:user:g0`，`_persist_conversation` 写 `{sid}:user`，内容相同；`ai_chat_messages` 只有 id 主键、无 `(session_id, role)` 唯一约束，`get_child_messages`（`batch_repo.py:1112-1122`）按 seq 全量返回 → 子任务对话里同一问题出现两次。实测：

```
('…:user:g0', 'user', '"同一个问题"')
('…:user',    'user', '"同一个问题"')
```

同时 `render_history_block(exclude_msg_id=f'{sid}:user')` 不再排除本轮提示词 → 恢复路径（`batch_engine.py:1787-1806`）把当前问题既放进"此前对话摘要"又追加一次，并丢掉 gen-0 那条用户消息。

### 4.3 【中】编排 × 自动重试互相误杀

`on_child_terminal`（`orchestration_engine.py:457-483`）把任何非 `running/completed/needs_review/failed` 的子会话状态都当失败；而 worker 的自动重试会先把子会话改回 `pending` 再 `return`（`batch_engine.py:2482-2488`），调用点在 `finally`（`:1355-1362`）→ **一次本可自愈的 auto-retry 会把 step 判 failed、下游永久 skip、run 直接 failed**。探针实证：

```
steps after requeue callback: [('A','failed','子会话终态 pending'), ('B','skipped',None)]
run: failed
```

### 4.4 【中】投递器与编排调度器租约无重试 → 静默停摆
