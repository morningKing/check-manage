# AI 动作门禁与执行前审批

> **适用对象**：为 AI 批任务配置「动作门禁」（动作核对清单）的使用者，以及需要处理「AI 执行前审批」的用户
> **入口**：AI 助手 → 批任务（门禁配置随批任务）；顶部栏「我的待办」按钮（执行前审批）
> **相关设计**：动作门禁机制细节见设计文档 `docs/design/ai/05-动作门禁与审批.md`；对外 API 字段见 [AI 批任务 API §11.5](../integration/ai-batch-api.md)

---

## 门禁是什么

给批任务的每个子任务挂一份「核对要求」清单。子任务跑到终态时逐条核对：

- **全部通过** → 子任务正常完成；
- **有未通过的** → 子任务标记失败，失败原因写明是哪一条、差在哪；
- **无法证实**（核对机制自身故障）→ 同样失败（绝不静默放行）。

批级开关「**自动修正**」（`gate_retry`，默认关）开启后，未通过的子任务会带着缺失明细**在原会话上**定向修复续跑一次（与自动重试共用重试次数），修复后仍不过才落败。

门禁回答两个问题：**「该做的做了没」**（终态核对，默认模式）与**「不允许做的别做」**（pre 阻断，见下文）。执行前审批则补上事前防线——高危步骤在执行前挂起等人工裁决，与事后门禁互补、不互相替代。

## 期望怎么登记：三个入口

### 入口 A：批创建参数（界面）

1. 顶部导航进入 **AI 助手**，左侧栏「批任务」区点 **新建**；
2. 在对话框中勾选 **启用动作门禁**，出现期望编辑区；
3. 每条期望包含：
   - **类型**：「工具调用断言」（`tool`）或「判官核对」（`verifier`）；
   - **名称**：如「克隆目标仓库」（必填，一条期望只表达一件事）；
   - 工具断言：**工具**（如 `bash`）、**参数正则**（如 `git clone\s+\S*acme/inspector`）、**最少次数**；
   - 判官核对：**判定要点**（rubric，≤2000 字）；
   - **适用子代理**（可选，逗号分隔，如 `general, explore`；留空 = 对所有子代理生效）；
4. 点 **创建** 提交。正则写错会在提交时被拦下（提示重新修改），不会「带病入库」。

创建后的批次可随时在分组的 **编辑** 对话框中修改门禁（勾选项「自动修正」即 `gate_retry`）——修改只对**未完成**的子任务生效，已完成子任务的历史核对结果不变。

### 入口 B：Prompt 模板携带

常用核对清单可随 **Prompt 模板** 保存：模板的 `action_checks` 字段会随模板落库，从模板创建的批任务自动继承。批任务自身没有配置门禁时，派发时会**回退到模板上的清单**。适合「同一类任务每次都要核对同样的动作」的场景——模板维护一份即可。

### 入口 C：会话内登记（AI 自主）

交互会话中，AI 助手可在派发子代理或执行关键动作**之前**，通过 `register_action_check` 工具把「必经动作」登记为期望（回合结束后自动核对）。你可以直接在对话里要求它，例如：「把『必须运行过 pytest』登记为门禁」。

- 只支持「工具调用断言」类期望；
- **登记后不可由会话撤销**——核对在服务端完成，模型没有删除或干预已登记期望的路径；
- 强度说明：登记依赖模型自主调用，比入口 A/B 的人工确认弱一档，适合临时、长尾的核对需求。

### 辅助入口

- **AI 提炼（只出建议）**：创建对话框中的「AI 提炼」按钮，按 Prompt 与已启用技能的步骤生成建议清单并**预填表单**——真正的登记仍然以你点「创建」确认为准。平台不会因 AI 的建议自动增删任何期望。
- **管理员补挂**：对已在运行中/排队中的子会话，管理员可经 API（`POST /ai/chat/batches/<id>/action-checks/attach`）逐会话补挂期望。

## 四类核对怎么选

界面支持前两类中的「工具调用断言」与「判官核对」；「文件产物」「数据记录」目前经 [对外 API](../integration/ai-batch-api.md) 配置。

| 要核对的东西 | 用哪类 | 例子 |
|---|---|---|
| 「必须执行过某个操作」且操作形式固定 | `tool`（正则匹配调用账本） | 必须跑过 `git clone`；必须调用过 `write` 写某文件 |
| 「必须产出某个文件」且只关心存在性 | `file` | 产出物必须落到 `outputs/report.md` |
| 「必须写入某条数据」 | `db_record` | 集合里必须有 status=done 的记录 |
| 「做得对不对」——语义、质量、过程合理性 | `verifier`（判官核对） | 结论必须覆盖三个要点；必须先调研再汇总；子代理的回答必须回应了提问 |

原则：**能用前三类确定性原语表达的，不要用判官**。判官是 LLM 判定，有正常波动；`tool`/`file`/`db_record` 是确定性的，快、免费、可精确复现。判官的价值在于表达「正则写不出来的要求」。

## 两种模式：pre 阻断 vs 终态核对

每条期望都有核对时机（`mode`）：

| | 终态核对（`post`，默认） | pre 阻断（`pre`） |
|---|---|---|
| 回答的问题 | 该做的**做了没** | 不允许做的**别做** |
| 生效时机 | 子任务跑到终态时逐条核对 | **每次工具调用前**询问，命中即阻断该次调用 |
| 适用类型 | 四类均可 | 仅「工具调用断言」（`tool`） |
| 典型用途 | 交付物完整性、过程合规 | 禁止 `rm -rf`、禁止写某个路径、禁止外发 |
| 失败表现 | 子任务失败并写明缺失项 | 该次工具调用被拒绝，AI 收到拦截原因后自行调整 |

pre 阻断由平台部署的运行时插件执行：插件在每次工具调用前把「工具名 + 参数」送回服务端比对 deny 清单，命中即抛错阻断。为可用性考虑，pre 阻断在核对通道不可用时会**放行**（不让一次基础设施故障瘫痪全部工具调用）——终态核对仍然兜底。pre 模式目前经 API 配置（界面上配的期望均为终态核对）：创建请求的 `actionChecks` 数组项支持 `mode: 'pre' | 'post'` 字段——内部接口与对外 API 走同一服务端校验（注意该字段尚未列入 [AI 批任务 API](../integration/ai-batch-api.md) §11.5 的字段表，以服务端校验为准）。

## 判官核对（verifier）三要素

### 1. rubric（判定要点）怎么写

rubric 是写给判官的判定标准，≤2000 字。把它当成「交给一个认真但不了解任务的审查者的验收清单」：

- **写「可观察的事实」**，不写「抽象评价」。✅「最终回复必须包含输入文件的原文内容」❌「回复质量要好」——判官看得到回复和工作区，看不到你心里的预期。
- **给出可判定的锚点**：具体字符串、文件路径、数量。✅「回复必须包含字符串 X」「`outputs/report.md` 必须存在且包含输入原文」；❌「必须充分分析」。
- **一条期望一件事**。要核对的点多了拆成多条期望（各有名称），失败时才能定位到具体缺什么，自动修正的修复提示也更准。
- **明确「在哪里找证据」**：涉及文件的写「请打开工作区核对 `outputs/x.md`」，判官会用只读工具去读。

反例：`"结论要好"`——判官只能凭感觉，两次判定可能不一致。
正例：`"最终回复必须包含三个风险点的名称，且每个风险点后附一行数据依据"`。

### 2. 粒度怎么选（适用子代理）

- **留空（默认）**：判官核对任务会话整体——最终回复 + 全部工具调用轨迹（含子代理）+ 工作区文件。适合「最终交付物」类要求。
- **填写子代理名单**（如 `general`）：判官只看指定子代理的会话消息与它的工具调用轨迹。适合「过程中某个环节对不对」——例如「调研子代理必须两次委派且第二次引用第一次结论」。可填多个名字（同一条期望对名单合并判定）；同批次多条期望用同一名单会合并为一次判官会话，节省核对开销。
- 注意：定向组要求该子代理**确实被委派过**（名字要与主代理实际委派的子代理类型一致，如 `general`）。没有委派发生时材料为空，判官会把「未执行」当作失败证据——这通常正是你想要的。

### 3. 判官能看到什么 / 看不到什么

| 看得到 | 看不到 |
|---|---|
| 任务最终回复全文（定向组则替换为指定子代理的会话消息） | 工具调用的**输出内容**（账本只记入参） |
| 工具调用轨迹（工具名/入参/状态/时序，含子代理，封顶 100 条） | 工作区之外的系统状态（外部回调是否发生等——用 `db_record`） |
| 工作区文件（只读：read/grep/list，判官可主动打开取证） | 交互式聊天会话（门禁只在批任务子任务上运行） |

判定结果三态：通过 / 未通过（附理由与证据引用）/ 无法证实（判官超时、不可解析等基础设施问题 → 同样落失败，但原因写明是核对不可证实）。

## 编写辅助

- **AI 提炼**：见入口 A，按 Prompt 与技能步骤生成建议并预填表单。
- **工具调用时间线**：设置中心 → AI 能力 → **AI 执行中心（「批量执行」页签）** → 子任务行「工具调用」，可查看该子会话及子代理树实际发生的工具调用（工具名、参数摘要、状态、时间），写参数正则时取材用。见 [AI 批任务](./batch-tasks.md)。
- **dry-run 试算**：保存期望前按整个子任务树的实际账本**试跑一次匹配**，返回命中数与样例——正则写得对不对，写的时候就能验。该能力目前**没有界面按钮**，可经后端内部 API（需登录会话：`POST /ai/chat/batches/{batchId}/children/{sessionId}/gate/dry-run`，属平台内部蓝图、不在对外 API 家族内）调用；判官核对类期望无法预演，需真实会话核对。

## 失败之后

- 子任务标记失败，失败原因形如 `action_gate: 期望名(判官未通过: 具体理由)` 或 `action_gate: 期望名(需至少 1 次,实际命中 0 次)`；
- 批级开启「自动修正」后：预算内自动带着缺失明细在**原会话**续跑修复——模型看到的是「哪些条没过、差在哪」，只补缺口不重做；与自动重试共用重试次数，修复后仍不过才最终落败；
- 每条期望的核对结果（通过/未通过、证据摘要）会记录在期望行上（`last_status`/`last_evidence`），当前**没有界面展示**；可在批任务管理页子任务的「工具调用」时间线里间接观察——工具调用是否实际发生、是否被 pre 规则拒绝，在那里一目了然。

## 执行前审批（收件箱）

编排运行中的高危步骤（人工审批节点、策略拦截）会在执行前挂起，生成一条**审批请求**等待人工裁决。审批与事后门禁互补：审批是「事前放行」，门禁是「事后核对」。

**入口**：点击**顶部栏「我的待办」按钮**打开统一收件箱（`/workflow/inbox`）。

> <!-- TODO(screenshot): 我的待办收件箱，含一条带「AI 审批」标记的行与通过/拒绝操作 -->

- 收件箱统一混排业务工作流待办与 AI 审批——AI 审批是其中**带「AI 审批」标记的行**（不是独立页签），行内直接提供 **通过 / 拒绝** 操作（工作流待办则是「去处理」跳转数据页）；
- 行上以「AI 编排审批」为名展示，阶段列显示该次审批的**影响摘要**（高危工具与脱敏后的参数说明），并带风险等级与进入时间；
- **可见范围**：管理员可见全部待决审批；普通用户只看到审批节点上**点名自己（或所在角色）**的待决审批（平台能力键清单中有对应的「AI 执行前审批」`admin.ai_approval`）；
- **幂等**：重复点击或多人同时裁决，只有第一次生效，后续返回既有结果；
- 所有通过/拒绝动作都会写入操作日志（含备注）；审批超时未处理会按「视为拒绝」处理，对应步骤失败；
- 「编辑后批准」（批准时携带下游输入修改）目前仅审批 API 支持（approve 请求体可带 `edits`），收件箱界面暂未提供该入口。见 [AI 编排管理](./orchestration.md)。

## 常见问题

**门禁核对没跑，子任务却显示失败，原因写着「无法证实」？**
核对机制把「没法证明达标」与「没达标」同等对待（绝不静默放行）。常见触发：账本落账失败、判官超时或判官 agent 未部署。可先看批任务管理页的 Attempt 链与子任务错误信息定位，必要时重跑子任务。

**判官核对每次结果略有不同？**
判官是 LLM 判定，存在正常波动。把 rubric 写得更「可观察、有锚点」（见上文三要素），波动会显著收敛；强确定性要求请改用工具断言/文件/数据记录类。

**界面上配的期望，和 API 文档里的字段对不上？**
界面只覆盖「工具调用断言」与「判官核对」两类终态核对；`file`/`db_record` 类型与 pre 阻断模式经 [对外 API](../integration/ai-batch-api.md) 配置。字段命名上，顶层是驼峰（`actionChecks`），数组元素内沿用下划线（`check_type`/`args_pattern`），见 API 文档 §11.5 的命名说明。

**为什么修改门禁后已完成的子任务不受影响？**
核对发生在子任务终态，已终态的子任务不会重新核对；编辑只同步到未完成的子任务。

**审批一直挂起没人处理？**
待决审批有超时机制，超时按「视为拒绝」处理、对应步骤失败。可在收件箱确认是否遗漏；普通用户看不到非点名给自己的审批，可找管理员处理。
