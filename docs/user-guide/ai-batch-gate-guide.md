# AI 批任务动作门禁编写指南

> 面向需要在批任务上配置「动作门禁」（`actionChecks`）的使用者：四类核对怎么选、
> `rubric` 判定要点怎么写、判官能看到什么。技术实现细节见设计文档
> `docs/design/ai/AI动作门禁verifier判官核对设计.md`；对外接口字段见
> `docs/user-guide/integration/ai-batch-api.md` §11.5。

## 门禁是什么

给批任务的每个子任务挂「核对要求」清单。子任务跑到终态时逐条核对：全部通过 →
子任务正常完成；有未通过的 → 子任务标记失败，`error` 写明是哪条、差在哪；无法
证实（核对机制自身故障）→ 同样失败（fail-closed，绝不静默放行）。批级开关
`gate_retry`（默认关）开启后，未通过的子任务会带着缺失明细在原会话上定向修复
续跑一次（预算内），修复后仍不过才落败。

## 四类核对怎么选

| 要核对的东西 | 用哪类 | 例子 |
|---|---|---|
| 「必须执行过某个操作」且操作形式固定 | `tool`（正则匹配调用账本） | 必须跑过 `git clone`；必须调用过 `write` 写某文件 |
| 「必须产出某个文件」且只关心存在性 | `file` | 产出物必须落到 `outputs/report.md` |
| 「必须写入某条数据」 | `db_record` | 集合里必须有 status=done 的记录 |
| 「做得对不对」——语义、质量、过程合理性 | `verifier`（判官核对） | 结论必须覆盖三个要点；必须先调研再汇总；子代理的回答必须回应了提问 |

原则：**能用前三类确定性原语表达的，不要用判官**。判官是 LLM 判定，有正常波动；
`tool`/`file`/`db_record` 是确定性的，快、免费、可精确复现。判官的价值在于表达
「正则写不出来的要求」。

## 判官核对（verifier）三要素

### 1. rubric（判定要点）怎么写

rubric 是写给判官的判定标准，≤2000 字。写法上把它当成「交给一个认真但不了解
任务的审查者的验收清单」：

- **写「可观察的事实」**，不写「抽象评价」。✅「最终回复必须包含输入文件的原文
  内容」❌「回复质量要好」——判官看得到回复和工作区，看不到你心里的预期。
- **给出可判定的锚点**：具体字符串、文件路径、数量。✅「回复必须包含字符串
  X」「`outputs/report.md` 必须存在且包含输入原文」；❌「必须充分分析」。
- **一条期望一件事**。要核对的点多了拆成多条期望（各有 name），失败时才能定位
  到具体缺什么，gate_retry 的修复提示也更准。
- **明确「在哪里找证据」**：涉及文件的写「请打开工作区核对 `outputs/x.md`」，
  判官会用只读工具去读。

反例：`"结论要好"`——判官只能凭感觉，两次判定可能不一致。
正例：`"最终回复必须包含三个风险点的名称，且每个风险点后附一行数据依据"`。

### 2. 粒度怎么选（subagents）

- **留空（默认）**：判官核对任务会话整体——最终回复 + 全部工具调用轨迹（含
  子代理）+ 工作区文件。适合「最终交付物」类要求。
- **`subagents: ["某子代理名"]`**：判官只看指定子代理的会话消息与它的工具调用
  轨迹。适合「过程中某个环节对不对」——例如「调研子代理必须两次委派且第二次
  引用第一次结论」。可填多个名字（同一条期望对名单合并判定）；同批次多条期望
  用同一名单会合并为一次判官会话。
- 注意：定向组要求该子代理**确实被委派过**（名字要与主代理实际委派的 subagent
  类型一致，如 `general`）。没有委派发生时材料为空，判官会把「未执行」当作
  失败证据——这通常正是你想要的。

### 3. 判官能看到什么 / 看不到什么

| 看得到 | 看不到 |
|---|---|
| 任务最终回复全文（定向组则替换为指定子代理的会话消息） | 工具调用的**输出内容**（账本只记入参） |
| 工具调用轨迹（工具名/入参/状态/时序，含子代理，封顶 100 条） | 工作区之外的系统状态（外部回调是否发生等——用 `db_record`） |
| 工作区文件（只读：read/grep/list，判官可主动打开取证） | 交互式聊天会话（门禁只在批任务子任务上运行） |

判定结果三态：passed / failed（`error` 带理由与证据引用）/ 无法证实（判官超时、
不可解析等基础设施问题 → 同样落失败，但原因写明是核对不可证实）。

## 失败之后

- 子任务 `failed`，`error` 形如 `action_gate: 期望名(判官未通过: 具体理由)`；
- 批级开启 `gate_retry` 后：预算内（与自动重试共用重试计数）自动带缺失明细在
  **原会话**续跑修复——模型看到的是「哪些条没过、差在哪」，只补缺口不重做；
- 门禁核对结果也会记录在期望行（`last_status`/`last_evidence`），可在子会话
  详情与 dry-run 辅助里查看（`verifier` 类型无法预演，需真实会话核对）。
