## 1. 模块职责

对话助手是平台的**交互式 AI 工作台**：用户在 per-session workspace 里与 OpenCode 会话对话，Flask（`server/routes/ai_chat.py`，蓝图 `ai_chat_bp`，前缀 `/ai/chat`，`ai_chat.py:112`）承担会话生命周期管理、消息收发与持久化、事件流转发、工作区文件/变更/产出管理、问答卡与权限卡闭环、子代理可见性、提示词模板等全部入口。

按职责分四块：

| 职责 | 说明 | 证据 |
| --- | --- | --- |
| 会话面 | 建/列/搜/改名/分组/置顶/关闭/重开/清空/删除/归档，模型与 agent 选择器 | `ai_chat.py:119-505,727-739,2029-2257` |
| 回合面 | 发消息（含附件/@提及/导出兜底）、SSE 事件流、上下文压缩、中止、重连恢复、问答/权限卡、截断重发 | `ai_chat.py:788-1459,1763-1960` |
| 工作区面 | 文件上传/下载/预览、变更文件与 diff、产出文件与独立记录、导入 data_files、脚本运行 | `ai_chat.py:1486-1662,1981-2026` |
| 辅助面 | MCP 服务列表、命令面板（命令+技能）、skill zip 安装、LSP/Formatter 状态、工具调用时间线、拟合摘要、提示词模板 CRUD | `ai_chat.py:1314-1374,1462-1483,1507-1524,1665-1760`；`ai_chat_prompt_templates.py:38-98` |

同一套会话链路还有两个**消费方**：批任务子会话（分册 03，worker 是唯一写者）与公开客服 kefu（见 §6.3）。

## 4. 核心流程

### 4.1 建会话（复用分册 01 §4.1 五步，本册补充会话面语义）

`POST /ai/chat/sessions`（`@write_required`）→ workspace 创建 → 插行（先 `'_pending_'` 占位再由 `generate_token` 覆写）→ 写 `opencode.json`（平台 MCP 条目 `check-manage` + 外部注册合并 + 内部 MCP 开关）→ `inject_global_skills` 注入全局技能（best-effort，`ai_chat.py:153-158`）→ `client.create_session(directory=workspace)` → 回写 `opencode_session_id` → 操作审计。前端 `startNewSession` 记录进行中的创建 promise（`_pendingNewSession`），期间用户点发送会先等它落定，避免把消息发进上一个会话（`aiChat.ts:164-167,607-611`）。

### 4.2 发消息（`send_message`，`ai_chat.py:838-1041`）

1. **门禁**：`_execution_controlled`（批或编排子会话处于 `pending/running/paused`）→ 409 `BATCH_SESSION_CONTROLLED`；`AI_BATCH_STRICT_OWNERSHIP=0` 时降级放行（`:772-785`）。
2. **组装存储 parts**：`[{type:'text',text}, {type:'file',name,path}...]`——用户看到的是自己的原文 + 文件 chip。
3. **组装 agent prompt**（增强式，模型无关）：`_AGENT_DIRECTIVE`（系统规则：代码块/mermaid/echarts 制品约定、数据查询必须走 `query_collection`、git clone 到子目录等，`ai_chat.py:99-110`）+ 记忆块（`search_memory`+`render_memory_block`，limit 5）+ 原文 + 附件内联（utf-8 文本 ≤200KB 内联 fenced block，二进制/超限给绝对路径指针，`_read_text_attachment:1051-1063`）+ `@提及` 内联（`inline_file_mentions`：正则 `(?:^|\s)@([A-Za-z0-9_./\-\u4e00-\u9fa5]+)`，跳过 agent 名与已附文件，`mention_files.py:25-56`）+ 导出兜底（`is_export_intent` 且能解析集合 → 服务端直接 `export_collection_to_xlsx`，把「已导出文件路径」追加进 prompt 让 agent 转告而不再写脚本，`ai_chat.py:906-919`）。
4. **执行审计**：`execution_audit.create_attempt` 记录 requested vs effective agent/model、prompt 哈希与全部增强项（`ai_chat.py:949-984`；审计面归分册 06）。
5. **先挂监听再派发**：`ensure_listener` 必须在 `send_prompt_async` 之前——订阅晚了首段事件不可重放（`:985-990`）。
6. **派发与恢复**：`send_prompt_async` 抛 `RequestException` → `_recover_session_and_resend`：新建 OpenCode 会话 + `render_history_block` 注入历史 + 重绑 `opencode_session_id` + 重发（`:1066-1076`）；恢复再失败 → 结构化 502 `OPENCODE_UNAVAILABLE`（`retryable:true` + 已落库的 `messageId` 供前端清理重试，`:1012-1029`），绝不返回裸 500 让前端永远「正在回复」。
7. 返回 202 `{messageId, model, agent}`。

### 4.3 流式落库与双路收口

同一回合有**两条互为备份的持久化路径**（机制源在分册 01 §4.3，本册写对话助手的接线）：

- **后台监听器**：`ensure_listener` 为会话起守护线程订阅 per-directory 事件流，`apply_event` 把本会话与子代理事件分 scope 累积，`session.idle` 时 `persist_turn` 整轮落库；流中每 1s 增量落一次（切走会话不丢半截输出）。批子会话运行期由 worker 独家写（REST、按消息 id），监听器对其不落库（分册 03）。
- **浏览器 SSE 代理**（`GET /sessions/:id/events`，`@login_required_sse`，`ai_chat.py:1377-1459`）：逐事件转发给浏览器的同时跑同一套 `apply_event` 累积；收到 `idle`/`error` 时——无后台监听器接管且非批子会话 → 兜底 `persist_turn`（`error` 后流里可能永远等不到 idle，error part 是回合失败的唯一痕迹）；随后调 `agent_ledger.finalize_interactive_turn` 收口动作账本（幂等键 `(oc_session_id, part_id)` 去重，双路径只落一份账，`:1432-1441`）。

meta 聚合规则见 §2.1（`ai_message_meta.py`）：输入 token 取 max、输出/成本求和、时长取首尾。

### 4.4 前端 part upsert 状态机（`stores/aiChat.ts`）

OpenCode 发的是**按 part id 的全量快照**（≥1.15 起正文追加改发 `message.part.delta` 增量），store 的应对（模块级索引 `_streamingAssistantMsgId / _assistantMsgIds / _partIndexById / _reasoningByPart / _toolChildByMsg / _subtaskPartByMsg`，`aiChat.ts:156-163`）：

- `message.updated`：登记 assistant 消息 id；已完成快照自带 tokens → 就地刷新 `contextTokens` 水位线（`:989-1006`）。
- `message.part.updated`：`_upsertAssistantPart` 按 part id **存在即替换、不存在即追加**（`aiChat.ts:1200-1220`），渲染顺序=到达顺序。`tool:'task'` part 一旦在 `state.metadata.sessionId` 里出现真实子会话 id → 渲染/修正 `subtask_use` 气泡并启动 todo 轮询（`:1015-1047`）；`subtask` part 先渲染占位（权威状态展开时 REST 现取，`:1059-1074`）。
- `message.part.delta`：只拼 `field==='text'`（text 与 reasoning 共用 text 字段）；结构性字段无法按字符串增量拼装，留给 idle 后全量校正（`:1077-1100`）。
- `session.idle`：清 streaming/thinking → `loadFiles/loadChanges` → `_reloadPersisted`（拉服务端持久化版本收敛，仅在不打断新回合、且条数不少于内存时采纳，`:1163-1178`）→ `_drainQueue` 补发排队插话（`:1102-1114`）。
- `session.error`：顶层错误渲染 error part；**子代理自己的失败不带顶层失败语义**（`:1115-1133`）。
- reasoning part 按 partId 分开存、值直接拼接（OpenCode 会把一段连续推理拆成大量短 part，`:1189-1198`）。

回合生命周态：运行中插话**不调接口**，挂 `queuedBySession` 队列渲染「排队中」，idle 或 SSE 重连 open 时逐条 drain（`:136,621-627,696-711,899-910`）；发送失败收敛为 `turnFailure`（清 streaming、移除未确认本地气泡、保留原文供一键重试；重试先按服务端返回的 `messageId` `deleteFromMessage` 清理孤儿行再原样重发，`:642-673`）；SSE 重连成功后先查 `runtime-state` 再决定继续等流还是收敛到完成态（`_syncAfterReconnect:917-931`）。批子会话打开时**刻意不开 SSE**（worker 增量落库 + REST 轮询 `reloadMessages`，避免 live 流写进轮询替换后的过期下标，`:360-366,372-381`）。

### 4.5 问答卡与权限卡闭环

OpenCode 的 `question.asked` / `permission.asked` 事件**只发一次**——浏览器关页/重连期间的询问会永久丢失，所以 REST 侧提供再水化：

- `GET /pending-question` / `GET /pending-permission`：从 OpenCode 现查挂起列表并匹配本会话（`ai_chat.py:1819-1837,1880-1897`）；前端 `openSession` 时必调（`aiChat.ts:357-358`）。两者是**实时回合状态，刻意不进 messages**（`aiChat.ts:120-127`）。
- 应答：`POST /questions/:req_id/reply` / `POST /permissions/:req_id/reply`。`request_id` 必须命中**新鲜拉取的**本会话挂起列表（防拿他人 requestID 代答——OpenCode 自身端点不按我们的 session/user 收敛，`:1840-1861,1900-1919`）。权限应答 `once`（仅本次）/`always`（写进 OpenCode 配置全局放行）/`reject`（本次拒绝，模型继续）。
- 拒绝：`POST /questions/:req_id/reject`。
- 前端 SSE `question.replied/rejected`、`permission.replied/rejected` 回声也会清卡（多标签页场景），本地应答者走乐观清卡（`aiChat.ts:532-555,1140-1159`）。
- 无人值守的批子会话不走这套：workspace 已写项目级 allow、清扫自动拒绝（`:1883-1886`）。

### 4.6 会话状态语义（close / reopen / clear / delete / archive）与执行所有权

所有「改 status / 停 listener / 删上下文」的入口都过 `_execution_controlled` 门禁（409 `BATCH_SESSION_CONTROLLED`）：`compact`（主/子）、`send_message`、`run_session_command`、`delete_message_onwards`、`run_script`、`close`、`clear`、`delete`、admin `archive` 共十处（`ai_chat.py:803,852,1183,1730,1934,1993,2038,2105,2159,2243`）。**刻意不加门禁的例外**：`abort_session`（幂等生命线，重复调用/竞态自然完成都成功，OpenCode 不可达报 no-op 而非 500，`:1763-1786`）与 `abort_subtask`（父会话被 worker 驱动时用户仍必须能单独叫停失控子代理，`:1264-1307`）。

| 操作 | 语义 | 要点 |
| --- | --- | --- |
| `close` | 软关闭、可 reopen | 关闭运行中的会话**先 abort 在跑回合再停监听**（顺序保证尾部事件还能落库，不留「没人持久化的孤儿回合」，`:2047-2060`）；保留 token/workspace/OC 会话使 reopen 能续上 |
| `reopen` | `closed → active` | archived 403、deleted 409（`:2069-2085`） |
| `clear` | 原地重置 | 停监听 → 删旧 OC 会话 → rmtree 重建 workspace 脚手架 → 重签 token 重写 `opencode.json` → 新建 OC 会话（上下文重置）→ 删光消息与子任务 → 置 active；会话仍留在列表可立即继续用（`:2088-2143`） |
| `delete` | 个人硬删除 | abort → 停监听 → 删 OC 会话 → **先吊销 token 再标记 deleted**（安全边界优先）→ 清理 workspace；清理失败（Windows 句柄占用）返回 207 `WORKSPACE_CLEANUP_FAILED` 而不伪装全成功；行+消息保留审计（`:2146-2206`） |
| `archive`（admin） | 归档任意用户会话 | `admin.ai_chat_admin` 能力门；不按 user_id 过滤、不续期 `last_active_at`（`:2227-2257`） |

`runtime-state`（`:1789-1816`）：`turnStatus = running iff OpenCode session id 非空（bool(sess[2])）且会话 active 且有监听器`（`ai_chat.py:1808`），配合 `lastMessageId` 供前端重连后判定收敛方式。

### 4.7 NL 查询：`POST /ai/query`——翻译不执行（`ai.py:27-65`）

边界先行：**该端点只把自然语言翻译成 MongoDB 风格 filter JSON 返回，从不执行查询**。执行权在前端/数据页的既有查询通道（`utils/mongo_query.translate`），AI 只产草稿。

流程：`collection + question` → 从 `page_configs` 取 `page-{collection}` 的字段 schema（无则 404）→ `nl_to_mongo_filter`（`ai_query.py:186-273`：字段 schema 拼进 system prompt——跳过 `relation/reference/quoteSelect/file/image/richText` 等不可查类型（`_SKIP_TYPES`，`ai_query.py:24`），select 字段附选项表，操作符速查 + 「无法理解输出 `{}`」规则，temperature 0.1，剥 markdown 围栏后 `json.loads`）→ 安全兜底 `remap_labels`（LLM 可能输出中文标签）→ `mongo_translate` 干跑校验语法（不过 `MongoQueryError` 则 422 连同 `raw_filter` 返回）。LLM 未启用/无 Key/网络失败 → RuntimeError → 503（缺 API Key）/500（`ai.py:53-54`）。

复用机制：`ai_query.get_http_session()` 的进程级连接池化 Session（Retry on 429/5xx）同时被 NL 建页共用（`ai_schema_designer.py:19`）。

### 4.8 NL 建页草案：`utils/ai_schema_designer.py`

`draft_page_schema(description)`（`ai_schema_designer.py:188-254`）把一句业务描述（如「我要创建一张订货表」）翻译成 page-config **草案**（name/description/collectionSlug/menuName/menuPath/fields）。**只产草案，不建页**：消费方是 `POST /pageConfigs/ai-draft`（`page_configs.py:91-103`）与 MCP 工具 `ai_create_data_page`（二者复用同一服务端实现），正式建页必须由管理员在对话框逐项确认。

LLM 输出按**不可信输入**处理（防御性归一化）：`SAFE_CONTROL_TYPES` 白名单之外的 controlType 一律降级 `text`（`:24-28,105-107`）；`fieldName` 不合 `[a-zA-Z_][a-zA-Z0-9_]*` 就 slug 化并去重（`:91-103`）；select 无可用 options 降级 text 而不是交付不可用控件（`:116-128`）；`collectionSlug`/`menuPath` 强制 kebab-case（`:148-158`）；字段数 4–12 截断（`_MAX_FIELDS=12`，`:30,166`）；纯中文名 slug 化失败退 `table-N` 占位（`:83-88`，反正前端可编辑）。

### 6.3 kefu 消费方（公开客服复用对话助手链路）

kefu **不是**第二套对话系统，而是同一五步建链的租户化复用 + 一层公开身份钳制：

1. **bot 用户与角色**：`kefu-guest`（「智能客服访客」，只读、可见数据页需显式授予）由 `init_db.py:1740` / `scripts/migrate_kefu.py:30` 种子；`kefu_repo.ensure_bot_user` 在**每次建会话时重钉角色**（ON CONFLICT DO UPDATE），DB 手改无法悄悄扩权（`kefu_repo.py:27,171-178`）。
2. **会话创建**（`kefu_repo.create_kefu_session`，`kefu_repo.py:171-222`）：同 §4.1 五步，行上多 `kefu_instance_id + visitor_id`（`load_kefu_session` 按 visitor 归属校验）；工作区 `AGENTS.md` 追加「客服角色与边界」护栏块（`assemble_system_prompt`，`kefu_repo.py:160-164`）。公开入口 `server/routes/kefu_public.py`（无 JWT，`X-Visitor-Id` + 双桶限速 + SSE 并发帽），消息持久化复用 `chat_persist` 同一套监听/落库实现。
3. **MCP 通道钳制**（`mcp-server/rbac.py`）：
   - 身份判定：`PUBLIC_KEFU_ROLE='kefu-guest'`、`READONLY_ROLES={'guest','kefu-guest'}`（`rbac.py:7-8`）——早版本只守卫字面量 `'guest'` 曾被 kefu-guest 绕过，现集中一处（`rbac.py:3-5` 设计修正注记）。
   - **工具白名单**：`KEFU_TOOL_ALLOWLIST = frozenset({"query_collection", "list_collections", "read_upload"})`（`rbac.py:10`）——公开匿名客服只允许数据查询、集合列表、会话级上传读取三个只读工具。
   - **双防护执行点**：分发口 `tools/__init__.py._dispatch_tool` 白名单外抛 `PermissionError`（防护 a，`:62-70`）；`list_tools` 按角色过滤目录，kefu 会话里模型根本看不见其余 24 个工具（防护 b，`:73-84`）。另有各工具守卫纵深：`run_python.py:84` 与 `tools/_data_api.py:43` 对只读角色一律拒绝，`download_field_files.py:15` 刻意不在白名单内。
   - 身份解析仍走同一 token 链：`mcp-server/auth.py.validate_session_token`（`ai_chat_sessions` JOIN `users`，active+未过期）取 `role`（`auth.py:19-46`）。

## 7. 设计决策

1. **增强式 prompt 而非裸转发**（`_AGENT_DIRECTIVE` + 记忆块 + 附件/@内联 + 导出兜底）：把「产出制品、查真实数据、别臆造」等平台约定钉进每条 prompt，模型无关、可测试；存储消息与 agent prompt 分离，用户气泡保持原文。导出意图在服务端确定性完成（真 .xlsx 落 outputs/），不赌模型是否调用 MCP 工具（`ai_chat.py:99-110,866-919`）。
2. **先挂监听再派发**：SSE 事件不可重放，订阅晚于派发必丢首段；idle 时 REST 回填兜底竞态残余（`ai_chat.py:985-990`）。
3. **执行所有权统一门禁**（P0）：非终态批/编排子会话由 worker 独家驱动，十个会改状态的入口一律 409；abort 是唯一刻意豁免的生命线（含子代理级 abort），保证用户永远叫得停（`ai_chat.py:772-785`）。`AI_BATCH_STRICT_OWNERSHIP=0` 为渐进迁移降级开关。
4. **close/reopen/clear/delete 四态分明**：close 软关可逆、clear 原地重置可立即续用、delete 吊销 token 后标记（行保留审计、清理失败 207 不伪装）、archive 为 admin 治理态。关闭先 abort 再停监听的顺序是防「孤儿回合」的关键（§4.6）。
5. **上下文水位线（F1）**：`/models` 透出各模型 `contextLimit`，前端由消息 meta 实时算 `contextTokens`（流式中随每步 `message.updated` 刷新、idle 后按落库 meta 重算），`ContextStatusBar` 按 <70/70-90/≥90% 分级并在 ≥90% 弹「立即压缩」；压缩本身走后台线程的 `compact` 端点，结果作为普通回合经 SSE 回来（`ContextStatusBar.vue:1-8`；`aiChat.ts:989-1006,884-891`）。长会话另有「加载更早」的 seq 游标分页窗口（§5.1 #16），成本与性能双收敛。
6. **轨迹分析会话复用对话视图**：轨迹分析（`kind='trace_analysis'`）不建新前端——就是普通 AI 会话 + 系统侧栏分组（默认折叠、标题内嵌目标会话 id、不可移动/置顶/删除），分析产物照常享受 parts 渲染/制品/文件面板（`ai_chat.py:532-579`；`AiChatView.vue:1447-1465`）。
7. **搜索物化**：内容搜索从 jsonb 逐片段 ILIKE 改为 `search_text` 触发器物化 + `gin_trgm`（六处消息写入点一次覆盖），批子会话搜索用正向状态白名单而非 NOT IN（§3.2；`ai_chat.py:315-323`）。
8. **kefu 白名单只读**：公开匿名身份的工具面收敛为 3 个只读工具，且分发口与工具目录双层钳制、工具内第三层拒绝；bot 角色每次建会话重钉（§6.3）。
9. **NL 查询/建页只翻译不执行**：`/ai/query` 返回 filter 由既有查询通道执行（干跑校验 + 中文标签兜底重映射）；建页只产草案、controlType 白名单 + 防御归一化，正式建页必经管理员确认（§4.7/§4.8）。
10. **与代码的现状差异记录**：`ai_chat.py` 文件头 docstring（`:4-27`）的路由清单滞后（漏 13 个后增端点族），以本册 §5.1 为准——按全局约束不改产品代码，仅在此记一句。另 `server/routes/ai.py:282` 的 `delete_mcp_server` 引用了未导入的 `get_server`（运行时 NameError），该端点属分册 10，此处仅登记不展开。
