## 1. 模块职责

执行审计回答一个问题：**「这次 AI 执行，实际发生了什么」**。每一次 AI 执行（交互/批/扫描/客服/OpenAPI/轨迹分析……）在派发边界记一条统一形状的 attempt（请求的 vs 生效的 agent/model 及其**解析方式**、prompt 哈希、可见的定义清单），执行过程中追加不可变事件，回合收敛时收口；轨迹分析再在这些事实之上做诊断——**契约（该做什么）× 自声明计划（agent 说它做了什么）× 观测证据（工具实际跑了什么）三方对比**。全链路两条铁律：**采集绝不打断执行**（best-effort，异常只记日志）；**缺数据就说缺数据**（`unknown_due_to_missing_data`），绝不臆造违规或伪造默认值。

按职责分五块：

| 职责 | 说明 | 证据 |
| --- | --- | --- |
| 事实采集 | 六来源统一 attempt 形状 + prompt 快照（默认只存哈希）+ manifest 清单 + append-only 事件 | `server/utils/execution_audit.py`（390 行）`create_attempt :78`/`record_event :219` |
| 执行契约 | 结构化「应该做什么」：explicit=SKILL.md frontmatter / inferred=LLM 草案置信度<1 待审 | `server/utils/execution_contract.py`（113 行）`contract_for_skill :101` |
| 声明计划投影 | 从 todowrite/todoread 快照重建 agent **自述**计划——`src/utils/todos.ts` 的服务端孪生，永不当证据 | `server/utils/todo_trace.py`（100 行）`build_declared_plan :54` |
| 确定性审计器 | 三方对比产出结构化诊断报告；LLM 只解释事实、不制造事实 | `server/utils/trace_auditor.py`（468 行）`build_diagnosis_report :246` |

## 3. 数据模型

表结构以迁移文件为准（本表族全部由迁移创建，无 `db_schema/` 定义；除注明外均在 `server/migrations/2026_09_17_execution_audit_tables.py`，下称「审计迁移」）。

### 3.1 事实族（审计迁移七表）

- **`ai_execution_attempts`**（`:31-66`）——统一执行尝试。`session_id` FK `ai_chat_sessions` CASCADE；`source_type`（`interactive | batch | scan | kefu | open_api | row_action | trace_analysis | subagent`，`:35-37`）；`parent_attempt_id` 自引用 SET NULL（重排/续跑串链）；`attempt_no`（同会话序号，UNIQUE `(session_id, attempt_no)` `:68-69`）；`operation`（`send | retry | continue | resume | reexecute | command | analysis`）；requested/effective agent+model 与 `agent_resolution`/`model_resolution`（`requested | session_default | batch_default | runtime_default | fallback | unknown`）；`raw_prompt_hash`/`effective_prompt_hash`/`effective_prompt_len`/`prompt_version`；`workspace_path`/`workspace_config_hash`/`guidance_hash`；`status`（`accepted | running | completed | failed | stopped | orphaned | recovering`）。租约/心跳/fencing/queue_started_at/`recovery_reason`/`checkpoint_id`/`budget_snapshot` 十列由分册 03 的迁移补加（`2026_09_23_harness_p1_durable_execution.py:25-37`），并加**部分唯一索引** `uniq_attempt_running_per_session … WHERE status IN ('claimed','running')`（`:56-60`，谓词刻意不含 recovering——它是旧 attempt 的收口态，见该迁移 `:52-55` 注释）。

- **`ai_execution_manifests`**（`:96-115`）——本次执行可见的定义清单：`kind`（`skill | agent | guidance | mcp | workspace_config`）、`name`、`source`（`runtime_global | platform_global | project | session | generated`）、`path`+`content_hash`（SHA256）、四态观测列 `injected/injection_status/runtime_loaded/selected/invoked`（默认 FALSE/unknown）+ `evidence_refs` JSONB。
- **`ai_execution_events`**（`:123-142`）——不可变事件：`UNIQUE(attempt_id, event_seq)` `:141`（幂等锚）；`event_type`（现值：`dispatch.ok/dispatch.failed/dispatch.recovered/tool.state/message.updated/session.idle/session.error/skill.invoke/gate.evaluated` 等）；定位列 `session_id/parent_session_id/message_id/part_id/tool_call_id/parent_part_id/subtask_id`；`payload` JSONB + `redaction_status`。

### 3.2 Skill 调用族（`2026_09_18_skillopt_p2.py`）

- **`ai_skill_invocations`**（`:21-39`）——`session_id`/`attempt_id` 双 FK CASCADE；`skill_name`+`skill_hash`；`source`（`runtime | heuristic`，默认 heuristic）；`evidence_level`（`confirmed | inferred`）；`outcome`（`completed | failed | abandoned`，可空=进行中）；`tool_calls/duration_ms/evidence_refs`；**`UNIQUE (attempt_id, skill_name, skill_hash)` `:38`**（幂键）。`subtask_id` 列由拟合迁移补加（`2026_10_01_skill_fit_tables.py:68-70`，spec §5c 子代理归属标注）。
- **`ai_suggestion_feedback`**（`:46-59`）——`diagnosis_id` FK `ai_execution_diagnoses` CASCADE；`suggestion_id`；`action`（`accepted | rejected | modified | applied | rolled_back`）；`applied_value/applied_by/applied_at`；`before_metrics`/`after_metrics` JSONB（效果追踪前后快照）。

### 3.3 状态小结

attempt `status`：schema 默认 `accepted`，但 `create_attempt` 建行即写 `running`（`create_attempt :121-124`）→ `completed/failed`（`finish_latest_running`）→ 重排场景 `recovering`（旧条收口，分册 03）；`orphaned` 由分册 03 迁移对存量悬挂收口；`stopped`（FORCE_STOPPED）。Skill 调用 `outcome`：NULL（进行中）→ `completed`（`mark_session_idle` / status 上报）/ `failed`（status=error 上报）。诊断 `status`：`pending`（分析会话创建即插 `ai_session_admin.py:275-282`）→ `completed`/`partial`（`ensure_diagnosis_for_session :384-385`）→ `failed`（触发失败 `_fail :251-254`）。

## 4. 核心流程

总链：**采集（派发边界+过程+收敛）→ 契约建立 → 确定性审计诊断 → 管理员发起分析会话 → 报告与消费 → 建议反馈闭环**。

### 4.1 采集：派发边界统一 attempt + prompt 快照

每个 AI 执行来源在自己的派发边界调 `create_attempt`，落**同一形状**：

- **交互**（`ai_chat.py:951-999`）：`source_type='interactive'`、`operation='send'`、`prompt_version='chat-v1'`；resolution 显式声明（有指定→`requested`，走默认模型→`session_default`，否则 `runtime_default`，`:958-965`）；`augmentations` 记录增强链组成（agent 指令/记忆块/附件内联/@提及/导出兜底，`:964-975`）；随后 `scan_workspace_manifests` 落清单 + 请求的 agent 记为未注入的 manifest 行（`:978-984`）。
- **批/扫描/OpenAPI**（`batch_engine.py:1440-1476`）：一次子任务运行一条（continue/reexecute 各自成条），`source_type` 由会话行判定——`scan_task_id`→scan、批 `api_key_id`→open_api、否则 batch；`operation='continue'/'send'`；`parent_attempt_id` 串链；manifest 附 agent 行（provision 克隆来源标 `project`，否则 `batch_config`）；attempt id 关联进本轮 turn（`:1476`）。
- **kefu**（`kefu_public.py:261-286`）：`source_type='kefu'`、`source_id=kefu_instance_id`，agent/model 取实例当时配置快照（配置后改不篡改历史）。
- **轨迹分析**（`ai_session_admin.py:357-376`）：`source_type='trace_analysis'`、`operation='analysis'`、`prompt_version='trace-analysis-v1'`，manifest 首行=被注入的 trace-analyzer skill（`selected='requested'`、`source='platform_global'`、带 SKILL.md 哈希）。
- **Prompt 快照与明文默认不落库**：`create_attempt :132-145` 同时插快照行——`raw_user_content`/`effective_prompt` 明文列**仅当 `EXECUTION_AUDIT_PROMPT_PLAINTEXT=1`** 才写内容，否则为 NULL、`redaction_status='redacted'`；哈希/长度/增强项/上下文快照**永远记录**（`:9-13` 设计规则；测试 `test_execution_audit.py:59-60` 锁默认脱敏行为）。读侧 `execution-prompt` 端点只在 `redaction_status='plaintext'` 时返回明文并另要求 `admin.ai_execution_prompt_read` 权限+留痕（`ai_session_admin.py:550-591`）。
- **过程事件**：监听器把回合中的工具状态与消息更新压成事件摘要（`chat_persist.py:612-637` `_audit_capture`——attempt id 懒查一次、仅 running/accepted/recovering 时记录；异常全吞，审计绝不破坏持久化）；派发侧记 `dispatch.ok/failed/recovered`；`gate.evaluated` 由分册 05 的核对流程落时间线（`batch_engine.py:1586-1602`）。
- **收敛收口**：回合 idle/error → 启发式 Skill 采集 → 收敛拟合钩子 → `session.idle`/`session.error` 事件 → `finish_latest_running`（idle=completed / error=failed+`TURN_ERROR`，`chat_persist.py:700-728`）；批侧由 worker 终态标记与强制停止收口（`batch_engine.py:3075-3243`、`batch_repo.py:1447-1450`）。

### 4.2 契约建立：explicit 自动登记，inferred 待审

审计器需要「应该做什么」时按 `contract_for_skill :101-113` 取：DB 活跃契约优先；没有则解析该 skill 的 SKILL.md frontmatter `execution_contract:`，解析成功即**自动登记为 explicit（confidence=1.0）**——契约随定义文件走，无维护负担。inferred 来源（LLM/手动起草）按模块约定 `confidence<1`、需人工评审后才可转正（`execution_contract.py:5-9`）；`upsert_contract :59-79` 换版不覆盖历史。当前代码中 `upsert_contract` 的调用方只有 `contract_for_skill` 的显式自动登记，**「admin API 登记 inferred 契约」在模块 docstring `:7` 被提及但无对应路由**（§7-7 观测项）。

### 4.3 确定性审计诊断：三方对比

`ensure_diagnosis_for_session :363-417` 对最近一条终态 attempt：

1. **输入**：attempt 行 + manifest 清单 + 全量消息（`_load_messages :451-468`，按 seq 排序、content JSON 解析）+ 事件计数。
2. **声明计划**：`build_declared_plan`（todo 快照投影，evidence_level='declared_plan'）。
3. **观测证据**：`tool_calls_from_messages` 摊平 tool_use parts（带 `message:<id>#tool<序>` 定位）。
4. **契约**：遍历 skill manifest，逐个 `contract_for_skill`（带真实文件路径）取到即止（`:256-266`）；无契约 ⇒ contract 块 `unknown_due_to_missing_data`、violations 留空——**不臆造违规**（`:278-284`）。
5. **逐步骤比对**（`build_step_results :157-228`）：契约步骤 × todo 声明 × 工具证据三元判定——有证据看顺序（依赖倒置→`out_of_order`）与结果（error→`failed`，否则 `completed_confirmed`）；无证据时 todo 声明完成→`completed_claimed`（confidence=0.4，reason「Todo 声明完成，但没有工具证据」）、声明未完成或必需→`missing`、可选→`unknown_due_to_missing_data`。
6. **工具失败**：逐个 error 调用归类（八类信号 + 30s 时长兜底）并附恢复分析（同参重试/换策略/是否恢复，`:105-132`）。
7. **落库**：报告 upsert 进 `ai_execution_diagnoses`（同 attempt 复用最新行 `:390-400`）；步骤行重写进 `ai_execution_step_results`；`data_completeness` 七项检查打分（`:231-243`），缺契约在 `limitations` 里明说「无法审计步骤遗漏」（`:348-352`）。契约未就绪或完整性<1 ⇒ 诊断 `partial`。

诊断是**确定性事实**；trace-analyzer skill 的 LLM 叙述（分析会话产出）只在这些事实之上解释——`trace_auditor.py:8-10`「LLM explains the facts afterwards, it never manufactures them」。

### 4.4 管理员发起分析会话（analyze 闭环）

`POST /ai/chat/admin/sessions/v2/<sid>/analyze`（`ai_session_admin.py:155-409`），创建一个**真正的 AI 会话**来跑分析：

1. **预检 fail-fast**：MCP 服务器 `/health` 不通 → 502（分析 agent 的核心能力是 `analyze_trace`/`query_sessions`，缺了会退化成在文件系统里乱逛——实测观察写进注释 `:174-191`）；平台内置 MCP 被禁用 → 409（`:192-200`）；trace-analyzer 平台技能缺失/注入失败 → 409/502 **fail-closed，不建瞎会话**（`:294-303`）。
2. **建行**：`ai_chat_sessions` 插入 `kind='trace_analysis'` 会话（标题「轨迹分析: <sid>」，半角冒号+空格，`ai_session_admin.py:272`）+ `ai_execution_diagnoses` 插 `pending` 行（`analysis_id → target_session_id → analysis_session_id` 关联，`:263-282`）。
3. **建链**：会话 token → opencode.json（MCP url 带每会话 token，机制归分册 01）→ 仅注入 trace-analyzer 单技能（`inject_single_skill`，`:294-303`）→ OpenCode 会话 → 落分析 user 消息（prompt 模板带目标会话来源/状态/错误摘要，`:325-354`）。
4. **自审**：分析本身就是一次一等执行——`create_attempt(source_type='trace_analysis')` + manifest（含 skill 哈希）+ `dispatch.ok` 事件（`:356-400`）；派发失败收口 attempt 为 failed（`ANALYSIS_DISPATCH_FAILED`）。
5. **收敛收敛失败清理**：任何一步失败走 `_fail :236-261` 收敛——停监听、删分析会话消息与会话行、诊断行置 failed、清工作区，**不留孤儿行**（Spec §22 P0-8）。
6. **分析进行中**：分析会话复用对话助手持久化链路（`ensure_listener` 先挂再派发 `:378-380`）；分析 agent 经 MCP 调 `analyze_trace`/`query_sessions`（§5.3）读目标会话事实，按 SKILL.md 的流程产出诊断叙述。
7. **回看**：`GET /<sid>/analyses` 列目标会话的全部分析（含 analysis_session_id 可直开，`:414-438`）；`GET /analyses/<id>` 查状态、`GET /analyses/<id>/report` 取报告（报告列在返回时**现场重编译**确定性审计 `:628-636`——保存的是触发时的快照，读的是最新事实）。

### 4.5 Skill 调用采集与分层保留（SkillOpt P2）

- **确证路径（runtime）**：baize-trace 插件在 OpenCode 宿主内监听 `message.part.updated`（`tool='skill'`）→ POST `/ai/memory/internal/runtime-events`（`kind='skill'`，internal token 鉴权，`ai_memory_internal.py:56-71`）→ `record_runtime_skill_event`：OC 会话 id 映射平台会话（子代理归属根会话+`subtask_id` 标注）→ manifest 回写 `invoked='confirmed'` + `skill.invoke` 事件 + `ai_skill_invocations` runtime/confirmed 行（`skillopt.py:130-184`）。`session.idle` 上报（`kind='session.idle'`）把该会话 outcome 为 NULL 的调用收口 completed（`:187-203`）。
- **启发路径（heuristic）**：attempt 收敛时（本地 idle 先到不等插件并发路径，`chat_persist.py:700-717`）从 manifest × 工具证据推断，写 `source='heuristic'/evidence_level='inferred'` 行；同 attempt 已有 runtime 行的同名 skill **不再写推断行**（`skillopt.py:208-231`——UI 永不把推断呈现为确证）。upsert 的 DO UPDATE 保证 runtime/confirmed 不被启发数据降级（`:68-77`）。
- **聚合消费**：`GET /ai/chat/admin/skill-analytics`（`:776-839`）把 invocation 精确行与「存量清单 × attempt」兜底行 UNION ALL 后按 (name, hash) 聚合，runtime_confirmed/heuristic 两列分开计数；`/skill-analytics/versions`（`:661-698`）按 content_hash 拆版本算完成率 delta（P2）。
- **分层保留**（`apply_retention :399-416`，启动执行一次 + 每日 03:17 定时（`app.py:189-192,232-247`），持 `audit_retention` 调度租约多实例单跑 `app.py:283-297`）：事件 `payload` 30 天后清空（`EXECUTION_AUDIT_EVENT_PLAINTEXT_DAYS`，置 `redaction_status='expired'`）；事件行 180 天后删除（`EXECUTION_AUDIT_EVENT_ROWS_DAYS`）。**attempts/prompt 快照哈希/diagnoses/invocations 永存**（模块头 `:9-11`）。

### 4.6 管理面消费与前端闭环

- 审计抽屉一站式：`GET /sessions/<sid>/execution-audit`（`:524-532`）聚合 attempts+当前 attempt+manifests+events+现场构建的诊断报告（`_attempt_block :487-521`，终态 attempt 才构建）；events 详情端点 `:535-547`；prompt 快照端点 `:550-591`。存在未收口 attempt 时抽屉每 5s 轮询（`ExecutionAuditDrawer.vue:221-238`）。

## 7. 设计决策

1. **采集 best-effort、绝不打断执行**（`execution_audit.py:9-11,63-73`）：全部公共写入口经 `_safe` 包裹，失败记 warning 返回 None；唯一逃生门 `EXECUTION_AUDIT_STRICT=1` 供测试把静默失败变显式失败。监听器侧 `_audit_capture` 再包一层 try（`chat_persist.py:637`）——双层防护保证审计故障不阻断持久化与回合收口。
2. **明文 Prompt 默认不落库**（`:12-13,140-145`）：哈希/长度/增强项永远记录（可审计「改了什么形状」），正文需 `EXECUTION_AUDIT_PROMPT_PLAINTEXT=1` 显式开启且行级 `redaction_status` 标记；读侧再叠权限（`ai_execution_prompt_read`）+ `log_operation` 留痕——两层控制，默认最小暴露。
3. **resolution 语义「没说清就 unknown」**（`:93-96,103-108`）：effective 值为空时 resolution 保持 `unknown`，绝不假装用了默认值；调用方显式声明的 resolution 原样保留——审计报告里「为什么是这个 agent/model」永远可答。
4. **契约信任序 + unknown 不臆造违规**（`execution_contract.py:5-9`；`trace_auditor.py:278-284`）：explicit（文件 frontmatter，confidence=1.0）> inferred（草案，<1 待审）> 无契约（报告 `unknown_due_to_missing_data`，violations 为空）——审计器的权威性建立在「不虚构」上。
5. **Todo 永不当证据**（`todo_trace.py:5-7`）：自声明计划的证据级别固定 `declared_plan`；无工具证据的「已完成」只值 `completed_claimed`（confidence=0.4）——agent 自己说做完了不算完，三方对比里它只是「被告方陈述」。
6. **确定性规则在前、LLM 在后**（`trace_auditor.py:8-10`）：失败归类/步骤比对/评分全部规则化并带 evidence_refs；LLM（trace-analyzer）只解释既有事实。`analyze_trace` 的六维评分同理——LLM 依赖的两维显式 `computed:false`、总分标 `partial`，不把四维归一化冒充六维（`analyze_trace.py:291-336`）。
7. **分析引擎跑在 OpenCode 内部**（继承旧册 `11-AI执行轨迹分析.md`「核心架构决策」，代码证实后吸收）：`analyze` 端点创建真 OpenCode 会话 + 注入 trace-analyzer skill + 走 MCP 工具取数（`ai_session_admin.py:294-409`），复用对话持久化/工作区/多轮推理既有能力，平台侧不另起分析进程。旧册的 Layer 1/2 组件（`root_cause_classifier.py`、物化视图）在当前代码中**不存在**，未吸收。
8. **观测项**：`trace_auditor.contract_id_of :425-426` 恒返回 None——`ai_execution_step_results.contract_id` 现无写入值，契约关联靠 owner 列（模块注释自述「kept via owner」）；`ai_execution_diagnoses.attempt_id` 在 analyze 触发行上也未填（只填 target/analysis_session_id），后续如需按 attempt 检索诊断需补。
9. **观测项**：`execution_contract.py:7` 提及「admin API 登记」inferred 契约，但代码中 `upsert_contract` 的调用方只有 `contract_for_skill` 的 explicit 自动登记（全仓 grep 证实）——inferred 通道目前是模块预留，无路由落地。
10. **观测项**：迁移枚举的 `source_type='row_action'/'subagent'`（`2026_09_17:36-37`）与 `query_sessions` 的 `row_action` 枚举，当前**没有** `create_attempt` 写入路径（全仓仅 4 个创建点：interactive/batch+scan+open_api/kefu/trace_analysis）；`ai_session_admin.py:1022` 的 skill-fit 查询会匹配 `source_type='subagent'` 的 attempt，属于为未来写入预留的枚举。
11. **事件幂等靠「锁行 + 递增 seq」而非自然键**（`execution_audit.py:236-244`）：同一逻辑事件的重试应复用调用方选定的 event id，`record_event` 每次取新 seq；`UNIQUE(attempt_id, event_seq)` 兜底并发插入——P1-5 修复把「无锁 MAX+1 撞唯一约束被 `_safe` 吞掉、事件静默丢失」的缝堵上。
12. **Skill 调用双源合并，runtime 永不被降级**（`skillopt.py:68-77,208-231`）：确证（插件上报）与推断（清单×证据）同表共存，聚合端点分列计数、UI 不混presentation；`skill_hash` 归一 `''` 保证无 hash 上报也能命中唯一键幂等合并。
13. **与旧文档的关系**：`docs/design/AI执行审计能力说明.md`、`11-AI执行轨迹分析.md`、`11-AI-trace-analyzer-skill-spec.md`、`SkillOpt任务拟合设计.md` 等历史文档与本册冲突处以代码与本册为准；旧册 11 的「分析在 OpenCode 内部」结论已吸收（§7-7），其未落地组件见同节。
