## 1. 模块职责

动作门禁回答一个问题：**「该做的做了没，不允许做的别做」**。期望（expectation）在执行开始前登记，执行过程中每次工具调用落入账本，终态时逐条机械核对——核对不通过不算完成（fail-closed），核对本身不可证实（inconclusive）同样不算完成；语义级要求（正则穷举不了的过程/结论断言）交给 verifier 判官——一个只读取证的隐藏 OpenCode 会话按 rubric 逐条裁决。审批则补上事前防线：高危 step 在执行前挂起等人工裁决，与事后门禁互补、不互相替代（`approval_repo.py:3`）。

按职责分六块：

| 职责 | 说明 | 证据 |
| --- | --- | --- |
| 期望登记 | 三入口（批创建参数/模板携带/MCP 工具）+ 管理员补挂 + LLM 提炼建议；正则可编译性在此把关 | `server/utils/agent_ledger.py`（862 行）`validate_checks :292` |
| Pre 阻断 | PreToolUse deny list：插件每次工具调用前询问，`mode='pre'` 期望命中即阻断 | `server/routes/ai_gate_internal.py`（91 行）+ 插件 `utils/skillopt.py:247-364` |
| 动作账本 | OpenCode 消息里的 tool part 落账 `agent_tool_calls`，幂等、best-effort | `agent_ledger.py` `record_messages :100`/`record_state :137` |
| 终态核对 | 对某会话的全部 `mode='post'` 期望逐一计数核对；verifier 期望由判官核对 | `agent_ledger.py` `check_session_gate :646`；`server/utils/verifier.py`（513 行） |
| 试算与编写辅助 | dry-run 试跑正则、工具调用时间线、AI 提炼建议 | `server/routes/ai_chat_batches.py:185-299`；`server/utils/action_check_extractor.py`（147 行） |

## 3. 数据模型

表结构以 `server/db_schema/` 与迁移文件为准（证据为 `文件:行`）。三张本册表均无 `db_schema` 定义，全部由迁移创建。

### 3.1 `agent_tool_calls`（`2026_09_20_agent_action_gate.py:17-36`）

工具调用账本（append-only upsert）：`oc_session_id`+`part_id` **唯一索引** `uq_agent_tool_call_part :31-33`（幂键——轮询/快照重复投递与 SSE/REST 双落账路径只落一份）；`root_session_id`（树作用域查询键）、`subtask_id`（FK `ai_chat_subtasks` CASCADE）、`agent`（子代理动作归属，`2026_09_20:66-70` + 索引）、`tool`/`args_text`（压平文本，正则匹配对象）/`state`/`occurred_at`（落账时刻，非真实执行时刻，`agent_ledger.py:188-189`）。查询索引 `(oc_session_id, tool, state) :34-36`。存量消息回填迁移 `2026_09_29_tool_calls_backfill.py`（`part_id = message_id:序号`、ON CONFLICT DO NOTHING、随启动幂等执行）。

### 3.2 `action_expectations`（`2026_09_20_agent_action_gate.py:37-53` + 增列）

到位期望：`scope_type`（`session`/`tree`，`VALID_SCOPES agent_ledger.py:243`）+ `scope_id`（平台会话 id）+ `name` **唯一** `:52`（重复登记/重试续跑幂等覆盖）；`tool`+`args_pattern`（`tool` 型）、`require_state`（默认 `completed`）、`min_count`；`source`（`batch`/`mcp`）；核对回写列 `last_status`/`last_checked_at`/`last_evidence`。增列：`check_type`（`tool`/`file`/`db_record`/`verifier`，`2026_09_20:58-62`）与 `effect_spec` JSONB（`:63-64`，file 存工作区相对 glob、db_record 存 collection+Mongo filter、verifier 存 rubric）、`subagents` JSONB（`:71-72`，定向组名单）、`mode`（`2026_09_26_action_gate_mode.py:15-17`，`post`=终态核对默认回填 / `pre`=PreToolUse deny list）+ 热路径窄索引 `(scope_id, mode)` `:19-21`。

### 3.3 `ai_approval_requests`（`2026_09_23_harness_p2_orchestration.py:90-110`）

审批请求：`run_id`（FK runs CASCADE）+`step_id`、`risk_level`（默认 medium）、`tool`/`args_redacted`（脱敏入参，最小集未填）、`effect_summary`（收件箱展示文案）、`status`（`pending/approved/rejected/expired/cancelled`）、`requested_roles`/`requested_users` JSONB（点名对象）、裁决列 `decided_by`/`decision_comment`/`decision_hash`（sha256，`:104`）、`expires_at`/`resolved_at`。**部分唯一索引** `uniq_approval_pending_step ON (step_id) WHERE status='pending'` `:109-110`——每 step 至多一个 pending，天然防并发重复建单。

### 3.4 期望的承载列（批定义与模板）

`ai_chat_batches.action_checks` JSONB + `gate_retry` BOOLEAN（`2026_09_20:54-57,73-76`）、`ai_chat_prompt_templates.action_checks` JSONB（`:56-57`，落库经 `utils/prompt_template.py:30,74`）。创建/编辑路径先过 `validate_checks` 再落列（`ai_chat_batches.py:121-126,310-321`）——`action_checks` 必须落批列：编辑对话框重开的预填读这一列（`ai_chat_batches.py:310-313` 注释）。

### 3.5 状态小结

期望行 `last_status`：`pending`（登记初值/inconclusive 判官重置 `verifier.py:500-505`）→ `passed`/`failed`（核对回写 `agent_ledger.py:750-758`、`verifier.py:507-512`）。审批 `status`：`pending` → `approved`/`rejected`（CAS）→ `expired`（超时扫描）。子任务门禁结论不单独建表，落在 `ai_chat_sessions` 的终态与 error_message（`action_gate:` 前缀，`gate_failure_message :805-821`）与审计事件 `gate.evaluated`（`batch_engine.py:1588-1602`，归分册 06）。

## 4. 核心流程

### 4.1 期望登记：三入口 + 提炼与补挂

登记先于派发（`_register_action_expectations` 在 `_run_one` 派发前调用，`batch_engine.py:1336`），不存在「执行中才登记、错过早期动作」的漏登窗口；登记时把正则可编译性问题拦在 400（「不带病入库」）。

- **入口 A · 批创建参数**：`POST /ai/chat/batches` body `action_checks` → `validate_checks`（`ai_chat_batches.py:121-126`）→ `create_batch` 落 `ai_chat_batches.action_checks` 列（`batch_repo.py:289,294`）。编辑同口径（`update_config :302-353`，显式传入才更新；落列后 `sync_batch_expectations :351-352` 把非终态子任务期望替换、已终态的历史核对结果不重写，`agent_ledger.py:435-451`）。
- **入口 B · 模板携带**：`/ai/chat/prompt-templates` 的 `_payload` 校验 `action_checks`（`ai_chat_prompt_templates.py:30-34`）随模板落列；派发时批自身未配则**回退模板**（`_fetch_action_checks batch_engine.py:1740-1756`）——从模板创建的批任务自动继承。
- **入口 C · 交互会话 MCP 工具** `register_action_check`（`mcp-server/tools/register_action_check.py`）：主 agent 在派发子代理/执行关键动作**之前**把「必经动作」登记为期望，`handle :105` 直插 `action_expectations`（`source='mcp'`，`INSERT` `:113`）。红线：**模型不能增删已登记的期望**——核对在服务端，工具只有 INSERT、无删除/干预路径，登记后「不可由会话撤销」（工具 docstring `:1-9`）。强度说明：登记本身依赖模型调用，比 A/B 的确定性登记弱一档，适用临时/长尾需求（`:6-8`）。kefu-guest 公开身份不在白名单（`mcp-server/rbac.py:10` `KEFU_TOOL_ALLOWLIST` 仅三个只读工具）。工具 schema 只暴露 `name/tool/args_pattern/min_count/scope`——即入口 C 只能登记 `tool` 型 `post` 期望（无 `check_type`/`mode`/`rubric` 参数）。
- **派发登记（引擎侧）**：`_register_action_expectations`（`batch_engine.py:1763-1789`）取批/模板 checks，按 `apply_to` 条件过滤（`check_applies_to_child :454-477`：`batch_seq` 序号数组或输入文件名 glob——不匹配的子任务不登记，从源头消除误报），再 `register_session_expectations`（`agent_ledger.py:480-522`，按 `(scope_type,scope_id,name)` 幂等覆盖并把核对状态重置 pending）。**P0 fail-closed**（`batch_engine.py:1766-1771`）：登记异常不再降级 warning，`error` 非空 → 终态 inconclusive → failed，不得 completed。
- **入口 D · 管理员补挂**：`POST /ai/chat/batches/<id>/action-checks/attach`（`ai_chat_batches.py:268-299`）——运行中/排队中子会话逐会话登记，仅 admin（`:274-275`）。
- **入口 E · LLM 提炼（只出建议）**：`POST /ai/chat/batches/action-checks/extract`（`:247-265`）→ `extract_action_checks`（`action_check_extractor.py:88-147`）分析任务文本+Agent+已启用技能 SKILL.md，产出建议数组（≤8 条 `:21`；verifier rubric ≤2000 字由 `validate_checks :327-328` 把关）。**红线：提炼只产出建议，执行侧无增删期望的路径**（模块头 `:7`）——预填入口 A/B 表单，登记仍走创建/模板保存的人工确认（`ai_chat_batches.py:250-251`）。

`validate_checks`（`agent_ledger.py:292-417`）是全部入口共用的规范器：name 必填 ≤100 字且不重复（`:303-304,414-416`）；`check_type` 四类（`:244`）；`tool` 型必须给 tool+`args_pattern`，先 `re.compile`（`:338-341`）再 **PG 口径** `validate_pg_regex`（`:277-289`，真连库执行 `SELECT '' ~ %s`，仅 sqlstate 2201B 转 ValueError、基础设施故障原样抛）——核对执行、dry-run、登记三处同一口径（`:343-348` 注释）；`verifier` 型拒绝 `tool/args_pattern/min_count`、rubric 必填，落库时 `tool='verifier'` 归一化哨兵（NOT NULL 列惯例，`:312-332`）；`file`/`db_record` 的 `effect_spec` 走 `_validate_effect_spec :251-274`（路径必须工作区相对、防 `..` 逃逸；filter 经 `mongo_query.translate` 校验）；`mode=pre` 只允许 `tool` 型（`:358-360`——file/db_record/verifier 是效果断言，过程期无从拦截）；`subagents` ≤10 个名字（`:383-390`）、`apply_to` 结构校验（`:395-413`）。

### 4.2 Pre 阻断：PreToolUse deny list（P3-C3）

终态核对回答「该做的做了没」，pre 阻断补上「**不允许做的别做**」（`ai_gate_internal.py:3-6`）：

1. **登记**：入口 A/B 的 check 带 `mode:'pre'`（或模板/编辑路径），`validate_checks` 校验后随期望落 `action_expectations.mode='pre'` 行；迁移 `2026_09_26_action_gate_mode` 给存量行回填 `'post'` 并建 `(scope_id, mode)` 窄索引。
2. **询问**：OC 插件 baize-trace 注册 `tool.execute.before` 钩子（`skillopt.py:343-359`），每次工具调用前把 `{sessionId, tool, argsText}` POST 到 `/ai/gate/internal/pre-check`——`argsText` 经 `gateArgsText :278-291` 压平，与 Python 侧 `args_to_text` **同一文本形状**（两侧正则匹配同一对象）。`sessionId` 是 OpenCode 内部会话 id，服务端 `_resolve_scope_id :36-65` 映射：平台 id（`sess_` 前缀）原样；OC 内部 id 先查 `ai_chat_sessions.opencode_session_id`（最近活跃行优先），再查 `ai_chat_subtasks` 归属**根会话**——子代理动作受根上登记的 deny list 约束（期望登记在根作用域、约束整棵树）；都查不到原样返回（匹配不上 → allow，与无期望同义）。
3. **判定** `pre_check_tool`（`agent_ledger.py:529-560`）：取该 scope 全部 `mode='pre'` 且 `tool` 相等的行，`re.search(pattern, args_text)` 命中即 `{'allow': False, 'reason': 门禁规则「name」拦截了…}`；插件把 reason 抛错阻断该次调用，OC 将错误作为工具结果回给模型（`skillopt.py:356-359`）。返回 `rules=0` 时插件短路缓存 30s（`:558-560` + `skillopt.py:262-263`）——无规则是常态，热路径零开销。
4. **fail-open 三层**（分册 01 §5.1 口径，本册记机制位）：插件侧不可达/超时 3s/非 2xx（含 token 失配 403）一律放行（`skillopt.py:293-316`）；服务端 `pre_check_tool` 查询异常 → `allow:true` + 日志留痕（`ai_gate_internal.py:84-90`）；缺 sessionId/tool 直接 allow（`:81-82`）。拦截基础设施故障不得阻断全部工具调用，终态核对仍兜底。

### 4.3 执行落账：动作账本

- **批侧**：worker REST 轮询持久化对话时同步落账——根会话 `record_messages(oc_session_id, raw, root_session_id=sid)` + 逐子代理 `record_messages(child_sid, …, subtask_id, agent_name)`（`batch_engine.py:2939-2949`）；任一失败置 `_ledger_health[sid]=False`（`:781,2949`）。
- **交互侧**：两条路径互为备份、幂键天然去重——SSE 流 `idle`/`error` 信号处 `finalize_interactive_turn`（`ai_chat.py:1432-1442`），后台监听器收口处同样调用（`chat_persist.py:679-686`）；`record_state :137-181` 把 root 的 `parts_by_id` 与 `state['subtasks']` 里每个子代理的累积态落账，幂等与批任务共用同一张表。
- **幂等与写放大**：`INSERT … ON CONFLICT (oc_session_id, part_id) DO UPDATE SET state/args_text … WHERE … IS DISTINCT FROM …`（`:121-126`）——part 状态未变不产生行写入；同 part 重复投递取最后一次状态（`extract_tool_parts :91-97` 按 part_id 去重留最后）。
- **best-effort 契约**：落账失败记 warning 返回 `False`、绝不抛（`:132-134`「账本绝不打断任务流程」）——调用方据此把门禁判 **inconclusive**：不算未到位、也不静默放行（`:6-9` 模块头）。
- part 抽取 `extract_from_parts :73-88`：只收 `type='tool'` 的 part，`state.status` 缺省 `pending`，入参压平截断 8192。

### 4.4 终态核对

**批任务路径**（主链，`batch_engine.py:1548-1608`）：回合收敛 → `wait_subtasks_drained`（`:612-643`，轮询 `ai_chat_subtasks` 至无 running，批侧预算 120s `:38`——模型可能先于子代理结束回合，否则核对到「中途快照」）→ `_check_action_gate :1791-1831`：

1. `check_session_gate(sid, ledger_healthy=…)`（`agent_ledger.py:646-788`）取该 scope 全部 **`mode='post'`** 期望逐条核对（pre 行不参与——deny 规则在调用前已拦截，终态「该做的做了没」对它无意义，`:16-18`）：
   - `tool` 型：在账本计数——`tree` 作用域的会话集合 = 根 oc id + `ai_chat_subtasks` 全部子代理 id（`_subtree_oc_ids :567-583`），SQL `oc_session_id = ANY(…) AND tool=… AND state=require_state AND args_text ~ pattern`；带 `subagents` 名单时 JOIN `ai_chat_subtasks.agent = ANY(名单)` 定向计数（`:723-737`）；`session` 作用域只数根会话。命中 ≥ `min_count` 即 passed。
   - `file` 型：会话工作区内相对 glob 命中数（`_count_file_evidence :586-596`，封顶 `MAX_FILE_EVIDENCE=1000`）。
   - `db_record` 型：`dynamic_data` 按 collection+Mongo filter 计数（`_count_db_record_evidence :599-609`，与编排 output_contract 同一证据通道——分册 04 §4.5）。
   - `verifier` 型：证据循环跳过（`:705-708`——`args_pattern=''` 会让 `~ ''` 恒真），交判官（§4.5）。
   - 每条结果回写期望行 `last_status/last_checked_at/last_evidence`（`:750-758`）；无期望 → passed（门禁只约束登记过的事项，`:699-700`）。
2. inconclusive 语义（`:671-685,770-786`）：账本不健康/会话映射不到 oc/核对异常 → `{'status':'inconclusive','expected':N}`——**inconclusive 携带已登记期望条数**，供引擎区分「真的无期望」与「有期望但无法核对」（后者必须 fail-closed，不得当 skipped 静默放行）。
3. 引擎判定（`batch_engine.py:1558-1586`）：`gate_participates :700-707` 三信号（evaluated/applicable/expected 任一 >0 即参与判定）→ 登记失败/登记不完整/inconclusive 一律 `_mark_failed`（fail-closed，`:1587-1595`）；`failed` → `gate_failure_message :805-821` 压缩缺失明细（`action_gate: 名(需…,实际命中 x/y)`，verifier 条目渲染判官理由与 `[agent=名单]` 前缀）→ **gate_retry**：批级开关（`_batch_gate_retry_flag :1833`，NULL 跟随 env `AI_BATCH_GATE_RETRY` 默认关、True 时预算至少 1 次）预算内把子任务重排 pending 并注入定向修复提示「只补齐缺失动作」（`_maybe_gate_retry :1853-1897`，attempt 链收口 `recovering`）；否则 failed 终态。审计事件 `gate.evaluated` 随 attempt 落时间线（`:1588-1602`）。

**交互路径**（`finalize_interactive_turn :219-236`）：落账 → 等子代理收敛（预算 30s `:40`）→ `check_session_gate`——**不阻断回合**：failed/inconclusive 只写期望行与 warning 日志，由前端「工具调用/门禁」卡片与日志消费。

### 4.5 verifier 判官

`check_type='verifier'` 的期望无法穷举为正则（「结论覆盖要点」「必须先读后写」），判官方案 B（`verifier.py:1-6`）：终态核对时在**子会话工作区**开一个隐藏 OpenCode 会话，平台部署的 `baize-verifier` agent（`_AGENT_MD :42-72`：`mode: primary`、只读工具 `read/grep/list=true`、`write/edit/bash/task=false`）按材料逐条核对 rubric，以 JSON 契约返回 verdict。

- **部署与预检**：启动时 `ensure_verifier_agent :75-94` 幂等部署 agent md（`app.py:216-220`，部署后需重启 OC serve）；核对前 `_agent_registered :304-314` 用 `oc.list_agents` 预检——**未注册不建会话**，直接全条目 inconclusive（fail-closed；否则会以默认 primary agent 在受判工作区跑判官轮）。
- **分组核对**（2026-09-30，`:8-17`）：`collect_materials :126-204` 按 `_group_key :118`（无名单 = `(None,)` 全树组；有名单 = 排序名字元组）分桶——**全树组**材料 = 子任务最终回复全文（`ai_chat_messages` 最新 assistant，截断 8000 字）+ 全树工具轨迹（≤100 行）；**定向组**材料 = 名单内 agent 的全部子代理会话消息（`ai_chat_subtask_messages` 按 seq，每会话 ≤40 条/每条 ≤500 字）+ 这些子代理的轨迹；同一名单组合一组、每组一次判官会话。无 verifier 期望 → 返回 None，零开销跳过。
- **单组会话** `_run_group :317-392`：`create_session(directory=workspace)` + `send_prompt_async(agent=baize-verifier)` → 2s 轮询：总超时 180s/输出停滞 60s（快照不变判停滞）→ abort 会话、该组全条目 inconclusive；完成判定与 batch_engine 同口径（`time.completed` 非空且 finish 非 continuation），且**JSON 契约出现才算终判**（`:376-378`——finished 但只吐「思考中」继续轮询）。
- **契约解析** `parse_verdicts :247-277`：从回复抠 `{...}` 候选（契约要求最后输出，从后往前取），校验 name ∈ 期望清单、verdict ∈ passed/failed/inconclusive；不可解析/缺名不抛——缺名条目补 inconclusive（fail-closed）。契约本身要求「材料不足给 inconclusive 绝不凭空 failed」（`_AGENT_MD :60-67`，含「rubric 要求多次委派而材料未见 → 极可能仍在进行，判 inconclusive」指引）。
- **合并** `merge_verifier_results :444-513`：verdict 行并入 gate results 重算 overall——任一 inconclusive → 整体 inconclusive（携带 error，引擎 fail-closed）；否则任一 failed → failed；否则 passed。verdict 经 `ai_skill_fit_results`（`def_kind='verifier'`）落拟合证据（`:477-499`，attempt 现查最新行）；inconclusive 的期望行重置 `pending`（`:500-505`，等下一轮重判）。
- **用完即弃**：判官会话不落 `ai_chat_messages`/`ai_chat_subtasks`/账本，平台只保留 verdict 与证据引用——「会话用完即弃」（`:5-6`）。
- **委派级提前判定**（`batch_engine.py:2022-2246`）：定向组在名单内子代理全部终态时即可提前跑判官——守卫是**父回合已 finished**（材料才完整，`:2033-2046`）；passed 暂存 `_deleg_gate_results`（终态合并跳过重复判官），failed 未开 gate_retry 即写 `cancel_requested` 立即停（`:2220-2246`）、开了则暂存交终态定向修复。判定时机总体不变：任务子会话每轮终态各核对一轮（子代理终态即判无增益，`verifier.py:15-17`）。

### 4.6 dry-run 试算与编写辅助

### 4.7 效果账本衔接面（机制详述归分册 03 §3.5/§4.7）

副作用账本 `ai_execution_effects` 与动作门禁是**两条互补安全网**：门禁管「动作到位」，effect 管业务副作用的幂等与可恢复。衔接点只有三处：

1. **record → 执行 → settle**：每个外部副作用先 `record_effect`（幂键 `(session_id, effect_type, idempotency_key)`，`execution_effect.py:25-88`；批回调 outbox 入队时与终态同事务登记，`batch_engine.py:457-465`）→ 执行 → `settle_effect` 收口终态。条件更新状态机（`:104-117`）：`planned/started` 可落任意终态；`failed/unknown → committed` 是重试成功的正向收口；`unknown → failed` 允许首次超时后续判（避免粘滞）；`committed` 粘性不可再改。
2. **unknown 禁自动重放 → needs_review**：`has_unknown_effects :256-266` 存在 unknown 结局时，对账器恢复决策把该子任务分流 `_mark_needs_review`（`batch_engine.py:3310-3316`）——不计入完成、需人工复核后重试或重执行（`_mark_needs_review :3235-3262`，子任务行保留字面 `needs_review` 状态）。补偿通道 `compensate_effect :155-253` 仅支持 committed 的 mcp_write POST 创建记录（unknown 一律不动）。
3. **编排侧 effect 自动补偿**：step failed 终态时的补偿调用方在 `orchestration_engine.py:664-685`（分册 04 §4.7）。

### 4.8 执行前审批：HTTP 面、收件箱与裁决

审批请求行由编排引擎创建（结构 approval 节点 `_open_approval` / 策略拦截 `_open_policy_approval`，`orchestration_engine.py:583-652`——结构语义归分册 04 §4.5），本册写消费面：

- **端点表**（§5.2）：`GET /v1/ai-approvals`——admin 看全部（`list_all`），普通用户只看被点名待决（`get_pending_for_inbox`，`ai_approvals.py:17-26`）；`POST /<id>/approve`、`POST /<id>/reject` 统一 `_decide :41-73`。
- **权限**：admin 角色天然可决；非 admin 必须是 `requested_users`/`requested_roles` 点名对象（`can_decide approval_repo.py:32-39`；路由判断 `ai_approvals.py:57-62`）。
- **裁决幂等与审计**：先查 status，非 pending 返回既有状态 `duplicate:true`（`:60-62`）；pending 上 CAS（`WHERE status='pending'`，`approval_repo.py:69-74`）落 `decided_by/decision_comment/decision_hash/resolved_at`——**`decision_hash`** = sha256(`{id, decision, by, comment}` 规范化 JSON)（`:63-68`），可审计不可篡改。`uniq_approval_pending_step` 部分唯一索引保证每 step 至多一个 pending，与 CAS 双保险。
- **approve 可带 edits**：body `edits` dict（`ai_approvals.py:45-46`）→ `decide` 把修改 jsonb `||` 合并进 `ai_orchestration_runs.run_input_snapshot`（`approval_repo.py:124-137`）——「改参数后批准」，下游 step 渲染 `{{input.*}}` 用改后值。
- **决策写 log_operation**：`log_operation(…, f'{decision}（{comment}）')`（`ai_approvals.py:67-72`，best-effort 吞异常）。
- **超时**：`expire_overdue :150-182`（scheduler 每 tick 调，分册 04 §4.3）——pending 且过期 → `expired` + step failed('审批超时') + `approval.expired` 事件（escalation=treated_as_reject）。
- **前端入口**：`GET /workflow/inbox` 把 pending 审批投影进统一收件箱（`workflows.py:116-123`，`kind='ai_approval'`、非点名对象不可见 `approval_repo.py:198-201`）→ `WorkflowInbox.vue` 「我的待办」页直接通过/拒绝（`:32-37,85-92`）。

## 7. 设计决策

1. **三入口职责分离**（`register_action_check.py:5-8`）：A/B 是**确定性登记**——创建/保存时人工确认、服务端校验、落批列可审计；C 是**模型自主登记**——依赖模型调用，强度弱一档，只补临时/长尾需求；E（提炼）**只出建议**，预填表单，人工确认后才登记——三道机械校验（schema/正则 → dry-run 试算 → 人工确认）逐道收窄，执行侧自始至终无增删期望的路径（`action_check_extractor.py:7`）。
2. **fail-open 只给 pre 阻断，终态核对 fail-closed**：pre-check 三层放行（§4.2.4）是可用性取舍——拦截基础设施故障不得让全部工具调用瘫痪，且终态核对兜底；而终态核对自身不可证实（inconclusive）一律不算完成（`batch_engine.py:1553-1556`）。与数据写转发通道（`ai_data_internal` 白名单、失败即拒）的失败语义方向相反，是刻意的（分册 01 §7-6）。
3. **账本 best-effort + inconclusive 必须可区分**（`agent_ledger.py:6-9,671-685`）：落账失败不抛、绝不打断任务流程，但 `check_session_gate` 的 inconclusive 携带 `expected` 条数、`gate_participates` 把它算作参与判定信号——「有期望但无法核对」不会被当 skipped 静默放行。
4. **正则三处同一 PG 口径**（`agent_ledger.py:277-289,343-348`）：登记、dry-run、终态核对（`args_text ~ %s`）都以 PG `~` 为准；pre 阻断用 Python `re.search` 但登记时已按 PG 口径滤过方言——堵「登记过审、执行时 500」与「登记成永远无法核对的期望」两种缝。
5. **verifier 会话用完即弃、判官 fail-closed**（`verifier.py:3-6,304-314`）：判官不落消息表/子代理表/账本，平台只留 verdict 与证据引用；agent 未注册不建会话（防以默认 primary agent 带写权限跑判官轮）、契约不可解析/缺名/超时/停滞全部落 inconclusive——判官故障只会让任务「无法证实」而不会误放行或误判 failed。
6. **mode 拆分 pre/post 而非两张表**（`2026_09_26_action_gate_mode.py:2-6`）：deny 规则与效果断言共用登记/校验/承载列，只有核对时机不同；`mode='pre'` 限制 tool 型是语义必然（file/db_record/verifier 是效果断言，过程期无从拦截，`agent_ledger.py:245-247`）。
7. **审批与门禁互补、幂等双保险**（`approval_repo.py:3-4`）：事前人工裁决（edits 支持「改参数后批准」）不替代事后机械核对；`uniq pending per step` 部分唯一索引 + pending 状态 CAS + `decision_hash` 让重复决策、并发决策、篡改审计三类问题都有确定行为。
8. **观测项（沿用分册 04 §7-9 口径）**：`approval_repo.decide` 策略放行分支的 `command.applied` 事件重复 append 两次（`approval_repo.py:99-109`），多余一条重复事件、不影响状态。
9. **观测项**：`ai_approvals.py:67-72` 调 `log_operation` 的实参顺序与签名 `log_operation(action, target_type, target_id, target_name, description)`（`operation_log.py:83`）错位——`userId` 落进 `action` 位、`'update'` 落进 `target_type` 位；best-effort 吞异常不报错，留痕行口径失真，决策审计以 `ai_approval_requests` 行与 `decision_hash` 为准。
10. **观测项**：`register_action_check` 的 upsert 冲突目标 `(scope_type, scope_id, name)` 不含 `source`（`register_action_check.py:117-126`）——同名期望会被模型侧覆盖（含批侧 `source='batch'` 行），与「不能增删已登记期望」的红线存在同名覆盖的理论缝隙；无删除路径、核对在服务端，终态核对仍兜底。
11. **与旧文档的关系**：`docs/design/AI子任务动作账本与到位门禁设计.md`、`docs/design/AI动作门禁verifier判官核对设计.md` 等历史设计文档与本册冲突处，以代码与本册为准（`agent_ledger.py:3`、`2026_09_20:4` 仍指向旧文档，属历史引用）。
