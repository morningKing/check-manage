# 域⑪ AI 执行轨迹分析与优化

> 本文档是域⑨ AI 智能助手的扩展能力——**查询驱动**的执行轨迹分析、基于 MAST 失败分类法的主动跑偏检测、Agent-as-a-Judge 自动诊断、以及优化建议引擎。
>
> **核心架构决策：分析引擎运行在 OpenCode 内部，而非外部。** 通过 MCP 工具（确定性数据获取）+ Skill（智能分析指令）+ 直接 LLM API（低成本分类）的三层混合架构，让 OpenCode Agent 自己分析自己的执行轨迹，复用其工具调用、多轮推理、子代理委托等已有能力。

## 1. 模块职责

为平台 AI 能力（交互对话、批任务、定时扫描、行操作）的每一次执行提供**端到端可观测性 + 主动诊断**。解决三个层次的问题：

| 层次 | 问题 | 能力 | 实现方式 |
|------|------|------|---------|
| **L1 可见** | 执行数据散落各表，无法统一追溯 | 从已有表构建 trace tree + 链路关联 | MCP 工具 `analyze_trace`（确定性） |
| **L2 可析** | 失败了但不知道为什么 | 失败模式自动分类 + 根因定位 | 规则检测（确定性）+ OpenCode Skill（深度分析） |
| **L3 可优** | 知道原因但不知道怎么改 | 优化建议引擎 + 一键应用 | OpenCode Skill（智能建议）+ 直接 LLM（低成本分类） |

### 1.1 设计原则

**原则一：查询驱动，非侵入式**

项目已有的持久化层已覆盖 80%+ 的执行轨迹数据：

| 数据点 | 已有存储位置 | 字段 |
|--------|-------------|------|
| 工具调用（名称/输入/输出/状态/耗时） | `ai_chat_messages.content[]` | `type='tool_use'` 的 `name`, `input`, `result`, `status`, `durationMs` |
| 子代理委托（agent/描述/嵌套/对话） | `ai_chat_subtasks` + `ai_chat_subtask_messages` | 完整子代理对话树，支持 5 层嵌套 |
| 每轮耗时/Token/成本 | `ai_chat_messages.meta` | `durationMs`, `tokensInput`, `tokensOutput`, `cost` |
| 错误信息 | `ai_chat_sessions.error_message` + `ai_chat_subtasks.error_message` | 结构化错误类型 + 消息 |
| 工作区文件变更 | `ai_chat_session_files` | `path`, `status`(added/modified) |
| Agent/Model 配置 | `ai_chat_batches.agent/model` + `ai_chat_sessions.agent` | 批任务和会话级配置 |
| 推理过程 | `ai_chat_messages.content[]` | `type='reasoning'` |

**不需要新建 `ai_execution_traces` 冗余表，不需要 MCP Server 埋点中间件。**

**原则二：分析在 OpenCode 内部执行**

OpenCode 是平台的 Agent 运行时，具备：
- `get_messages()` — 获取任意会话的完整对话历史（REST API）
- `run_python` MCP 工具 — 在 workspace 中执行任意 Python（可查 DB）
- `save_artifact` MCP 工具 — 将分析报告写入 `outputs/` 供用户下载
- `memory_search/add` MCP 工具 — 跨会话记忆（可存储分析发现）
- 子代理委托 — 将分析任务分发给 specialized agent
- 多轮推理 — 分析过程中可迭代查询、验证假设

因此，**分析功能本身是一个 OpenCode Skill + MCP 工具的组合**，运行在 OpenCode 内部，复用其全部能力。

参考学术基础：
- **MAST（Multi-Agent System Failure Taxonomy）**：14 种失败模式 × 3 大类，来源 [Cemri et al., 2025](https://arxiv.org/abs/2503.13657)
- **Agent-as-a-Judge**：用 Agent 评估 Agent 的中间过程，来源 [Zhuge et al., 2024](https://arxiv.org/abs/2410.10934)

### 3.5 物化视图

从已有 `ai_chat_messages.meta` 聚合，不依赖 `ai_execution_traces`。

```sql
-- 每日成本归因（按用户 × 来源类型 × 天）
CREATE MATERIALIZED VIEW ai_cost_daily AS
SELECT
  date_trunc('day', m.created_at)::date AS day,
  s.user_id,
  CASE
    WHEN s.batch_id IS NOT NULL AND s.scan_task_id IS NOT NULL THEN 'scan'
    WHEN s.batch_id IS NOT NULL THEN 'batch'
    WHEN s.api_key_id IS NOT NULL THEN 'open_api'
    ELSE 'interactive'
  END AS source_type,
  COUNT(*)                                    AS message_count,
  SUM((m.meta->>'tokensInput')::int)          AS tokens_input,
  SUM((m.meta->>'tokensOutput')::int)         AS tokens_output,
  SUM((m.meta->>'cost')::numeric)             AS total_cost,
  AVG((m.meta->>'durationMs')::int)           AS avg_duration_ms
FROM ai_chat_messages m
JOIN ai_chat_sessions s ON s.id = m.session_id
WHERE m.role = 'assistant' AND m.meta IS NOT NULL
GROUP BY 1, 2, 3;

CREATE UNIQUE INDEX idx_cost_daily_uk
  ON ai_cost_daily(day, user_id, source_type);

-- MCP 工具调用统计（从 messages.content 中解析 tool_use）
CREATE MATERIALIZED VIEW ai_tool_metrics AS
SELECT
  date_trunc('hour', m.created_at) AS hour,
  part->>'name'                    AS tool_name,
  CASE
    WHEN s.batch_id IS NOT NULL AND s.scan_task_id IS NOT NULL THEN 'scan'
    WHEN s.batch_id IS NOT NULL THEN 'batch'
    WHEN s.api_key_id IS NOT NULL THEN 'open_api'
    ELSE 'interactive'
  END AS source_type,
  COUNT(*)                                           AS call_count,
  COUNT(*) FILTER (WHERE part->>'status' = 'completed') AS success_count,
  COUNT(*) FILTER (WHERE part->>'status' = 'error')     AS error_count,
  ROUND(AVG((part->>'durationMs')::int))               AS avg_duration_ms,
  PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY (part->>'durationMs')::int) AS p95_duration_ms
FROM ai_chat_messages m
JOIN ai_chat_sessions s ON s.id = m.session_id,
  jsonb_array_elements(m.content) AS part
WHERE m.role = 'assistant'
  AND part->>'type' = 'tool_use'
GROUP BY 1, 2, 3;

CREATE UNIQUE INDEX idx_tool_metrics_uk
  ON ai_tool_metrics(hour, tool_name, source_type);

-- Skill 效果汇总
CREATE MATERIALIZED VIEW ai_skill_daily AS
SELECT
  date_trunc('day', invoked_at)::date AS day,
  skill_name,
  skill_source,
  COUNT(*)                                          AS invocation_count,
  COUNT(*) FILTER (WHERE outcome = 'completed')     AS success_count,
  COUNT(*) FILTER (WHERE outcome = 'failed')        AS failed_count,
  ROUND(AVG(duration_ms))                           AS avg_duration_ms,
  ROUND(AVG(tokens_total))                          AS avg_tokens,
  SUM(cost)                                         AS total_cost
FROM ai_skill_invocations
GROUP BY 1, 2, 3;

CREATE UNIQUE INDEX idx_skill_daily_uk
  ON ai_skill_daily(day, skill_name, skill_source);

-- 失败模式统计
CREATE MATERIALIZED VIEW ai_failure_patterns AS
SELECT
  date_trunc('day', created_at)::date AS day,
  failure_category,
  failure_mode,
  severity,
  COUNT(*)                           AS occurrence_count,
  ROUND(AVG(confidence), 2)          AS avg_confidence,
  COUNT(*) FILTER (WHERE applied_at IS NOT NULL) AS remediation_count
FROM ai_failure_diagnoses
GROUP BY 1, 2, 3, 4;

CREATE UNIQUE INDEX idx_failure_patterns_uk
  ON ai_failure_patterns(day, failure_category, failure_mode, severity);
```

**刷新策略**：APScheduler 每 15 分钟执行 `REFRESH MATERIALIZED VIEW CONCURRENTLY`。与现有 `ai_scan_scheduler` 同进程、`WERKZEUG_RUN_MAIN` 守卫。

## 4. 核心流程

### 4.1 轨迹获取：查询驱动，非侵入式

```
                    已有持久化数据（零改动）
                    ─────────────────────
ai_chat_messages ──→ content[].tool_use    ──→ 工具调用序列
                 ──→ content[].subtask_use ──→ 子代理委托
                 ──→ content[].reasoning   ──→ 推理过程
                 ──→ content[].text        ──→ AI 输出
                 ──→ meta.{durationMs,     ──→ 性能指标
                     tokensInput/Output,
                     cost}
ai_chat_subtasks ──→ agent, status,        ──→ 子代理执行记录
                     error_message
subtask_messages ──→ content + meta        ──→ 子代理完整对话
session_files    ──→ path, status          ──→ 工作区变更
sessions         ──→ status, error_message ──→ 会话状态
batches          ──→ agent, model, status  ──→ 批任务配置与状态

                    分析引擎（新增，只读查询）
                    ─────────────────────────
trace_engine.build_session_trace(session_id)
  ├── _get_messages()    → 解析 content JSONB → tool_calls[], reasoning[], text[]
  ├── _get_subtasks()    → 递归构建子代理树
  ├── _get_performance() → 聚合 meta → total_duration/tokens/cost
  └── _get_files()       → 工作区变更列表

failure_detector.detect(session_id)
  ├── _detect_tool_loops()        → 从 tool_calls 序列检测
  ├── _detect_empty_output()      → 从 messages 检测
  ├── _detect_json_parse_failures → 从 scan 写回结果检测
  ├── _detect_token_anomalies()   → 从 meta 检测
  └── _detect_timeout_anomalies() → 从 tool_use.durationMs 检测
```

**关键区别**：原方案在 MCP Server 中插入 `trace_middleware` 拦截每次工具调用并写入 `ai_execution_traces` 表。修正方案**不新增任何埋点**，直接从 `ai_chat_messages.content` 中解析已持久化的 `tool_use` 数据——这些数据由 `chat_persist.py` 和 `batch_engine.py` 在会话结束时已经完整写入。

### 4.2 轨迹树构建

```python
# server/utils/trace_engine.py

class TraceEngine:
    """从已有表中构建执行轨迹树，纯只读，零侵入"""

    def build_session_trace(self, session_id: str) -> SessionTrace:
        """从已有数据构建完整执行轨迹"""
        # 1. 读取会话元数据
        session = self._get_session(session_id)

        # 2. 读取所有消息，解析 content JSONB
        messages = self._get_messages(session_id)
        tool_calls = []
        reasoning_parts = []
        for msg in messages:
            if msg['role'] != 'assistant':
                continue
            for part in msg.get('content', []):
                if part['type'] == 'tool_use':
                    tool_calls.append(ToolCall(
                        name=part['name'],
                        input=part.get('input'),
                        result=part.get('result'),
                        status=part.get('status'),
                        duration_ms=part.get('durationMs'),
                    ))
                elif part['type'] == 'reasoning':
                    reasoning_parts.append(part['text'])

        # 3. 读取子代理树（递归）
        subtasks = self._get_subtasks_recursive(session_id)

        # 4. 读取工作区变更
        files = self._get_session_files(session_id)

        # 5. 聚合性能指标
        performance = self._aggregate_performance(messages)

        # 6. 关联触发来源
        source = self._resolve_source(session)

        return SessionTrace(
            session=session,
            source=source,
            tool_calls=tool_calls,
            reasoning=reasoning_parts,
            subtasks=subtasks,
            files=files,
            performance=performance,
            messages=messages,
        )

    def _resolve_source(self, session: dict) -> dict:
        """关联到触发来源（批任务/扫描/行操作/API/交互）"""
        if session.get('scan_task_id'):
            scan_task = self._get_scan_task(session['scan_task_id'])
            return {'type': 'scan', 'id': session['scan_task_id'],
                    'name': scan_task['name'], 'record_id': session.get('source_record_id')}
        if session.get('batch_id'):
            batch = self._get_batch(session['batch_id'])
            return {'type': 'batch', 'id': session['batch_id'], 'name': batch['name']}
        if session.get('api_key_id'):
            return {'type': 'open_api', 'id': session['api_key_id']}
        return {'type': 'interactive'}
```

### 4.3 Skill 调用检测（唯一新增采集点）

Skill 不是结构化调用——它是 `SKILL.md` 文本被 LLM 解释执行。检测策略：在 `chat_persist.persist_turn()` 完成后，从已持久化的消息中推断。

```python
# server/utils/skill_tracker.py

SKILL_PATTERN = re.compile(r'使用 [`\']([^`\']+)[`\'] 技能[：:]')

def detect_skill_invocation(session_id: str, messages: list):
    """从已持久化的消息中检测 skill 调用，异步写入 ai_skill_invocations"""
    for msg in messages:
        if msg.get('role') != 'user':
            continue
        text = _extract_text(msg)
        match = SKILL_PATTERN.search(text)
        if match:
            skill_name = match.group(1)
            stats = _compute_skill_stats(messages, skill_name)
            _write_invocation(session_id, skill_name, stats)

def _compute_skill_stats(messages: list, skill_name: str) -> dict:
    """计算 skill 作用域内的统计（从 user 消息到会话结束）"""
    # 从 skill 调用消息开始统计
    tool_calls = 0
    tokens_total = 0
    cost = 0
    in_scope = False
    for msg in messages:
        if msg.get('role') == 'user' and skill_name in _extract_text(msg):
            in_scope = True
        if not in_scope:
            continue
        if msg.get('role') == 'assistant':
            for part in msg.get('content', []):
                if part['type'] == 'tool_use':
                    tool_calls += 1
            meta = msg.get('meta', {})
            tokens_total += meta.get('tokensInput', 0) + meta.get('tokensOutput', 0)
            cost += meta.get('cost', 0)
    return {'tool_calls': tool_calls, 'tokens_total': tokens_total, 'cost': cost}
```

**侵入点**（最小改动）：在 `chat_persist.persist_turn()` 末尾追加一行调用：

### 4.4 失败模式检测

基于 MAST 分类法，定义平台特定的失败模式目录。检测器在会话结束时自动触发，**直接分析已有消息数据，不依赖新增埋点**。

#### 失败模式目录

| 分类 | 模式 ID | 模式名称 | 检测信号（全部来自已有数据） | 典型表现 |
|------|---------|----------|--------------------------|----------|
| **系统设计** | `SD-01` | Prompt 模糊 | `messages.content` 输出格式不稳定 | 同一 prompt 不同记录的输出结构差异大 |
| | `SD-02` | 上下文溢出 | `meta.tokensInput` 接近模型上限 | 最后几轮工具调用失败率突增 |
| | `SD-03` | 工具选择错误 | `tool_use.name` 调用了不合适的工具 | 用 `run_python` 做简单查询 |
| | `SD-04` | Skill 指令冲突 | `reasoning` 中出现矛盾判断 | Skill 要求"不要修改"但任务需要写入 |
| **Agent 间失调** | `IA-01` | 子代理死循环 | `subtasks` 递归深度 > 阈值 | SubtaskBubble 嵌套 5 层仍未完成 |
| | `IA-02` | 信息丢失 | 子代理 `messages` 重复询问父代理已知信息 | 子代理 prompt 包含已知上下文 |
| | `IA-03` | 结果未回传 | 子代理有 `tool_use` 输出但父代理无对应 `text` | 子代理完成了但最终响应为空 |
| **任务验证** | `TV-01` | 输出格式错误 | scan `on_child_finished` 的 `extract_json` 返回 None | JSON 解析失败 |
| | `TV-02` | 输出内容幻觉 | AI 输出的 `jsonKey` 不在 `fieldMapping` 中 | 引用不存在的字段 |
| | `TV-03` | 回写失败 | `sessions.error_message` 包含 SQL 错误 | 目标字段类型不匹配 |
| **平台特定** | `PS-01` | 工具超时 | `tool_use.durationMs` > 30000 | `run_python` 长时间无响应 |
| | `PS-02` | 空输出 | `assistant` 消息无 `text`/`tool_use` content | AI 只返回了 reasoning |
| | `PS-03` | Token 消耗异常 | `meta.tokensInput` > 历史均值 × 5 | 可能陷入"读取→推理→再读取"循环 |
| | `PS-04` | 成本飙升 | 单会话 `meta.cost` > 阈值 | 死循环或过度工具调用 |

#### 检测器实现

```python
# server/utils/failure_detector.py

class FailureDetector:
    """从已有会话数据中检测失败模式，零侵入"""

    def __init__(self, trace_engine: TraceEngine):
        self.trace_engine = trace_engine

    def detect(self, session_id: str) -> list[Diagnosis]:
        """对一次会话执行全面的失败模式检测"""
        trace = self.trace_engine.build_session_trace(session_id)
        diagnoses = []

        # Phase 1: 规则检测（快速、确定性、零成本）
        diagnoses.extend(self._detect_tool_loops(trace.tool_calls))
        diagnoses.extend(self._detect_empty_output(trace.messages))
        diagnoses.extend(self._detect_json_parse_failures(trace))
        diagnoses.extend(self._detect_token_anomalies(trace.performance))
        diagnoses.extend(self._detect_timeout_anomalies(trace.tool_calls))
        diagnoses.extend(self._detect_subtask_depth(trace.subtasks))
        diagnoses.extend(self._detect_cost_anomalies(trace.performance))

        # Phase 2: LLM 辅助诊断（仅对高严重度触发）
        high_severity = [d for d in diagnoses if d.severity in ('high', 'critical')]
        if high_severity:
            llm_diagnoses = self._llm_assisted_diagnosis(trace, high_severity)
            diagnoses.extend(llm_diagnoses)

        # 写入诊断结果
        for diag in diagnoses:
            self._persist_diagnosis(session_id, diag)

        return diagnoses

    def _detect_tool_loops(self, tool_calls: list) -> list[Diagnosis]:
        """从 tool_use 序列中检测连续相同调用"""
        if len(tool_calls) < 3:
            return []
        for i in range(len(tool_calls) - 2):
            if (tool_calls[i].name == tool_calls[i+1].name == tool_calls[i+2].name
                and tool_calls[i].input == tool_calls[i+1].input == tool_calls[i+2].input):
                return [Diagnosis(
                    failure_mode='IA-01', severity='high', confidence=0.95,
                    evidence={'tool_name': tool_calls[i].name,
                              'repeated_times': 3,
                              'input_summary': str(tool_calls[i].input)[:200]},
                )]
        return []

    def _detect_empty_output(self, messages: list) -> list[Diagnosis]:
        """从 messages 中检测空输出"""
        for msg in messages:
            if msg['role'] != 'assistant':
                continue
            content = msg.get('content', [])
            has_text = any(p['type'] == 'text' and p.get('text', '').strip() for p in content)
            has_tool = any(p['type'] == 'tool_use' for p in content)
            if not has_text and not has_tool and content:
                return [Diagnosis(
                    failure_mode='PS-02', severity='medium', confidence=0.90,
                    evidence={'message_id': msg['id'], 'content_types': [p['type'] for p in content]},
                )]
        return []
```

```python
def diagnose_session_async(session_id: str, only_on_failure: bool = True):
    """异步触发失败诊断"""
    def _run():
        try:
            session = get_session(session_id)
            if only_on_failure and session.get('status') not in ('failed', None):
                return
            FailureDetector(TraceEngine()).detect(session_id)
        except Exception:
            pass  # 诊断失败不影响业务
    threading.Thread(target=_run, daemon=True).start()
```

### 4.5 根因分析：三层混合架构

根因分析采用**三层递进**策略，根据分析深度和成本选择不同的执行方式：

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 1: 规则检测（确定性，零成本）                           │
│  failure_detector.py — 8 条规则覆盖已知失败模式               │
│  输出：failure_mode + severity + evidence                    │
│  触发：每次会话结束                                          │
└──────────────────────┬──────────────────────────────────────┘
                       │ 高严重度
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Layer 2: 直接 LLM 分类（轻量，低成本）                       │
│  root_cause_classifier.py — 调用 ai_settings 的 LLM API     │
│  输出：root_cause + suggestions JSON                         │
│  触发：仅 high/critical 严重度                               │
│  成本：~800 token/次，复用 ai_query.py 的 HTTP 连接池         │
└──────────────────────┬──────────────────────────────────────┘
                       │ 需要深度分析
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Layer 3: OpenCode Skill 深度分析（智能，高能力）              │
│  trace-analyzer Skill — 在 OpenCode 内部执行                 │
│  能力：                                                     │
│    • 调用 analyze_trace MCP 工具获取结构化 trace              │
│    • 调用 run_python MCP 工具执行自定义分析脚本               │
│    • 多轮推理：假设 → 验证 → 修正                            │
│    • 子代理委托：分发给 specialized agent                     │
│    • 查询同类成功案例做对比                                   │
│    • 生成详细的分析报告（save_artifact）                      │
│  触发：用户主动请求 / critical 严重度自动触发                 │
│  成本：~3000-8000 token/次（含系统提示 + 工具调用）           │
└─────────────────────────────────────────────────────────────┘
```

#### Layer 2: 直接 LLM 分类（`root_cause_classifier.py`）

对 Layer 1 检测到的高严重度失败，用轻量 LLM 做结构化分类。**不使用 OpenCode**——这是单轮 JSON→JSON 推理，复用 `ai_query.py` 的 HTTP 调用模式即可。

```python
# server/utils/root_cause_classifier.py

from utils.ai_query import get_ai_settings, get_http_session

CLASSIFIER_PROMPT = """你是 AI Agent 执行轨迹分析专家。分析以下失败会话，输出 JSON。

## 失败模式: {failure_mode}
## 证据: {evidence_json}
## 用户请求: {user_prompt}
## 工具调用序列: {tool_call_sequence}
## 错误信息: {error_message}

输出 JSON:
{{"root_cause": "根因（1-3句）", "suggestions": [{{"type": "...", "target": "...", "description": "...", "effort": "low|medium|high", "impact": "low|medium|high", "auto_applicable": true/false, "suggested_value": "..."}}], "confidence": 0.85}}"""

class RootCauseClassifier:
    """Layer 2: 直接调用 LLM API 做根因分类（非 OpenCode）"""

    def classify(self, trace: SessionTrace, diag: Diagnosis) -> Diagnosis:
        cfg = get_ai_settings()
        if not cfg['enabled'] or not cfg['apiKey']:
            return diag

        prompt = CLASSIFIER_PROMPT.format(
            failure_mode=diag.failure_mode,
            evidence_json=json.dumps(diag.evidence, ensure_ascii=False)[:500],
            user_prompt=trace.user_prompt[:300],
            tool_call_sequence=self._summarize_tools(trace.tool_calls),
            error_message=trace.error_message[:200],
        )

        result = self._call_llm(cfg, prompt)
        diag.root_cause = result.get('root_cause', '')
        diag.suggestions = result.get('suggestions', [])
        diag.confidence = result.get('confidence', diag.confidence)
        return diag
```

#### Layer 3: OpenCode Skill 深度分析

当 Layer 2 的分类不够（`confidence < 0.6` 或用户主动请求深度分析）时，触发 OpenCode Skill。分析任务在 OpenCode 内部执行，Agent 可以使用全部 MCP 工具和多轮推理能力。

**触发方式**：平台创建一个新的 OpenCode session，注入 `trace-analyzer` Skill，发送分析 prompt：

```python
# server/utils/trace_analysis_orchestrator.py

def trigger_deep_analysis(session_id: str, diagnosis_id: str):

- 分类: {diagnosis.failure_category}
- 模式: {diagnosis.failure_mode}
- 证据: {json.dumps(diagnosis.evidence, ensure_ascii=False)}

    # 5. 发送到 OpenCode（Agent 会自动使用 trace-analyzer Skill）
```

#### 三层的选择逻辑

```python
# server/utils/diagnosis_orchestrator.py

def orchestrate_diagnosis(session_id: str):
    """编排三层诊断"""
    # Layer 1: 规则检测（总是执行）
    trace = trace_engine.build_session_trace(session_id)
    diagnoses = failure_detector.detect(trace)

    if not diagnoses:
        return

    for diag in diagnoses:
        # Layer 2: LLM 分类（高严重度触发）
        if diag.severity in ('high', 'critical'):
            diag = root_cause_classifier.classify(trace, diag)
            persist_diagnosis(diag)

            # Layer 3: OpenCode 深度分析（条件触发）
            if diag.confidence < 0.6 or diag.severity == 'critical':
                trigger_deep_analysis(session_id, diag.id)
```

#### 为什么深度分析用 OpenCode 而不是直接 LLM API

| 维度 | 直接 LLM API（Layer 2） | OpenCode Skill（Layer 3） |
|------|------------------------|--------------------------|
| 调用方式 | 单轮 HTTP POST | 多轮 Agent 会话 |
| 工具能力 | 无 | `analyze_trace` + `run_python` + `query_sessions` + `save_artifact` + `memory_search` |
| 推理深度 | 单轮，受限于 prompt 长度 | 多轮，可迭代假设→验证→修正 |
| 上下文获取 | 由调用方构造，固定 | Agent 按需查询，动态获取 |
| 成本 | ~800 token | ~3000-8000 token |
| 延迟 | 0.5-2s | 10-60s |
| 适用场景 | 已知模式的快速分类 | 未知模式的深度探索 |

**结论**：Layer 2（直接 LLM）做"快筛"，Layer 3（OpenCode）做"精诊"。80% 的问题在 Layer 2 已解决，只有 20% 需要 Layer 3 的深度分析。

### 4.6 优化建议引擎

```python
# server/utils/optimization_advisor.py

class OptimizationAdvisor:
    """将诊断结果转化为可操作的优化建议"""

    # 安全边界：这些类型永远不自动应用
    MANUAL_ONLY_TYPES = {'prompt_rewrite', 'skill_update'}

    # 这些类型可以自动应用（有频率限制）
    AUTO_APPLICABLE_TYPES = {'agent_switch', 'config_change', 'filter_adjust', 'field_mapping_fix'}

    def apply_suggestion(self, diagnosis_id: str, suggestion_idx: int, user_id: str):
        """采纳建议"""
        diagnosis = self._get_diagnosis(diagnosis_id)
        suggestion = diagnosis['suggestions'][suggestion_idx]

        if suggestion['type'] in self.MANUAL_ONLY_TYPES:
            raise ValueError(f"类型 {suggestion['type']} 需要人工审核，不能自动应用")

        if suggestion.get('auto_applicable') and diagnosis['confidence'] >= 0.8:
            self._do_apply(suggestion)
            self._record_feedback(diagnosis_id, suggestion_idx, 'applied', user_id)
        else:
            self._record_feedback(diagnosis_id, suggestion_idx, 'pending_review', user_id)
```

## 8. 设计决策

### D1: 查询驱动 vs 侵入式埋点

**决策**：不新建 `ai_execution_traces` 表，不新增 MCP 埋点中间件，直接从已有 `ai_chat_messages.content` JSONB 中解析执行轨迹。

**理由**：
- 项目已有的持久化层（`chat_persist.py` + `batch_engine.py`）已经将完整的工具调用、子代理委托、推理过程、性能指标写入 `ai_chat_messages`
- 新增 `ai_execution_traces` 表会导致数据冗余，增加写入开销和一致性风险
- MCP Server 埋点需要 HTTP 回调 Flask，引入额外的网络延迟和故障点
- 查询驱动方案的唯一代价是 JSONB 解析开销（< 10ms/会话），远低于侵入式方案的持续写入开销
- **已知限制**：每轮的 per-message token 细分未持久化（`public_meta()` 剥离了内部时间戳），但对分析场景足够——轮级聚合已覆盖 95% 的分析需求

### D2: 两处最小侵入点

**决策**：仅在 `chat_persist.persist_turn()` 末尾追加 skill 检测调用，在 `batch_engine._run_one()` 完成时追加失败诊断触发。

**理由**：
- Skill 调用无法从 OpenCode 事件中结构化获取（它是 LLM 解释的文本），只能从已持久化的消息中推断
- 失败诊断需要在会话结束时触发，但异步执行、失败不影响主流程
- 两处改动都是"追加一步"，不修改现有业务逻辑，不增加数据库写入路径

### D3: 失败检测策略 — 规则 + LLM 两层

**决策**：规则检测（快速确定性）→ LLM 诊断（深度分析，仅高严重度触发）。

**理由**：
- 规则检测覆盖 8 种已知模式（tool_loop、empty_output、json_parse_fail、token_spike、timeout、subtask_depth、cost_spike、output_deviation），零成本
- LLM 诊断仅对 high/critical 触发，预计 < 5% 的会话会触发
- 参考 MAST 论文的三分法，覆盖学术界已验证的 14 种失败模式

### D4: LLM 诊断成本控制

**决策**：轻量模型 + 触发门槛 + 频率限制 + 缓存。

**理由**：
- 诊断不需要强推理能力，token 预算 < 2000/次
- 每个 session 最多诊断 3 次（防止"诊断风暴"）
- 同类失败模式的 few-shot 案例缓存 24 小时
- 预计月增成本 < 总 AI 成本的 2%

### D5: 优化建议的安全边界

**决策**：`prompt_rewrite`/`skill_update` 永远不自动应用，`agent_switch`/`config_change` 可自动应用但有频率限制。

**理由**：
- Prompt 和 Skill 直接影响 AI 行为，自动修改风险高
- Agent 切换和配置调整是低风险操作，有明确回滚路径
- 每个目标每天最多自动应用 2 次，防止抖动
- 所有自动应用记录到 `operation_logs`，支持一键回滚

### D6: Agent-as-a-Judge 的适用边界

**决策**：用 LLM 分析执行轨迹的"过程质量"，而非仅判断"结果对错"。

**理由**：
- "跑偏"往往发生在过程中间步骤，而非最终结果
- 将完整 tool_call 序列 + reasoning tokens 喂给诊断 LLM，判断"执行路径是否合理"
- 始终附带 `confidence` 分数和 `evidence`，供人工复核

### D7: 根因分析 — 三层混合架构（规则 + 直接 LLM + OpenCode Skill）

**决策**：根因分析采用三层递进架构：Layer 1 规则检测（确定性）→ Layer 2 直接 LLM 分类（低成本）→ Layer 3 OpenCode Skill 深度分析（高能力）。

**理由**：
- **Layer 1**（规则检测）覆盖 8 种已知失败模式，零成本、零延迟，是所有分析的起点
- **Layer 2**（直接 LLM API）对高严重度做快速分类，复用 `ai_query.py` 的 HTTP 连接池和 `ai_settings` 配置，单次 ~800 token，适合"已知模式的快筛"
- **Layer 3**（OpenCode Skill）对 Layer 2 置信度不足或 critical 严重度的场景做深度分析，运行在 OpenCode 内部，可调用 `analyze_trace`/`run_python`/`query_sessions`/`save_artifact` 等 MCP 工具，支持多轮推理和子代理委托，适合"未知模式的精诊"
- 80% 的问题在 Layer 2 已解决，只有 20% 需要 Layer 3，成本可控
- 分析功能本身作为 OpenCode Skill 发布，可被用户在交互对话中直接调用（"帮我分析这个会话的执行轨迹"），无需额外开发前端
- 分析发现可经 `memory_search/add` MCP 工具存入长期记忆，实现跨会话知识积累

**OpenCode 作为分析引擎的优势**：
- 工具能力：`analyze_trace`（结构化 trace）+ `run_python`（自定义脚本）+ `query_sessions`（历史查询）+ `save_artifact`（报告输出）+ `memory_search`（知识积累）
- 多轮推理：假设 → 验证 → 修正的迭代分析过程
- 子代理委托：可将"对比成功案例"等子任务分发给 specialized agent
- Skill 生态：分析指令以 SKILL.md 形式发布，可被所有用户复用，无需额外开发

### D8: 物化视图数据源

**决策**：物化视图从已有 `ai_chat_messages.meta` 和 `ai_chat_messages.content` 聚合，不依赖 `ai_execution_traces`。

**理由**：
- `ai_tool_metrics` 通过 `jsonb_array_elements(content)` 展开 `tool_use` 部分，直接统计
- `ai_cost_daily` 从 `meta.{tokensInput,tokensOutput,cost}` 聚合
- 唯一需要新表的是 `ai_skill_invocations`（Skill 调用推断结果）和 `ai_failure_diagnoses`（诊断结果）
- 减少一个大表（`ai_execution_traces`）的写入和维护开销
