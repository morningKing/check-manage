## 1. 模块职责

批任务与开放 API 子会话是**无人值守**运行的：用户发起后通常会离开，任何故障都不能靠"用户看到报错再点重试"收敛。本册覆盖的容灾体系回答一个问题：**从单回合派发失败到整机崩溃，系统如何自动把残账收敛到一致终态——以及在哪些边界上刻意拒绝自动处理、转人工复核。**

按故障作用面分层：

| 层 | 故障 | 兜底机制 | 自动/人工边界 | 证据 |
| --- | --- | --- | --- | --- |
| serve 进程级 | OpenCode serve 运行中挂掉 | 看门狗连续不可达自动 `restart_serve()` | 只拉起进程，**不重放**失败子任务（重放属对账器/人工） | `server/utils/oc_watchdog.py` |
| 实例级 | 多进程部署双跑 / 后端崩溃后重启 | 执行器租约（dispatcher/delivery/scheduler/oc-watchdog 四类键）+ 会话级执行权租约 + fencing token | 心跳连丢 3 次整实例让位；租约绝不打断调用方 | `server/utils/execution_lease.py`、`batch_engine.py:819-895` |
| 会话级 | 后端崩溃残留 running 行 | 运行中对账器 `_reconcile_stale_running` 前置两闸+六分支对账 | unknown 副作用 → needs_review **禁自动重放**；无进度证据 → 带因失败 | `batch_engine.py:3264-3368` |
| 派发级 | `send_message` 对旧 oc 会话派发失败 | `_recover_session` 新建会话 + 历史摘要重注入 | 恢复失败带真实原因落 failed，不静默重试 | `batch_engine.py:2436-2458`、`session_history.py` |
| 回合级 | 停滞/工具卡死/provider 瞬时错/门禁不过 | 重试分类 + auto-retry 预算 + gate_retry 定向修复 | 预算 `MAX_AUTO_RETRY=2` 用尽落 failed；密钥错/用户中断保守不重试 | `batch_engine.py:3161-3214,1853-1897` |
| 进度级 | 崩溃后"执行到哪"无从证明 | checkpoint 快照（dispatch/progress/turn_complete/recovery 四时机） | best-effort，checkpoint 失败不阻断执行 | `server/utils/execution_checkpoint.py` |
| 交付级 | 回调 HTTP 失败/超时/进程 kill | outbox 退避重投 + 死信 + 人工重放 | 8 次退避后 dead_letter 等人工；uncertain 结局触发 fail-safe | `server/utils/delivery_outbox.py`、`ai_batch_admin.py:448-465` |
| 资源级 | token/成本/时长/并发超限 | 预算 on_exceed：warn/drain/abort | 机制主描述在 03 册 §4.5，本册只记兜底动作语义 | `server/utils/execution_budget.py` |
| 验证 | 上述防线在真实故障下是否兜得住 | 专属压测栈（stub 容量层 + 真 serve 混沌层） | 套件部分落地（§4.10） | `server/tests/stress/` |

历史脉络：`docs/design/archive/AI批任务容灾与恢复机制.md` 是 2026-09-28 事故后的机制梳理（三层防线叙事沿用至今）；本文以当前代码为准重新组织，旧文档与代码冲突处以代码与本册为准。

## 3. 数据模型

### 3.1 `ai_batch_worker_leases`（`migrations/2026_09_23_harness_p0_execution_safety.py:60-66`；`lease_kind` 由 p1 迁移补，`2026_09_23_harness_p1_durable_execution.py:213-215`）

单行主键 `lease_key`、`lease_kind`（默认 `'dispatcher'`）、`owner_id`（host:pid:rand）、`fencing_token BIGINT`（默认 1）、`heartbeat_at`、`lease_until`。生产在用键：`'batch'`（批 dispatcher，`batch_engine.py:817`）、`'delivery'`（outbox 投递器）、`'audit_retention'` 与各调度器 `'scheduler'`（app/扫描/编排/备份/ETL/字段索引/状态徽章）、`'oc-watchdog'`（看门狗）、`'scan_scheduler'`。**租约的互斥语义由 `ON CONFLICT … WHERE` 一条语句原子完成**，无应用层锁。

### 3.2 会话级执行权列（`ai_chat_sessions`，p1 迁移 `:18-23`；控制标志 `db_schema/ai_scan.py:45,71,76,80`）

`lease_owner`/`lease_until`/`heartbeat_at`/`fencing_token`（claim 时写入，子会话行即 claim 单元）；`retry_count`（auto-retry 与 gate_retry **共用**的重试预算计数）、`continue_prompt`（续跑提示词，非空即下一轮走 continue 模式）、`cancel_requested`/`pause_requested`（协作式停止）。

### 3.3 `ai_execution_checkpoints`（p1 迁移 `:63-84`）

`checkpoint_type ∈ dispatch/progress/turn_complete/recovery/manual`；`message_seq`/`opencode_session_id`/`completed_effect_ids`/`artifact_refs`/`context_snapshot JSONB`。两个关键索引：

- `uniq_checkpoint_latest ON (session_id) WHERE is_latest`（`:78-80`）——**部分唯一索引**保证每会话至多一份最新快照；写入是「旧行置 false + 新行」同事务（`execution_checkpoint.py:33-53`），无需应用层去重。
- `idx_checkpoint_session_created ON (session_id, created_at DESC)`（`:82`）。

### 3.4 `ai_execution_attempts` 运行唯一约束（p1 迁移 `:57-60`）

`uniq_attempt_running_per_session ON (session_id) WHERE status IN ('claimed','running')`——「同会话至多一个真正在跑的 attempt」不变量由数据库保证。建索引前先把会话已不在 running 的悬挂 attempt 收口为 `orphaned`（存量修复 `:40-51`）；`recovering`（重排前收口态）刻意**不**纳入谓词，否则会挡住合法续链（迁移注释 `:52-56`）。attempt 主表归分册 06。

### 3.5 `ai_delivery_outbox`（p1 迁移 `:154-177`）

`event_id + target_url` 唯一（幂等去重）、`status ∈ pending/sending/delivered/failed/dead_letter`、`attempt_count`、`next_retry_at`、`last_error`、`signature`（HMAC 密钥）、`payload JSONB`。表结构主描述在 03 册 §3.7。

### 3.6 预算与用量（p1 迁移 `:179`、`:197`）

`ai_execution_budgets`（scope_type/scope_id 唯一，`max_tokens/max_cost/max_wall_clock_ms/max_concurrency/on_exceed/enabled`）与 `ai_execution_usage`（每会话一行 upsert）。机制主描述在 03 册 §4.5。

### 3.7 观测面：`/metrics`（`routes/metrics.py`，37 行）

Prometheus 文本格式，全部指标从既有表聚合（`:12-33`）七个 gauge：`ai_batch_queue_depth`/`ai_batch_running`/`ai_batch_failed_last_hour`/`ai_orchestration_runs_active`/`ai_attempts_running`/`ai_outbox_pending`/`ai_batch_needs_review`；另暴露 `ai_worker_lease_heartbeat_seconds{kind=…}`（`:34-36`）——每把租约距上次心跳的秒数，压测采样器与运维同时消费。

## 4. 核心流程

### 4.1 故障场景与收敛路径总览

```
OpenCode serve 挂 ──→ 看门狗（阈值 2 次连续不可达）──→ restart_serve（只拉进程）
                                                          │ 遗留 running 行不重放
后端进程崩溃/重启 ──→ 实例租约（旧实例 TTL 90s 过期）──→ 新实例 dispatcher 接管
                                                          │ 每 60s 对账一轮
                                                          ▼
                                            _reconcile_stale_running 前置两闸+六分支对账（§4.3）
                                                          │
单回合派发失败 ──→ _recover_session 新建会话+历史重注入（§4.4）
回合停滞/卡死/瞬时错 ──→ _is_retryable → auto-retry（预算 2，§4.5）
门禁不过 ──→ gate_retry 定向修复（预算与 auto-retry 共用 retry_count）
回调失败 ──→ outbox 退避 1s/5s/30s/5m/30m ×8 → dead_letter → 人工 replay（§4.8）
资源超限 ──→ 预算 warn/drain/abort（03 册 §4.5）
副作用结局未知 ──→ needs_review，禁自动重放（人工复核）
```

### 4.2 看门狗：serve 进程级兜底（`oc_watchdog.py`）

背景（2026-09-28）：自动拉起只有 proxy 启动时的一次，serve 运行中挂掉后所有 AI 能力静默不可用直到人工发现。`tick()`（`:69-133`）单次探测的状态机：

1. `serve_health()` 探测（异常按不健康计）→ 健康则清零 `consecutiveFailures`、清 external 标记；
2. 不健康且未达阈值 → `wait`（返回等下一轮）；
3. 达阈值且端口曾被标记 external → `skip-external`——**永不代杀外部实例**，等它恢复或人工处理；
4. 达阈值且 `restart_busy()`（管理页手动重启持 `RESTART_LOCK` 中）→ `skip-busy`，避免双重拉起；
5. 否则 `restart_serve()`：成功记 pid/version；抛 `EXTERNAL_PROCESS` → 置 `externalProcess=True` 后停止尝试直到健康恢复；其余失败记 `restart-failed` 并继续下轮。

三条安全设计（`:12-15,18-19`）：多进程部署靠 `lease_kind='oc-watchdog'` 租约只留一个值班（`:146-158`）；与手动重启共锁互跳；**恢复动作只做"拉起进程"，不自动重放失败的批任务子任务**——重放与否属恢复决策表（§4.3）/人工职责，避免盲目重试有副作用的执行。所有依赖失败都吞异常记状态——看门狗自身故障绝不打断 Flask。单元测试 `tests/test_oc_watchdog.py`（7 用例：阈值触发/外部进程/共锁跳过/状态形状等）。

### 4.3 重启对账：前置两闸+六分支对账（`batch_engine.py:3264-3368`）

与 dispatcher 同线程运行（天然避开 claim→入账窗口的竞态），节流 `RECONCILE_INTERVAL_SEC=60`（env `AI_BATCH_RECONCILE_SEC`，`:929`，调度点 `:1043-1047`）。查询全部 `status='running'` 且有 `batch_id` 或 `api_key_id` 的会话（`:3284-3288`），逐行判定：

**前置两闸**：

- 本进程线程表正在跟踪（`sid ∈ _running_session_ids`）→ 跳过（轮询循环自己负责，`:3296-3297`）；
- `lease_until > NOW()` → 跳过——租约未过期，原 owner（可能是另一实例）仍可能在工作（`:3298-3307`）。**孤儿判定不再只看本进程线程表，先看租约**——这是 P1 相对 P0 的本质差异（docstring `:3267-3269`）。

**恢复决策分流**（顺序即优先级）：

| # | 条件 | 动作 | 证据 |
| --- | --- | --- | --- |
| 1 | 存在结局未知的副作用（`execution_effect.has_unknown_effects`） | `_mark_needs_review`——**禁自动重放**，人工复核后重试或重执行 | `:3309-3317` |
| 2 | 无 oc 会话（丢失发生在 `create_session` 之前） | 原样重排（`_requeue_lost(continue_on_same=False)`，全新执行） | `:3318-3323` |
| 3 | `get_messages` 返回 404 | 带准确原因失败（服务端可能重启/清理过该会话）；其余 HTTP 状态本轮跳过 | `:3324-3335` |
| 4 | OpenCode 整体不可达（`RequestException`） | 跳过本轮——**不批量误杀** | `:3336-3337` |
| 5 | oc 存活 + 无 checkpoint + 无消息 + 无副作用 | failed（retryable 收口）——无任何进度证据，failed 优于静默重放；checkpoint 判定基建异常时保守按"有"处理 | `:3338-3364` |
| 6 | 其余（oc 存活 + 有 checkpoint 或有进度证据） | 原地续跑（`_requeue_lost(continue_on_same=True)`，写入 `AUTO_RETRY_CONTINUE_PROMPT` 原会话续跑；docstring 称"generation 不变"，实现仍 generation+1——见 §7 决策 1） | `:3365-3366` |

每次接管写 `ai_batch_events('child.recovered')`，`payload.decision ∈ needs_review/requeue_fresh/opencode_404/failed_no_progress/requeue_continue`（`_emit_recovered :3370-3375`）。

**`_requeue_lost`**（`:3377-3423`）：`retry_count >= MAX_AUTO_RETRY` → 带因失败；否则单条 UPDATE 置回 `pending`（`retry_count+1`、generation+1、清 `active_turn_id`，continue_on_same 时写入 `AUTO_RETRY_CONTINUE_PROMPT`），并写一份 `recovery` checkpoint（重排换代前的最后快照，`:3404-3415`）、收口旧 attempt 为 `recovering`（reason=`RECONCILE_REQUEUE`）、重算批次状态、`notify()` 立即唤醒调度器。

**重启路径的衔接**（H8）：`_start_with_lease :865-875` 与 `_acquire_retry_loop :842-863`（`:856` 注释）只起 dispatcher 线程，不再无条件把 running 重置为 pending 重发原始 prompt（那会重做已产生的外部副作用）——遗留行一律交给本对账器。

DB 级测试覆盖：`tests/test_harness_p1_durable.py:132`（租约未过期跳过）、`:145`（unknown effect → needs_review）、`:166`（存活会话原地续跑）、`:198`（无进度证据失败）、`:298`（OpenCode 不可达跳过）。

### 4.4 派发失败会话恢复与上下文重注入（`batch_engine.py:1501-1517,2436-2458`）

`send_message` 对存量 oc 会话派发抛 `RequestException` 时（continue 模式尤其容易撞上——它盲目复用 `opencode_session_id`，工作区 .git 变动或 OpenCode 库清理都会让旧 id 失效）：

1. `_recover_session`（`:2436-2458`）：`create_session` 新建 → `_set_opencode_id` 回写绑定 → `render_history_block` 渲染历史摘要 → 摘要+原 prompt 一次发出。排除键与 generation 后缀 id 对齐（M2 回修，`:2451-2455`）——排除本轮提示词本身，否则当前问题既进摘要又追加一次。
2. `baseline_ids = None`（`:1516`）——全新会话没有旧消息需要跳过，`_await_finished` 不会误读旧终态。
3. 恢复本身失败就直接抛（不重试）——`_run_one` 的 except 接住落 failed，带**真实的恢复失败原因**；原始派发失败原因已在调用前 `logger.warning` 记下（`:2445-2447`）。只包 `send_message` 不包 `create_session`：后者失败意味着 OpenCode 整体不可达，重建会立刻复现同样错误。

交互式聊天侧的同一机制是 `routes/ai_chat.py:1066` `_recover_session_and_resend`，两侧**共用** `utils/session_history.py::render_history_block`（§2.1）。

### 4.5 回合级重试：分类、预算与定向修复（`batch_engine.py:3161-3214,1853-1897`）

**分类** `_is_retryable`（`:3161-3176`）：

- 可重试：停滞（`_SessionTimeout('stalled (no progress)')`，STALL 看门狗 180s）与工具卡死（`'tool stuck'`，TOOL_STALL 看门狗 900s）两个 watchdog 原因；`_TurnFailed.name ∈ RETRYABLE_TURN_FAILED = {APIError, UnknownError, MessageOutputLengthError, StructuredOutputError}`（`:762-763`，provider 瞬时错误白名单）；网络异常（`RequestException`）。
- 不可重试：硬超时上限（长任务被时钟杀掉，续跑只会更大）、`ProviderAuthError`（密钥错，重试必然再炸）、用户中断（`MessageAbortedError`）、上下文超限（`ContextOverflowError`），以及**白名单外的一切未知失败——保守不重试**。

**预算内重排** `_maybe_auto_retry`（`:3178-3214`）：`MAX_AUTO_RETRY`（env `AI_BATCH_MAX_AUTO_RETRY`，默认 2，`:758`）**从 DB 现读**（claim 行里的快照在本轮已过期）；预算内 → 状态回 pending、`retry_count+1`、generation+1、已开跑过的置 `AUTO_RETRY_CONTINUE_PROMPT`（`:765-768`，"从中断处继续完成原任务；已完成的部分不要重做"）原会话续跑，从未开跑的原样重排；旧 attempt 收口 `recovering`（reason=`AUTO_RETRY`）并串 `parent_attempt_id` 链；`notify()` 立即唤醒调度器。预算用尽返回 False，由调用方走 failed 路径。

**gate_retry 定向修复** `_maybe_gate_retry`（`:1853-1897`）：动作门禁核对不过时，带「缺失明细」修复提示（`agent_ledger.gate_failure_message`）在**原会话**上 continue 续跑——上下文保留，只补缺失动作不重做已完成部分。开关优先级：批级 `gate_retry` 列（`:1833-1840`）> 全局 env `AI_BATCH_GATE_RETRY`（默认 0=关闭）；批级显式开启时预算至少 1 次；**与 auto-retry 共用 `retry_count`**——两条重试通道合计不突破预算。

单测 `tests/test_batch_auto_retry.py`（8 用例）。

### 4.7 租约与 fencing：实例互斥与执行权（两层租约）

**实例级**（`ai_batch_worker_leases`）：批 dispatcher 抢 `'batch'` 键（`batch_engine.py:826-827`），抢不到不启动、每 5s 后台重试直到旧租约过期接管（快速重启的 TTL 窗口内不永久放弃 dispatcher）；持有期间 `_lease_loop` 每 20s 心跳，**连丢 3 次停整个 dispatcher**——宁可整实例让位，不与接管者双跑（`:877-895`）。outbox 投递器同构（`delivery_outbox.py:313-351`），且 `drain_due_once` 每行投递后回调续租——最坏 10×30s 的 drain 期间心跳不停顿，杜绝"租约过期被重试线程接管 → 同进程双投递器"（`:218-240`）。

**会话级**（`ai_chat_sessions` 租约列）：claim CTE 写入四列并令 `fencing_token+1`（`:1150-1157`）；`_await_finished` 轮询里每 20s 调 `_renew_child_lease`（owner+fencing 双条件 WHERE，`:3217-3233`），rowcount=0 即执行权已被接管 → abort 本地回合并抛 `_LeaseLost`（`:2545-2556`），`_run_one` 对它**直接放手不写回**——接管者可能正在复用该 OpenCode 会话，任何终态写回都会被 fencing 拒绝（`:1642-1650`）。对账器的孤儿判定同样先看这份租约（§4.3 前置闸）。

P0 语义边界：**不做跨实例抢占**（不因 lease 过期主动杀别人的工作，只保证同一套部署里多进程不双跑）；`fencing_token` 的单调递增语义（每次 acquire +1，含自续占）为 P1 接管时"+1 使旧执行体写回全失效"预留——`force_stop_batch` 已消费该语义（`batch_repo.py:1400-1466`，03 册 §4.2）。单测：`tests/test_worker_lease_retry.py`、`test_batch_execution_safety_p0.py:767-782`（单实例）、`test_harness_p1_durable.py:83-131`（claim 写租约/过期接管/心跳续租）。

### 4.8 outbox 重放与死信（`delivery_outbox.py` + `ai_batch_admin.py:448-465`）

投递线程（`OutboxDeliveryLoop`，5s 轮询）每轮 `drain_due_once`：

1. **领取** `_claim_due`（`:91-117`）：`pending/failed` 且 `next_retry_at <= NOW()`，或 `sending` 超 10 分钟（进程被 kill 的回收——claim 时把 `next_retry_at` 锚到 NOW()+10min，回收窗口从 claim 起算）；`FOR UPDATE SKIP LOCKED`。
2. **投递** `deliver_one`（`:183-215`）：复用 `webhook_engine._fire_single_webhook` 的 HMAC 与 HTTP，返回值**三分类**——`True`（2xx）/ `False`（有 HTTP 状态码的确定性失败）/ `'uncertain'`（超时/连接拒绝/DNS，无响应）。
3. **收口** `_settle`（`:120-176`）：成功 → `delivered`；失败 → 退避 `1s/5s/30s/5m/30m`（`BACKOFF_SECONDS :22`），`attempt_count >= 8`（`MAX_ATTEMPTS :23`）→ `dead_letter`；同时把 callback effect 收口为 `committed/failed/unknown`——**unknown（uncertain 结局）是恢复决策表第 1 分支的输入**，该会话此后被对账器判 needs_review、禁自动重放（§4.3）；投递结果写 `delivery.sent/failed` 事件（批次已删则跳过，防孤儿事件累积）。
4. **人工重放**：管理页 `POST /ai/chat/admin/batches/deliveries/<oid>/replay`（`:457-465`）→ `replay_dead_letter`（`failed/dead_letter → pending`、`attempt_count=0`、立即到期）；状态查询 `GET /<batch_id>/deliveries`（`:448-454`）。

退避序列与死信口径的机制主描述在 03 册 §4.7；本册补的是容灾语义：**回调永不丢**（与终态同事务入队）、**不确定结局升级为人工复核**而非盲目重投。单测：`test_harness_p1_durable.py:350`（入队幂等）、`:365`（投递与重放）、`:389`（死信与人工重放）、`:271`（sending 回收）。

### 4.9 预算兜底（衔接分册 03）

预算判定点（claim 前 + 子任务终态）与预算表结构**主描述在 03 册 §4.5**，本册只记超限动作的容灾语义（`execution_budget.py:160-176,217-235`）：

- `warn`：仅写 `budget.exceeded` 事件与日志——观测不干预；
- `drain`：dispatcher 在批次超限后跳过该批 pending 行（`batch_budget_blocks_claim :179-194`，内联进 claim CTE 的 NOT EXISTS），**运行中的自然收敛**——不杀已开跑的子任务；
- `abort`：对批次内全部 `pending/running` 置 `cancel_requested`（`:163-173`）——协作式收口而非强杀；
- scope（user/api_key）级超限**恒为 drain**：scope 级不 abort 他批正在跑的子任务，只停止接收新认领。

## 7. 设计决策

1. **分层兜底 + 明确的自动收敛边界**：能证明有进度证据的原地续跑（checkpoint/消息/副作用任一存在）、丢失发生在开跑前的原样重排、无任何进度证据的带因失败（retryable）、**副作用结局未知的一律 needs_review 禁自动重放**——四条边界把"自动恢复"限制在可证明安全的范围内，其余交人工（`batch_engine.py:3269-3277` docstring 与实现一致）。与旧文档《AI批任务容灾与恢复机制》的"三层防线"叙事一致，但 P1 后的判定依据从"本进程线程表"升级为"租约 → 副作用 → oc 会话 → checkpoint"四路证据。一处 docstring 与实现的冲突如实记：`_reconcile_stale_running` docstring（`:3273-3274`）称 continue 分支"generation 不变"，而共用的 `_requeue_lost`（`:3398`）实现是 `execution_generation = execution_generation + 1`——以实现为准（换代与 auto-retry/重排路径口径一致，旧 attempt 链由 `parent_attempt_id` 串接）。
2. **看门狗只拉进程、不重放任务**（`oc_watchdog.py:17-19`）：进程拉起与任务重放是两个正交决策——盲目重试有副作用的执行属于恢复决策表/人工职责；serve 恢复后遗留 running 行由对账器按 §4.3 分流。
3. **端口所有权保护**：`EXTERNAL_PROCESS`（端口被非平台所有进程占用）时看门狗标记 external 后永不代杀（`:101-103,118-124`），与 01 册"外部进程永不按端口杀"决策同源。
4. **压测与 dev 零共享**（spec §2，conftest 落地）：专属 DB `casemanage_stress`、端口 3092/4097、独立 serve `GLOBAL_DIR`——kill/重启只伤压测自己的实例。**为什么必须专属 DB**：批 worker 租约按 DB 键互斥，若与 dev 共库，dev 后端的 worker 会抢走压测批次用真模型执行（spec 前置事实，已核实）；DROP DB 由 finalizer 保底，结构性杜绝压测残库。
5. **容量层 StubRuntime 不出网、零 token**（spec §3）：内存态模拟 agent 生命周期，压测成本与模型/网络解耦；唯一风险是消息形状漂移导致 worker 判据失真——以 `test_runtime_stub.py` 与真实 `get_messages` 返回的逐字段对照测试锁住。
6. **混沌层小规模验证进程语义**（spec §4.2）：真 serve + 真运行时只用于 C1/C4 类**进程级**故障注入（kill/重启的所有权与接管语义无法在内存 stub 里模拟），≤3 并发、分钟级成本；不追求真模型的容量结论——容量归 stub 层，进程语义归混沌层，两类问题分开回答。
7. **租约绝不打断调用方**（`execution_lease.py:12-13`）：表缺失/连接失败返回失败态并记日志，最坏退化为 P0 之前的多进程行为，而不是服务起不来；同理 checkpoint/outbox 入队/事件流全部 best-effort——兜底设施自身故障不得放大为业务故障。
8. **重试双通道共用一个预算**：auto-retry（机械性失败）与 gate_retry（门禁定向修复）共用 `retry_count`，`MAX_AUTO_RETRY` 从 DB 现读而非用 claim 快照——防止快照过期导致预算失控（`batch_engine.py:3183-3185`）。
9. **与 spec/现状的差异（如实记）**：spec 前置事实称 `AI_AGENT_RUNTIME`"当前仅 opencode_local"——stub 分支现已落地（`runtime/__init__.py:24-26`），该表述随 stub 交付过时；spec §5"跑完自动汇总 md 报告"未落地（仅 Sampler JSON 落盘，§4.10）；conftest 不变量把 spec 的 `total = done+failed+cancelled` 修正为 `total = done+failed`（`ai_chat_batches` 无 cancelled 列，`conftest.py:250-253` 注释）——以代码为准。
10. **历史文档关系**：`docs/design/archive/AI批任务容灾与恢复机制.md` 等旧文档的 claim/恢复描述与现状冲突处（如 P0 时代"无条件重放 running 行"已被 H8 移除），以代码与本册为准。
