## 1. 模块职责

长期记忆按 mem0（Chroma 向量库 + OpenAI 兼容 LLM/Embedder）实现**按用户隔离**的跨会话记忆：用户偏好、习惯与关键事实在对话/批任务中被动提炼沉淀，也可手动原样补写；每次发消息时检索 Top-5 注入 prompt 前缀。两条铁律：

1. **Flask 是 mem0/Chroma 的唯一持有者（单写者）**——MCP Server 是独立进程，让它直开 Chroma 就是双写，所以 MCP 的三个 memory 工具全部经内部端点转回 Flask（`memory.py:1-6`、`ai_memory_internal.py:1-6`）。
2. **记忆层全程降级 no-op，绝不阻断聊天**——未配置、初始化失败、读写抛错一律返回 `None`/`[]`/False 并记日志；唯一的例外是进程级 SIGSEGV（见 §7 决策 2），靠线程钉亲和**预防**而非捕获（`memory.py:1-6,23-45`）。

按职责分四块：

| 职责 | 说明 | 证据 |
| --- | --- | --- |
| mem0 持有与封装 | 单例构建（api/ollama 双 embedder 分支）、单线程 executor 钉原生线程亲和、add/search/get_all/delete 全降级 | `server/utils/memory.py`（253 行） |
| 用户面 HTTP | `GET/POST/DELETE /ai/memories`：列出、手动补写（verbatim 双模式）、删除（归属校验） | `server/routes/ai.py:145-181` |
| 内部通道 | `/ai/memory/internal/search|add|delete`：MCP 三工具的唯一通道（X-Internal-Token） | `server/routes/ai_memory_internal.py`（71 行） |

## 3. 数据模型

**本册无专属表**：记忆存 mem0/Chroma 文件存储，不在 Postgres。

- **存储位置**：`MEM0_STORE_ROOT`（env，默认 `~/.check-manage/mem0`，`memory.py:16-17`）；Chroma `collection_name='memories'` **固定一个集合**（`_build_config` `:81`），**按 `user_id` 分区**——写入传 `user_id=`、检索/列举传 `filters={'user_id': …}`，由 mem0 在集合内做用户作用域（`:134-135,167,178`）。
- **记忆条目元数据**：`metadata.source ∈ {manual, conversation, batch, …}`（`add_memory` `:127-143`）——前端来源筛选（`MemoryManager.vue:22-27`）与审计都吃这个标记。旧版 mem0 不支持 metadata 时退化为不带来源写入（`:136-139`）。
- **配置列**（`ai_settings`，归分册 10，本册只列本册消费的）：`mem0_enabled`/`embedding_model`/`default_chat_model`（`db_schema/core.py:172-174`）、`embedding_provider`/`embedding_ollama_url`/`embedding_dims`（迁移 `2026_09_29_embedding_provider.py:23-25`）。设置变更后 `reset_memory_singleton()` 丢缓存实例（`ai.py:134` → `memory.py:113-118`）。

## 4. 核心流程

### 4.1 初始化与线程亲和（`memory.py`）

1. **单例 `get_memory`**（`:89-110`）：`mem0Enabled` 且有 `apiKey` 才尝试；**只尝试一次**（`_init_attempted` 不复位，失败后恒 None 直到配置变更 reset）；构建在 mem0 专用线程上执行（`Memory.from_config` 也走 `_on_mem_thread`，`:106`）。
2. **配置组装 `_build_config`**（`:60-86`）：`llm` 恒走原 API 端点（`_base_url` 剥掉 `/chat/completions` 后缀，temperature 0.1）；`embedder` 按提供方分支——`api`=同端点 OpenAI 兼容（默认 `text-embedding-v3`，dims 1024），`ollama`=本地 Ollama（默认 `nomic-embed-text`、`http://localhost:11434`，dims 可配，`:65-78`）；`vector_store`=Chroma，`path=MEM0_STORE_ROOT`。
3. **单线程 executor 钉亲和**（`:23-53`）：`ThreadPoolExecutor(max_workers=1)` 是唯一的「mem0 线程」，`_on_mem_thread(fn)` 把初始化与**每一次** add/search/get_all/delete 提交到该线程并阻塞等结果（调用方保持同步语义）。原因见 §7 决策 2：chromadb 的 onnxruntime 原生状态线程仿射，跨线程触碰是非法原生内存访问 → SIGSEGV，进程级崩溃**无法**被 try/except 兜住——本应用是多线程的（waitress 请求 worker、APScheduler 备份/依赖/扫描线程、mem0 自身提炼线程），不加钉则「第一次调用成功、第二次换个线程就段错误」（实测症状，`:34`）。

### 4.2 注入：发消息时检索 Top-5

- **交互聊天**（`ai_chat.py:876-879`）：`POST` 发送消息时以用户原文为 query `search_memory(user_id, content, limit=5)` → `render_memory_block` 渲染为块，拼在 `_AGENT_DIRECTIVE` 之后、用户内容之前。
- **批/扫描子会话**（`batch_engine.py:1358-1363`）：`_run_one` 组装 prompt 时同样注入（`_BATCH_DIRECTIVE + mem_block + prompt`）；检索 query 用**用户原文**（`user_prompt_for_memory` 先取值再拼接）——无人值守指令是每条子任务相同的样板，混进检索与记忆都是噪音（`:1360-1362` 注释）。
- **块措辞**（`memory.py:184-190`）：`[关于当前用户的长期记忆（供参考，不必逐条复述）]` + 条目列表——定位是参考不是指令。

### 4.3 被动提炼：每轮对话沉淀（仅真人会话）

- **交互路径**（`chat_persist.py:690-694`）：回合收敛 `idle` 且 `persist_turn` 之后调 `extract_from_turn(sid, state)`，后台线程执行、绝不抛出。
- **`extract_from_turn`**（`memory.py:220-252`）：查会话行，**仅限真人交互会话**——`user_id` 为空或 `batch_id`/`scan_task_id` 任一非空直接返回（`:232`）；取本轮 `[最近一条 user 消息, assistant 纯文本]` 组成 messages，`add_memory` 落库（默认后台线程，`_sync=True` 供测试同步）。
- **批/扫描路径**（`batch_engine.py:1988-2004`）：`_record_memory` 走**独立直调**（不经内部端点）——`extract_from_turn` 会跳过 batch/scan 子会话，批侧在子会话成功终态后直调 `add_memory(user_id, [user, assistant])`（调用点 `:1630-1631`），与交互路径对齐；线程化 best-effort。

### 4.4 主动补写与删除：`/ai/memories`（用户面）

| 端点 | 行为 | 证据 |
| --- | --- | --- |
| GET `/ai/memories` | 列当前用户全部记忆 | `ai.py:145-149` |
| POST `/ai/memories` | 手动补写：`text` 必填、≤2000 字符；`verbatim=true` → `add_memory_text(infer=False)` **原样保存**（不提炼、仍嵌入向量化），缺省 → mem0 LLM 提炼成简洁事实；**mem0 未配置返回 409** `MEMORY_UNAVAILABLE`（与 500 写入失败分开） | `ai.py:152-168`；`memory.py:146-159` |
| DELETE `/ai/memories/<id>` | 归属校验先于删除：目标 id 必须在本人 `list_memories` 结果内，否则 404（不能拿别人的 memoryId 试探删除）；写 `log_operation` | `ai.py:171-181` |

### 4.5 MCP 三工具 → 内部端点（跨进程单写者）

```
Claude/OpenCode 会话 → MCP memory_search/add/delete（scope=ctx.user_id）
  → memory_client（urllib，X-Internal-Token，loopback 加固）
  → POST /ai/memory/internal/search|add|delete → Flask 内调 utils.memory
```

- **工具面**（`tools/memory.py:8-23`）：`memory_search(query, limit?)`、`memory_add(text)`、`memory_delete(memoryId)`；三个 handler 都先拒**公共客服会话**（`is_public_kefu` → PermissionError，`:27-28,36-37,43-44`）——匿名客服链路不得读写真实用户记忆。检索空结果返回「（无相关记忆）」提示而非空串（`:31-32`）。
- **客户端**（`memory_client.py`）：`FLASK_INTERNAL_URL` 默认 `http://127.0.0.1:3002`，**非 loopback 需显式 `MCP_ALLOW_REMOTE_INTERNAL=1`**（SSRF 加固，导入时校验 `:13-26`）；超时 10s，HTTPError/URLError 转 RuntimeError 带端点与状态码（`:29-41`）。
- **端点面**（`ai_memory_internal.py`）：`_authorized` 要求 `MCP_INTERNAL_TOKEN` 非空且请求头匹配，否则 403（token 为空 = 端点整体关闭，`:14-16`；信任边界口径见 01 册 §5.1）。search 的 `limit` 容错（非法/`<1` 回落 5，`:27-32`）；**add 缺省 `source='batch'`**（`:43`，来源语义详述见 §7 决策 4）；delete 直删 `memoryId`（工具面已限定 scope 内检索所得 id）。
- 同蓝图还有 `/runtime-events`（OpenCode 插件上报，归分册 08/01，与本通道同一信任边界，`:56-71`）。

### 4.6 备份与还原：`MEM0_STORE_ROOT` 归 `vector_store/`

`utils/backup.py` 从 env 直接读同一 `MEM0_STORE_ROOT`（避免 import memory 的副作用，`:28-31`）：打包进 ZIP 的 `vector_store/` 前缀（`:32,71`），还原时**全量覆盖**（先清空再解出——外部文件无 upsert 语义，须与备份时刻的 DB 引用配套，`:40-59,75`）；备份元数据 `hasVectorStore` 标记是否含记忆库（`:783`）。AI 会话工作区是 TTL 临时数据，**故意不备份**（`:28-30` 注释）。

## 7. 设计决策

1. **Flask 单写者**。Chroma 是单写者存储，mem0 实例只在 Flask 进程存在；MCP 进程一律走内部端点（与数据写同构）。这换来一个唯一的写序列化点（mem0 专用线程），也为未来换向量库留了单点收口。
2. **单线程 executor 钉原生线程亲和**。chromadb 的嵌入走 onnxruntime 原生 C++ 运行时，其句柄/session/BLAS 上下文绑定创建线程——跨线程访问是非法原生内存访问（SIGSEGV），**进程级崩溃无法被 try/except 捕获**。本应用天然多线程（请求 worker、APScheduler、mem0 自身提炼线程），不加约束的症状就是「第一次调用成功、第二次换线程段错误」。方案不是加锁而是**永不跨线程**：`max_workers=1` 的常驻线程承载 init 与全部读写，`_on_mem_thread` 阻塞转发保持同步语义（`memory.py:23-53`）。
3. **记忆层全程降级 no-op 不阻断聊天**。未启用/初始化失败 → 单例 None；读失败 → `[]`；写失败 → False/日志。聊天与批任务在任何记忆层故障下照常工作；唯一的进程级风险（决策 2）靠钉亲和预防。初始化**只尝试一次**，避免每次请求都撞同一个故障（配置变更经 reset 重建）。
4. **source 语义按实际代码**：`add_memory` 缺省 `'conversation'`（`memory.py:127`）——交互提炼与批侧直调 `_record_memory` 都落到这个缺省；内部端点 `/add` 缺省 `'batch'`（`ai_memory_internal.py:43`）——而其当前唯一调用方 `memory_client.add` 并不传 source（`memory_client.py:48-49`），故经 MCP 工具 `memory_add` 写入的记忆实际打 `batch` 标记。**注**：01 册 §5.1 端点表写「add 支持 source（batch/默认对话提取）」，与代码不符（`ai_memory_internal.py:41` 的行内注释「默认对话提取」同样与 `:43` 的代码矛盾）——以本册为准，01 册该行待勘误。
5. **verbatim 双模式**。手动补写默认让 mem0 LLM 提炼（去口语化、合并去重）；`verbatim=true` 时 `infer=False` 原样保存仍向量化——适合「一句话关键事实」，用户在界面上显式选择（`MemoryManager.vue:12-13`）。POST 端点把「未配置」(409) 与「写入失败」(500) 分开返回，前端能给出准确提示。
6. **归属边界三道**：用户面 DELETE 只能删本人记忆（owned 集合校验先于删除，404 不泄露存在性）；MCP 工具 scope 恒为 `ctx.user_id`；公共客服会话三工具全禁。记忆按 user_id 在固定 collection 内分区，不建每用户一集合。
7. **注入是参考不是指令**：记忆块带「供参考，不必逐条复述」措辞，且拼在 directive 之后、用户原文之前；批侧检索/提炼都围绕用户原文，无人值守样板指令不进记忆。
8. **备份口径**：`MEM0_STORE_ROOT` 归档为 ZIP `vector_store/` 前缀、还原全量覆盖——向量库与 DB 引用必须成套回滚，不做部分还原。
