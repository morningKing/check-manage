## 1. 模块职责

本册覆盖两块相邻能力：

**AI 编排（orchestration）**——把多步 AI 工作流声明为版本化 DAG（agent/approval/join 三种节点），按定义版本创建 run，引擎将 run 展开为 step 并推进 DAG；**agent step 的执行体不是独立调度器，而是 `ai_chat_sessions` 子会话**（`orchestration_run_id`/`orchestration_step_id` 关联，迁移 `2026_09_23_harness_p2_orchestration.py:171-175`），由批 worker 的既有认领通道驱动——P0 的 ownership/CAS/generation 与 P1 的 lease/checkpoint 全部安全语义原样复用（`orchestration_engine.py:5-8`）。join/approval 是结构性节点，由编排自己的 scheduler 推进，不占执行槽（`orchestration_engine.py:9`）。

**子代理（subagent）**——OpenCode `task` 工具委派产生的子会话执行轨迹（`ai_chat_subtasks`/`ai_chat_subtask_messages`，id 就是 OpenCode 子会话 sessionID）与会话复用钉住（`ai_subagent_pins`，`(root_session_id, agent)` 唯一 → task_id）：复用名单内的 agent 多次委派强制续跑同一子会话，不依赖模型自觉。

编排与子代理的交汇点：编排 agent step 的子会话在执行中再委派 task 工具时，其子代理轨迹照常落在 `ai_chat_subtasks`（根会话即 step 的子会话）；但**会话复用是批级能力**——`enabled` 判定要求父会话 `batch_id` 非空（`ai_subagent_internal.py:98-100`），编排子会话 `batch_id=NULL`，不在复用范围内。

## 3. 数据模型

### 3.1 编排三表（`2026_09_23_harness_p2_orchestration.py`）

- **`ai_orchestration_definitions`**（`:19-38`）—— 主键 **`(id, version)`**（发布后不可变：同 id 递增 version 插新行，旧行保留可取）；`nodes`/`edges` 与五个策略列（retry/timeout/budget/approval/compensation）全部 JSONB；`published_at`。校验在应用层（§4.1），库层无 CHECK。
- **`ai_orchestration_runs`**（`:40-61`）—— `status`：pending/running/waiting_approval/paused/recovering/partial/completed/failed/cancelled/needs_review（`:44-46` 注释）；`execution_mode`：auto/single_step（P3 单步调试，DDL 内幂等追加 `:129-131`）；`run_input_snapshot`（创建即冻结的输入快照）；`runtime_manifest_id` → `ai_runtime_manifests`（`:151-166`，run 创建时冻结的运行时能力快照）；`requested_by` + `requested_by_kind`（user/api_key）。索引 `(status, created_at DESC)`。
- **`ai_orchestration_steps`**（`:65-86`）—— 主键 `id = '{run_id}:{node_id}'`（engine 展开时拼装，`orchestration_engine.py:81`）；`kind`：agent/approval/join；`status`：blocked/runnable/running/waiting_approval/succeeded/failed/skipped/needs_review；`depends_on` JSONB（入边 source 集合，create_run 时由 edges 推导 `orchestration_engine.py:74-76`）；`node_def` JSONB（发布时冻结的节点定义原文——run 不回读定义 nodes，推进/渲染/超时/join 策略都读这份快照）；`session_id` → `ai_chat_sessions.id`；`attempt_count`；`output` JSONB。

### 3.2 审批与产物

- **`ai_approval_requests`**（`:90-113`）—— `run_id`/`step_id`/`risk_level`/`effect_summary`/`requested_roles`/`requested_users`/`decision_hash`（SHA-256 可审计不可篡改，`approval_repo.py:63-68`）/`expires_at`。部分唯一索引 `uniq_approval_pending_step (step_id) WHERE status='pending'`（`:109-110`）保证每 step 至多一个 pending——结构审批与策略拦截都靠它天然幂等。
- **`artifacts`**（`:114-127`）—— 内容寻址（`sha256` + `storage_key`），owner 隔离去重索引由 `2026_09_25_artifact_owner_scope.py` 统一创建（迁移注释 `:128-130`，此前全局 sha 唯一索引会与 owner 隔离冲突）。
- **`artifact_refs`**（`:135-145`）—— 产物 ↔ run/step/attempt/session/batch 的引用，`relation`: input/output/checkpoint/report；索引 `(run_id, step_id)`。

### 3.3 子代理族

- **`ai_chat_subtasks`**（`db_schema/core.py:459-476`）—— **id 就是 OpenCode 子会话 sessionID**（不发明并行合成 id：子代理总是先在 OC 侧存在、平台才从 SubtaskPart 发现它）；`root_session_id`（不管嵌套多深都指顶层会话）+ `parent_subtask_id`（直接父）双列；`status` CHECK (running/completed/failed)；`turn_segments` JSONB（复用子会话的任务段，`2026_09_24_subagent_session_reuse.py:37-40`）。
- **`ai_chat_subtask_messages`**（`core.py:478-488`）—— `seq BIGSERIAL` 定序（同事务 created_at 可能相同，`subtask_repo.py:24-26`）。
- **`ai_subagent_pins`**（`2026_09_24_subagent_session_reuse.py:23-33`）—— `(root_session_id, agent)` 唯一索引 `uniq_subagent_pin` → `task_id`（OpenCode 子会话 id）；`batch_id` 级联删除。
- **`ai_chat_batches.subagent_reuse`** JSONB（同迁移 `:18-19`）—— 批级复用名单（agent 名数组；空/NULL = 不启用）。
- **`ai_chat_sessions` 编排关联列**（`2026_09_23_harness_p2_orchestration.py:168-175`）—— `orchestration_run_id`（FK ON DELETE SET NULL）+ `orchestration_step_id`，索引 `idx_ai_chat_sessions_orch`。

### 3.4 状态派生关系

```
ai_orchestration_definitions (id, version)   ←发布不可变
        │ create_run 冻结 version + node_def 快照
ai_orchestration_runs (status 由 step 事实派生)
        │ 展开节点
ai_orchestration_steps (status 由子会话事实派生) ── session_id ──> ai_chat_sessions（执行体）
                                                                      │ task 委派
                                                      ai_chat_subtasks / ai_subagent_pins
```

run 状态**永远派生自 step**、step 状态**永远派生自子会话**；模型自声明的 Todo 计划只进 `step.output.declaredPlan` 观测字段，不参与 DAG 推进（`orchestration_engine.py:829-848`，沿用 todo_trace 的 declared_plan 边界）。常量：`RUN_ACTIVE = ('pending','running','waiting_approval','recovering')`、`STEP_TERMINAL = ('succeeded','failed','skipped','needs_review')`（`:22-23`）。

## 4. 核心流程

### 4.1 定义发布：校验 → 规范化 → 不可变版本

`POST /ai/orchestrations/definitions`（`ai_orchestrations.py:32-55`，`admin.ai_orchestration_admin`）→ `orchestration_defs.publish_definition`（`:144-183`）：

1. **`validate_definition(nodes, edges)`**（`:13-120`）逐条把关，非法抛 ValueError → 路由 400：
   - **节点**：`nodes` 非空数组（`:15-16`）；id 必填 ≤100 字且不重复（`:24-29`）；`kind` 只支持 `('agent','approval','join')`（`:8,30-32`）；规范化节点字典保留 prompt_template/agent/model/output_contract/retry/approval/approval_policy/priority 及扩展字段 skills/input_refs/runtime/budget/timeout_sec/join_policy/condition/action_checks（`:33-57`，扩展字段此前被白名单丢弃致 run 侧读不到，P2-A3 补齐 `:44-46`）；`timeout_sec` 必须正整数（`:58-63`）；`join_policy` 枚举 `all_success/any_success`（`:64-68`）；**agent 节点必须有 prompt_template**（`:69-70`）；声明了 `action_checks` 就在发布时过 `agent_ledger.validate_checks` 校验格式，不静默带病入库（`:71-79`）；**approval 节点必须声明 requested_roles 或 requested_users**（`:80-84`）。
   - **边**：source/target 必须引用已存在节点（**悬空边在此拦截**，`:92-97`）；不允许自环（`:98-99`）；`kind` 只支持 `('advance','join','compensation')`（`:9,100-102`）。
   - **join 语义**：join 节点必须有多条入边，且至少含一条 join/advance 入边（`:108-117`）。
   - **环检测**：`_assert_acyclic`（`:123-141`）DFS 三色标记（0=visiting/1=done），命中回边抛「DAG 存在环：经过 {u}」。
2. **版本发布**（`:160-181`）：同 id 取 `MAX(version)+1` 插入新行（调用方传 `def_id` 则每次发布都是该 id 的新版本，不查重）；`id` 缺省生成 `orch_` + 12 hex。**没有 UPDATE 路径——发布即新版本，旧行不可变**。
3. 读取：`get_definition` 缺省 `ORDER BY version DESC LIMIT 1`（`:191-196`）；`list_definitions` 用 `DISTINCT ON (id) … ORDER BY id, version DESC` 每定义只回最新版（`:217-219`）。

前端等价预检：`OrchDagEditor.vue` 的 `hasCycle`（`:178-195`，同为 DFS 三色 + 自环检查）与空画布拦截（`:200-203`），保存的 JSON 结构对齐 `validate_definition`（`OrchDagEditor.vue:197-231`）；**后端复检是权威**，前端预检只省一次 400。

### 4.2 run 创建：冻结版本 + 输入快照 + runtime manifest

`POST /runs`（JWT，任意登录用户 `ai_orchestrations.py:58-77`；对外 `POST /v1/ai-orchestrations/runs` 以密钥 owner 身份、`requested_by_kind='api_key'`，`open_api_orchestrations.py:71-94`）→ `orchestration_engine.create_run`（`:30-91`）：

1. `get_definition(def_id)` 取**最新已发布版本**（不允许指定旧版本创建）；run id `run_` + 14 hex。
2. **runtime manifest 冻结**（`:42-61`）：当前 runtime（OpenCodeLocal）的能力快照写 `ai_runtime_manifests`，供恢复/审计解释「当时用什么环境跑的」；失败置 NULL 不阻断创建（观测性数据）。
3. 单事务插 run 行（status='pending'、`run_input_snapshot`、`requested_by/kind`、manifest id）+ **把每个节点展开为 step 行**（id=`run_id:node_id`、status='blocked'、`depends_on`=入边 source 排序去重、`node_def`=节点定义原文快照）（`:62-85`）。
4. 追加 `run.created` 事件（`:86-90`）；JWT 路由侧创建后立即 `_advance_run` 推进一次（`ai_orchestrations.py:71-76`，失败静默——scheduler 5s 内兜底）；对外路由改为 `get_worker().notify()` 唤醒批 worker（`open_api_orchestrations.py:87-91`）。

### 4.3 scheduler 推进与 step→子会话认领复用链（本册核心机制）

**调度器**：`OrchestrationScheduler`（`orchestration_engine.py:896-1029`）随 Flask 启动（`app.py:576-577` → `start_scheduler`）。持 **`execution_lease` 的 `lease_kind='scheduler'` 租约**（`:913-915`）保证多进程单实例；抢占失败进后台重试线程每 5s 再试（`:907,930-945`，同批 worker 的 N2 模式）；心跳丢失即退出循环让位（`:956-959`）。`tick()`（`:963-978`）：先 `approval_repo.expire_overdue()`，再对全部 status IN (pending/running/waiting_approval) 的 run 逐个 `_advance_run`；轮询间隔 env `AI_ORCH_POLL_SEC` 默认 5s（`:897`）。tick 还做 workspace TTL 清理（`:980-1018`）——但该查询 JOIN `ai_chat_batches`，只覆盖批子会话，编排子会话（batch_id NULL）不在此回收。

**`_advance_run` 的一步**（`:217-449`；并发安全不依赖全局锁——advisory lock 方案因客户端崩溃会以 idle-in-transaction 毒化后续推进被否弃，改为「每处 step 转移都带状态谓词 CAS，重复推进时输者 0 行生效」，H4，`:210-213`）：

1. **超时兜底**（P2-A5，`:266-312`）：对每个 running step 按 `node_def.timeout_sec` → 定义 `timeout_policy.default_sec` → 900s 取阈值，在**同一条 UPDATE 内完成判定与转移**（`WHERE status='running' AND started_at + interval < NOW()`，并发推进输者 0 行）；转移后 best-effort abort 子会话的 OC 回合（`_abort_timeout_child :452-479`，失败只记日志，对账器兜底语义不变）并落 `step.timeout` 事件。只看 running：waiting_approval 归审批自身超时（`expire_overdue`）管。
2. **可达性**（`:231-263`）：从无入边根出发沿「生效边」走，不可达 step → skipped。生效边语义：某节点出边里有条件边且源已 succeeded → 只取命中的（全不命中回落默认边）；**源未收敛（无 output）时不做条件取舍、全部出边目标视为候选**——否则条件目标会在本轮被不可逆 skip（H5 残留修复，`:247-249`）。依赖 failed/needs_review/skipped 向下游传播 skip（H6：否则菱形 DAG 一侧 skipped 会让 join 永久 blocked）；`join_policy='any_success'` 的 join 在仍有非终态依赖时豁免（`:327-338`）。
3. **runnable 推进**（`:346-413`）：按 `node_def.priority` 降序，每轮 agent 派发上限 `AI_ORCH_MAX_LAUNCH_PER_TICK` 默认 8（背压，`:350`）。依赖判定：普通 step 全部依赖 succeeded；join 按 `join_policy`（`all_success` 全成功 / `any_success` 任一成功）。join → 直接 CAS 置 succeeded；approval → `_open_approval`；agent → 策略拦截检查后 `_launch_agent_step`。
4. **run 状态派生**（`:415-449`）：waiting_approval > running（含仍有 blocked）> 全终态后 completed（全 succeeded）/ partial（有成功有失败）/ needs_review / failed；`started_at` COALESCE 首推进时间，终态置 `finished_at`。状态有变落 `run.status` 事件。

**agent step 派发 `_launch_agent_step`**（`:489-580`）——分叉两条路径：

- **首派**：**CAS 抢派发权**——`UPDATE ai_orchestration_steps SET status='running', session_id=%s, attempt_count=1, started_at=NOW() WHERE id=%s AND status='blocked' RETURNING id`（`:528-534`）；只有赢得 CAS 的线程才创建子会话（输者直接返回，杜绝审查实测过的「并发推进创建 6 个子会话」缺陷）。同事务 INSERT `ai_chat_sessions`（status='pending'、`continue_prompt`=渲染后的 prompt、user=run 的 requested_by、agent/model 取 node_def、`orchestration_run_id`/`orchestration_step_id` 关联列）（`:536-546`）。prompt 渲染是最小模板引擎 `_render_prompt`（`:187-204`）：`{{input.x}}`/`{{input}}`/`{{steps.<node_id>}}`（取上一步 `output.text`）。
- **重试（换代重跑）**：step 已有 `attempt_count`+`session_id` 时复用原子会话——`UPDATE ai_chat_sessions SET status='pending', continue_prompt=retry_prompt, error_message=NULL, execution_generation=execution_generation+1`，同时 step CAS（running 谓词）`attempt_count+1`、`started_at=NOW()`（重置超时时钟，否则继承首跑 started_at 会被超时兜底立即误杀，P2-A5，`:498-518`）。prompt 取 `node_def.retry_prompt` 或缺省修复提示。首派 CAS 刻意不收容 failed 形态——failed 且有 session_id 的重试走本分支，其余 failed 形态不复位 attempt_count、不弃用原会话（`:523-527`）。
- **action_checks 期望同事务登记**（P3 门禁支持编排，`:547-573`）：节点声明了 `action_checks` 就在同一事务内 `SAVEPOINT` 包裹调 `agent_ledger.register_session_expectations(source='orchestration')`——保证 worker 认领（commit 触发 notify）时期望已可见，不存在「有会话无期望」的 fail-open 窗口；登记失败 ROLLBACK TO SAVEPOINT 不阻断派发。终态核对由批 worker 既有门禁承担：`_run_one` 对 `batch_id=NULL` 的编排子会话不登记批级期望（`gate_reg` 恒 applicable=0，`batch_engine.py:1299-1301`）、也不清除编排侧期望，`gate_participates` 按 evaluated/expected 判定（`batch_engine.py:700-709`）。

**step→子会话复用链（编排如何借用批引擎的全部安全语义）**——编排自己不执行任何回合，执行事实完全来自批 worker 对子会话的认领：

| 复用点 | 批引擎机制（归分册 03） | 编排接入点 |
| --- | --- | --- |
| 认领通道 | `_claim_pending_sessions` 单条 CTE：`FOR UPDATE SKIP LOCKED` + 同 UPDATE 写 running/lease_owner/lease_until/heartbeat_at/**fencing_token+1**（`batch_engine.py:1116-1201`） | 候选 WHERE 显式含 `orchestration_run_id IS NOT NULL`（`:1134`）——编排子会话与批/api_key 子会话走同一 claim |
| ownership（P0） | claim 即开 turn：先关残留 active turn（SUPERSEDED）再插本轮 turn 绑 `active_turn_id`，部分唯一索引保证一会话一 active turn（`:1163-1189`） | 原样生效（编排子会话同样开 turn） |
| generation（P0） | claim 行快照的 `execution_generation` 是本轮全部写回的通行证，换代后旧写回 0 行（`:1294-1296`） | 重试换代正是 `_launch_agent_step` 复用分支的 `generation+1`（`:510-511`）；旧 worker 的迟到写回/进度快照全部被拒 |
| CAS + fencing | 终态写回唯一入口 `transition_child`：WHERE 带 running 态 + generation + fencing_token（`batch_repo.py:85-178`） | 编排子会话终态照常走它；fencing 使被接管/换代方的写回失效 |

**终态回调 `on_child_terminal`**（`orchestration_engine.py:688-882`）——批 worker 在编排子会话到终态后于 finally 块调用（`batch_engine.py:1679-1690`，best-effort）：

1. 读子会话事实；**非终态（running/pending/paused）一律返回**——worker 的自动重试会把子会话改回 pending 后 return（自愈流程），此刻若把 pending 判成 failed 会杀死本可自愈的 step/下游/run；paused 同理（`:700-706`）。
2. **output_contract 合同校验**（子会话 completed 时）：`type='file'` 检查 workspace outputs 文件名 fnmatch（`:716-723`）；`json_schema` 取最后一条 assistant 消息 text 解析 JSON 并 jsonschema 校验（缺库退化为「合法 JSON 即通过」，`:724-757`）；`db_record` 复用动作账本的 db-record 证据通道计数 ≥ min_count（`:758-772`，与动作门禁同一事实源）。不达标 → step failed。
3. **终态翻译**：completed+合同过 → succeeded；completed 但合同不过 → failed(合同错误)；needs_review → needs_review；**failed/cancelled → 预算内重试**（`node_def.retry.max`，attempts ≤ max 且 failed 时 step 置回 running、走 `_launch_agent_step` 重试分支、落 `step.retry` 事件并 `_advance_run`；预算尽 → failed）（`:774-806`）。
4. **step.output 提取**（H5：此前全仓无写入点、条件分支恒不命中）：成功/失败时取最后一条 assistant 消息 text 拼 `output.text`（≤4000 字）；模型自声明 Todo 只进 `output.declaredPlan`（`:808-848`）。
5. step 状态落库（`:850-859`）后：failed → 触发副作用补偿（§4.7）；succeeded 且有 workspace → `artifact_store.ingest_session_outputs(run_id, step_id, owner=run.requested_by)` 收集产物（`:866-876`，M9 带 owner 否则创建者本人下载 403）。最后落 `step.finished` 事件并 `_advance_run` 推进 DAG（`:877-882`）。

### 4.4 join 与条件边

join 是**纯结构性节点**：依赖判定通过即 CAS 置 succeeded（`orchestration_engine.py:371-380`），不产生执行、不占执行槽、不进超时兜底。汇聚策略 `all_success`（默认）/`any_success` 见 §4.3 第 3 步。条件边判定 `_edge_matches`（`:145-184`）：读源 step `output` JSON 的 field 与 op/value 比较（`==`/`!=`/`>`/`<`/`>=`/`<=`；`field='text'` 特判支持 contains/not_contains——生产路径 output 形状即 `{'text': …}`）；无 condition 的边恒命中（默认边）。分支取舍时机见 §4.3 第 2 步（源收敛后才裁）。

### 4.5 审批的结构节点语义（审批流本身归分册 05）

引擎产生审批请求的**两条路径**：

- **结构 approval 节点** `_open_approval`（`:617-652`）：runnable 的 approval step → 插 `ai_approval_requests`（requested_roles/users、risk_level、`expires_at=NOW()+timeoutSeconds`）+ step → waiting_approval；并发下第二个 pending 被唯一索引挡住即跳过（幂等）。
- **策略拦截** `_open_policy_approval`（`:583-614`，P2 §7.1）：**agent** 节点声明 `approval_policy` → 派发前先进 waiting_approval 建审批；`_advance_run` 每轮先查该 step 是否已存在 approved 请求，有则豁免放行（`:388-397`）。

**裁决落 step**（`approval_repo.decide :42-147`；HTTP 面与鉴权归分册 05）：pending 状态 CAS（`WHERE status='pending'`）+ `decision_hash` 落账；非 pending 返回既有状态 duplicate（幂等）。之后按 step kind 分叉：**agent step approve → step 回 blocked**，由下轮 advance 重新派发（策略拦截放行语义，`:91-112`）；其余（结构 approval 节点）**approve → succeeded / reject → failed('审批被拒绝')**（`:113-123`）。**审批 edit**（P2 §7.2）：批准时可携带 `edits` dict 合并进 `run_input_snapshot`（jsonb `||`），下游 step 渲染 `{{input.*}}` 时使用改后参数（`:124-137`）。**超时** `expire_overdue`（`:150-182`，scheduler 每 tick 调）：pending 且过期 → expired + step failed('审批超时') + `approval.expired` 事件（escalation=treated_as_reject）+ `_advance_run`。

人工挂起 `POST /runs/<run_id>/suspend`（admin，`ai_orchestrations.py:122-144`）：对 running 的 step 建高危险审批（`effect_summary='人工挂起: …'`）。docstring 声称「暂停其子会话（pause_requested）」，但代码中的 `pause_batch(...)` 分支条件读 `step.get('batch_id')`——steps 行没有该列（§3.1），恒 None，**暂停分支当前不可达**（与 docstring 冲突，见 §7-9）。实际语义：挂起 = 建审批，approve 后 step 回 blocked 重新派发（fencing 使旧执行体写回失效），reject 则 step failed。

**单步调试（P3）**：`POST /runs/<run_id>/mode`（`:147-165`）写 `execution_mode`（auto/single_step，仅活跃 run 可切）；`POST /runs/<run_id>/advance`（`:168-193`）临时切 auto → `_advance_run` 派发一轮 → 用 `WHERE execution_mode='auto'` 守卫切回 single_step。引擎侧的 single_step 闸门在 `_advance_run_locked:228,406-410`（`execution_mode == 'single_step'` 时每轮只放行 1 个 agent step）——但闸门读的 `run.get('execution_mode')` 来自 `get_run`，其 SELECT 列表（`:98-102`）**不含 execution_mode 列**，恒取缺省 'auto'，**闸门当前不可达**（见 §7-4）。

### 4.6 子代理：轨迹与复用钉住

**轨迹**：编排/批子会话在 worker 轮询期间由 `_persist_conversation` → `_collect_subtasks` 递归发现整棵子代理树（`batch_engine.py:2714` 起），每个子代理 upsert 自己的 `ai_chat_subtasks` 行（id=OC 子会话 sessionID）与 `ai_chat_subtask_messages`；会话复用场景还合并 `turn_segments`（每条 user 消息 = 一次委派任务的边界，`:2748-2753,2825`）。读取：用户侧 `GET /ai/chat/sessions/<sid>/subtasks/<subtask_id>/messages`（`ai_chat.py:1141-1160`，`subtask_repo.get_subtask_messages` 带 `owner_user_id` 归属校验）与管理员侧 `GET /ai/chat/admin/batches/<batch_id>/sessions/<sid>/subtasks/<subtask_id>/messages`（`ai_batch_admin.py:195-215`，不带归属校验——`require_permission` 已把关）共用同一 repo 函数。

**独立取消**：`POST /ai/chat/sessions/<sid>/subtasks/<subtask_id>/abort`（P3-B5，`ai_chat.py:1262-1307`）——用户对失控子代理的干预，与主会话 abort 同一生命线语义；**刻意不加 `_execution_controlled` 门禁**：父会话正被批任务/编排 worker 驱动时用户仍必须能单独叫停其中一个子代理。归属校验要求子任务确属 URL 中的父会话；非 running 409；best-effort `OpenCodeClient.abort_session`（不可达不 500）+ DB CAS（`WHERE status='running'`）落 `failed('已被用户手动取消')`。编排 step 的状态不受子代理取消影响（取消的是 step 子会话内部的委派层）。

**复用钉住三层防线**（平台判定源是批级 `subagent_reuse` 名单，`ai_subagent_internal.py:72-81`；端点对外口径见分册 01 §5.1）：

1. **强制层（OC 插件）**：`baize-subagent-reuse.js` 在 `tool.execute.before` 查 `/reuse`（带 callId 登记 before 意图，进程内存 10min TTL，修复 after 登记 vs 子任务持久化的时序竞态，`ai_subagent_internal.py:28-49`），命中 pin 则**强制覆盖**模型入参 `task_id`——模型常回显/编造旧 id，平台 pin 权威（`subagent_reuse_plugin.py:123-131`）；`tool.execute.after` 从输出解析 `task_id: ses_xxx`（兜底 part metadata.sessionId，`:140-161`）回调 `/pins` 登记。回调 3s 超时 + 1 次重试 + 进程内 120s 缓存兜底；**负判定只固化「确定性拒绝」**（not_enabled/no_agent），unresolved（父会话反查失败）不缓存——固化它会把瞬断窗口内的强制注入停 120s（`:56-94`）。
2. **引导层（批引擎提示词）**：派发前 `_build_reuse_directive` 把已钉住的 (agent → task_id) 写进 prompt，要求模型显式携带并**严格串行**委派（并行委派会绕过复用，`batch_engine.py:2274-2304`）。
3. **审计层（事后校验）**：`_audit_reuse_violations` 检查名单内 agent 在父会话下出现多个子会话（插件未生效/静默分叉）→ warning + `child.reuse.violation` 事件，不改任务状态（`:2306-2335`）；worker 持久化路径也把最新子会话 id 回写 pins 双保险（`:2832`）。

**登记语义**：`POST /pins` 优先走 callId 路径（agent 取 before 意图，不依赖 `ai_chat_subtasks` 行已持久化；task_id 空则 no-op），否则老路径按 session+agent 校验后 UPSERT；两条路径都是 `ON CONFLICT (root_session_id, agent) DO UPDATE SET task_id=EXCLUDED.task_id`（`:154-195`）——**(root_session_id, agent) 唯一**是复用锚定的不变式。

### 4.7 effect 自动补偿与产物收集

- **补偿（C4）**：step 进入 failed 终态（且非重试路径——重试已提前 return）时 `_compensate_step_effects`（`:664-685`）取该子会话全部 `status='committed' AND effect_type='mcp_write'` 的 effect 逐个 `compensate_effect`。补偿器内部把关（`execution_effect.py:155-220`）：**仅 method=POST 且 path 匹配 `/{collection}` 的动态数据创建可自动回滚**（直接 DELETE dynamic_data 行 + effect 独立收口为 compensated）；PUT 旧值未知无法回滚、DELETE 无逆操作、`/menus` 与保留集合不可删、`unknown` 状态禁自动补偿——均跳过返回 None。补偿失败只记日志，不影响 run 推进。
- **产物收集（Phase D）**：step succeeded 时把子会话 workspace `outputs/` 下文件逐个 `put_file` 进 artifact store（内容寻址 + `artifact_refs(run_id, step_id, session_id, relation='output')`），并按 `run.requested_by` 记 owner（`artifact_store.py:82-118`，M9：不带 owner 创建者本人下载会 403）；同路径写 artifact 类 effect 账本（幂等键含 sha256）。消费面是 `GET /v1/artifacts`（列表，admin 全量/用户按 owner 过滤，`artifacts.py:30-52`）与 `GET /v1/artifacts/<artifact_id>`（下载，owner 或 admin，内容缺失 410，`:15-27`）。

## 7. 设计决策

1. **定义发布不可变，编辑 = 新版本**（`orchestration_defs.py:150-153,160-164`）：`(id, version)` 复合主键 + `MAX(version)+1` 插入，无任何 UPDATE 定义内容的路径；run 引用具体 version，旧版本保留可取。校验（环/悬空边/join 入边/审批目标/action_checks 格式）在发布时把关，run 侧不再校验。
2. **三层状态派生自事实**（`orchestration_engine.py:3-9`）：run 状态由 step 事实派生、step 状态由子会话事实派生；引擎不维护独立状态机——每轮 `_advance_run` 从 DB 重读事实再派生。模型自声明 Todo 只进 `output.declaredPlan` 观测字段，永远不推进 DAG（沿用 todo_trace 边界）。
3. **并发安全用每转移 CAS 而非全局锁**（H4，`:210-213`）：advisory lock 方案在客户端崩溃时会以 idle-in-transaction 形式毒化后续所有推进；改为状态谓词 CAS（首派 blocked 谓词、超时 running+时间谓词、审批 pending 谓词、终态 running 谓词），重复推进输者 0 行生效，无死锁面。
4. **P3 单步调试（execution_mode）与代码现状的冲突**：`/mode` `/advance` 端点与 DDL 注释、引擎闸门（每轮限 1 个 agent step）构成完整设计；但 `get_run` 的 SELECT（`orchestration_engine.py:98-102`）不含 `execution_mode` 列，`_advance_run_locked:228` 读到的恒为缺省 'auto'——**single_step 闸门当前不可达，advance 端点的「派发 1 个 step」实际退化为普通推进一轮**。机制按代码现状记录，修复需把该列补进 get_run SELECT。
5. **effect 自动补偿刻意收窄**（C4，`orchestration_engine.py:664-685` + `execution_effect.py:155-220`）：只自动回滚「mcp_write POST 创建的动态数据记录」这一种可逆副作用；PUT/DELETE/menus/保留集合/unknown 一律不自动补偿（删除不可逆、旧值未知、禁自动重放），补偿失败不阻断 run。补偿在 step 状态落库之后执行，重试路径提前 return 不补偿（重试意味着副作用可能仍会被复用）。
6. **子代理独立取消刻意绕过执行控制门禁**（P3-B5，`ai_chat.py:1264-1267`）：父会话被 worker 驱动时，`_execution_controlled` 的 409 保护必须给「单独叫停一个子代理」让路——取消是生命线不是控制面冲突；取消只动子代理层（subtask CAS + OC abort），不碰父会话与编排 step 状态。
7. **复用钉住 (root_session_id, agent) 唯一 + 三层防线**（`2026_09_24_subagent_session_reuse.py:32-33`）：强制层（插件覆盖入参，平台 pin 权威）保证「不依赖模型自觉」；引导层（提示词要求携带 task_id 与串行委派）覆盖插件未部署窗口；审计层（violation 事件）让静默分叉可观测。before 意图（callID→root+agent，进程内存 10min TTL）解决 after 登记 vs 子任务持久化的竞态；插件侧负判定只固化确定性拒绝，unresolved 不缓存。
8. **复用钉住是批级能力，编排子会话不在范围**：`/reuse` 的 enabled 判定要求父会话 `batch_id` 非空且批级名单含该 agent（`ai_subagent_internal.py:98-100`）；编排子会话 batch_id=NULL 恒 not_enabled。如需编排级复用，需扩展判定源（当前代码无此路径）。
9. **suspend 的暂停分支不可达（与 docstring 冲突）**：`ai_orchestrations.py:138-139` 的 `pause_batch(...)` 以 `step.get('batch_id')` 为条件，但 `ai_orchestration_steps` 无 batch_id 列、`get_run` 的 steps SELECT 亦不取——恒 None，pause 从不执行。实际语义退化为「建高危险审批，approve 回 blocked 重派 / reject 落 failed」；fencing 保证被替换执行体的写回失效。另 `approval_repo.decide` 策略放行分支的 `command.applied` 事件重复 append 两次（`approval_repo.py:99-109`），多余一条重复事件（不影响状态）。
10. **策略拦截与结构审批是两种语义**：结构 approval 节点的 approve/reject 直接落 step 终态（节点即审批）；agent 节点的 approval_policy 是「派发前闸门」——approve 只解除拦截（step 回 blocked 重新派发），已存在 approved 请求即永久豁免，防止重复拦截。
11. **条件边在源收敛前不裁剪**（H5 残留修复，`orchestration_engine.py:247-249`）：源节点无 output 时把全部出边目标视为候选，分支取舍推迟到源 succeeded——否则条件目标会被不可逆 skip，源收敛后也永不可达。step.output 的写入点（最后一条 assistant text）与条件判定/提示词渲染同源。
12. **join 的 any_success 兼顾不卡死与不误杀**（P2-A6/H6，`:327-338,360-366`）：一侧依赖 skip/failed 不再永久阻塞 join；但仍有非终态依赖时不提前判死（成功的那个可能还在路上），全部依赖终态且无一成功才允许 skip。
13. **与旧文档的关系**：`13-AI批任务实时进度与编排设计.md` 等历史文档中的编排描述与本册冲突处，以代码与本册为准；审批流细节以分册 05 为准。
