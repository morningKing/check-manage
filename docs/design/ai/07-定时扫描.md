## 1. 模块职责

定时扫描（界面称「AI 定时任务」）把 `dynamic_data` 数据页变成 AI 的待办队列：按任务配置的间隔，调度器把状态字段为「待处理」的记录**原子认领**（翻成「处理中」），为每条记录组装上下文目录（`record.md` + 附件）与 JSON 输出契约，然后作为批任务的一个来源（`scan_task_id` 打在批与子会话上）复用批引擎派生子会话执行。每个子会话到达终态时，批引擎回调扫描引擎 `on_child_finished`：从 AI 回复中解析 JSON、把映射字段**结构化回写**到同一条记录、状态字段落「已处理」，回写副作用登记效果账本；回写校验（TV-03/TV-04）不过的记录落「处理失败」；配置了产出文件字段时，把子会话工作区 `outputs/` 的产物导入 `data_files` 并挂到记录的文件字段。

按职责分四块：

| 职责 | 说明 | 证据 |
| --- | --- | --- |
| 任务 CRUD 与手动触发 | 任务管理面（全 `admin.ai_scan`）、run-now 立即跑一轮、手动幂等导入产出文件 | `server/routes/ai_scan_tasks.py`（103 行，7 端点） |
| 调度 | APScheduler 每分钟 tick，按 `last_run_at + interval` 判到期；两级租约保证多实例只有一份在跑；启动时孤儿清扫 | `server/utils/ai_scan_scheduler.py`（82 行） |
| 认领与派生 | `FOR UPDATE SKIP LOCKED` 批量/单条认领、上下文暂存目录、提示词与 JSON 契约组装、`create_batch` 派生 | `server/utils/ai_scan_engine.py`（493 行） |
| 回写与校验 | 终态回调：JSON 解析 → 同行结构化回写 → 效果账本 → TV-03/TV-04 确定性校验 → 产出文件导入 | `server/utils/ai_scan_engine.py:120-263`；`server/utils/scan_writeback_validator.py`（99 行） |

## 4. 核心流程

### 4.1 调度：两级租约 + 1 分钟 tick

`app.py:548-549` 启动时调 `start_scan_scheduler(app)`（`ai_scan_scheduler.py:60-82`）：

1. **启动门**：先抢实例级租约 `execution_lease.acquire('scan', …, lease_kind='scheduler')`——抢不到（他实例持有）直接 `return`，本进程不启动调度器（多实例部署只有一份在跑；本批不做后台重试）。
2. **孤儿清扫**：启动即跑一次 `sweep_orphans`——所有 `data->>status_field = running_value` 且**不存在** live（pending/running）子会话的记录，回翻 `pending_value`（`ai_scan_engine.py:475-493`；重启恢复语义，测试 `test_ai_scan_sweep_orphans.py`）。
3. **tick**：`BackgroundScheduler` 每 1 分钟跑 `_tick`（`id='ai_scan_tick', max_instances=1, coalesce=True`，`:80-81`）。tick 内再抢 tick 级租约 `scan_scheduler`（`:34-42`，租约基建不可用时退化为进程内互斥，不阻断扫描），然后遍历 `list_tasks()`：`enabled` 且 `_is_due(task, now)` 才跑。
4. **到期判定 `_is_due`**（`:14-23`）：`now - last_run_at >= scheduleIntervalMinutes * 60`；无 `last_run_at` 视为到期。
5. **任务级锁**：每任务一把非阻塞 `threading.Lock`（`:26-28,49-57`），拿不到（上一轮还在跑）跳过本轮，不排队。

### 4.2 一次扫描 `run_task`（`ai_scan_engine.py:430-458`）

```
claim_records → build_context_dir ×N → assemble_prompt → create_batch → mark_run
```

- **认领 `claim_records`**（`:359-396`）：CTE `picked` 按 `collection + branch_id + pending 谓词 + extra_filter` 选前 `max_records_per_scan` 条，`FOR UPDATE SKIP LOCKED` 防并发任务互抢，同语句 UPDATE 翻 `running_value`（`version+1`）并 `RETURNING id, data`。pending 谓词（`:351-356`）：`pendingValue` 为空匹配「键不存在或空串」，否则精确等值。`extraFilter` 经 `mongo_query.translate` 生成 WHERE 片段（引用未别名的 `data` 列，与 `routes/dynamic.py` 同口径；解析失败记日志并忽略过滤，不炸整轮，`:365-378`）。
- **上下文暂存 `build_context_dir`**（`:335-348`）：`<ws_root>/scan-staging/<task>/<record>/` 下写 `record.md`（按 `page_configs` 的字段标签渲染记录数据，**排除**状态字段与全部映射列——回写前不给 AI 看旧答案，`:344-346`）+ `attachments/`（记录 file/image 字段引用的 `data_files` 复制，`:312-332`）。返回相对路径作 batch_input_file。
- **提示词 `assemble_prompt`**（`:56-64`）：`[工作区说明 preamble] + [prompt_template] + [JSON 输出契约]`——契约按 `field_mapping` 的 jsonKey 列出 `{ "key": ... }`，要求回复末尾输出仅含这些字段的 JSON 代码块。前端管理页有同构的「输出契约预览」（`AiScanTaskManager.vue:138-140`）。
- **派生 `create_batch`**：批名 `AI定时·{task}·{时间戳}`，`scan_task_id=task.id`、`agent=task.agent`（空→None），每条记录一个子会话（`files` 携带 recordId）。机制归分册 03。
- **失败回滚**：`create_batch`/暂存抛错时 `_revert_claimed` 把已认领记录回翻 `pending_value`（下轮重试）、清理本任务 `scan-staging/`（**新旧两个 workspace 根都清**——根路径统一前的遗留树，`:448-457` 与 `utils.workspace.batch_roots`）、`mark_run(error)` 后 re-raise。

### 4.3 子会话执行：批通路上的扫描特例

子会话由批引擎 `BatchWorker._run_one`（`batch_engine.py:1289`）执行，扫描侧只有三处特判：输入提示不注入（扫描子会话自带上下文 preamble，`_with_input_hint` `:1263-1272`）；执行审计 attempt `source_type='scan'`（`:1438-1439`）；**不发子任务完成铃铛**——一次调度产出几十上百个子会话且周期反复，结果经数据表状态回写呈现（`_notify_child_done` `:1929-1930`）。机制详见分册 03 §4。

### 4.4 终态回调 `on_child_finished`（`ai_scan_engine.py:120-192`）

批引擎在每个子会话到达终态时调 `_notify_scan` → `on_child_finished(session_row, final_msg, ok)`（`batch_engine.py:1979-1986`；成功 `:1627`、各类失败路径 `:1383,1426,1604,1619,1636,1660,1670`）：

1. **定位**：`session_row.scan_task_id` 加载任务（snake_case 查询 `:67-82`）；无任务或无 `source_record_id` 直接返回。
2. **失败终态**：`ok=False` → 状态落 `failed_value`，返回（`:127-129`）。
3. **解析**：`extract_json(message_text(final_msg))`——`message_text` 拼接 assistant 文本 parts（`:47-53`）；`extract_json`（`:14-44`）优先取**最后一个** ```` ```json ```` 围栏块，退化为从后往前扫配平的顶层 `{...}`。解析失败或任一 `required` 映射键为空 → 记 TV-04 违例（见 4.5）+ `failed_value`，返回（`:130-139`）。
4. **同行结构化回写 `_write_back`**（`:97-117`）：单条 UPDATE，`data = jsonb_set(jsonb_set(…jsonb_set(data, ARRAY[col1], to_jsonb(v1::text))…, ARRAY[status_field], to_jsonb(done_value))`——嵌套表达式**逐层参数化**（列名与值全走 `%s` 占位，无字符串拼接），同语句 `updated_at=now(), version+1`，WHERE 带 `id + collection + branch_id`。返回 rowcount。
5. **效果账本**（`:143-157`，衔接口径以 03 册 §3.5 / 05 册 §4.7 为准）：`record_effect(session_id, 'scan_writeback', f"{task_id}:{rid}:{vh}")`，幂键含回写值摘要 `vh = sha256(sorted(映射列→值))[:16]`；登记成功即 `settle_effect('committed' if n else 'failed', external_ref=f'record:{rid}')`。**best-effort**：账本异常吞掉，不影响回写本身——锚定执行回写的会话，恢复决策按会话判定。
6. **rowcount=0**：匹配 0 行（记录被删/移）→ `validate_writeback` 产 TV-03 + 入审计，日志告警，返回（`:158-165`）。
7. **写后读校验**（`:166-183`）：`_recheck` 回读 `dynamic_data.data`，`validate_writeback` 逐映射列比对「期望 vs 实际」、状态字段比对 done_value（`scan_writeback_validator.py:38-65`）；不一致 → 违例入审计 + `failed_value`。
8. **产出文件导入**：配置了 `output_file_field` 时调 `_import_child_outputs_to_record`（异常只记日志，`:185-192`）。

### 4.5 回写校验器与违例入审计（`scan_writeback_validator.py`）

| 违例 | 判定 | 严重度 | 证据 |
| --- | --- | --- | --- |
| TV-03 回写失败 | UPDATE 匹配 0 行（`:23-30`）；映射列回读值与期望不一致（`:45-56`）；状态字段未落 done_value（`:57-65`） | high / high / medium | `record:{rid}`、`record:{rid}:{col}` |
| TV-04 结果不完整 | 必需 jsonKey 在 parsed 中缺失/空（回写虽成功但结果残缺，`:67-77`） | high | `record:{rid}:{jsonKey}` |

`record_violations_to_audit`（`:82-99`）把违例以 `scan.writeback.violation` 事件追加到该会话最新 attempt（attempt 不存在则静默跳过；全程 best-effort）——采集与事件通道口径归分册 06，与门禁/账本的互补关系见分册 05 §4.7。

### 4.6 产出文件导入 `_import_child_outputs_to_record`（`ai_scan_engine.py:195-263`）

把子会话工作区 `outputs/` 下的产物变成记录上的文件（与手工上传同构的 `{uid, name}` 列表，数据行内直接预览/下载）：

1. 读记录现有字段值，按已有 `uid` 去重（幂等：重复调用只导入新出现的文件，`:218-221`）。
2. 逐文件复制到 `DATA_FILES_ROOT`（`{uid前2位}/{fn}` 分桶）、INSERT `data_files`（`uploaded_by=子会话 user_id`，空则 `'ai-scan'`）。
3. **账本旁路补漏**（P1-A2b，`:206-244`）：此路径直接 INSERT，不经过批引擎的 `import_recorded_files`——逐文件登记 `file_import` effect（幂键 `session:文件名`，带 batch_id）并即时 `settle 'committed'`，审计/恢复按 `(session_id, effect_type, idempotency_key)` 幂等去重。
4. 有新增才 UPDATE：`data = jsonb_set(data, ARRAY[field], COALESCE(data->field,'[]') || 新数组)`（追加不覆盖，`version+1`，`:248-260`）。

### 4.7 手动路径

- **run-now**（`ai_scan_tasks.py:55-69`）：加载任务后同步调 `run_task`，异常返回 500（详情在服务端日志）；写 `log_operation('run', …)`。与调度同一函数，`enabled=False` 的任务也允许手动跑（run-now 不检查 enabled；对外 API 包装层刻意保持一致，见 `open_api_scan_tasks.py` 模块注释，归分册 12）。
- **import-outputs**（`:72-101`）：对指定子会话手动重跑导入。校验子会话确属该任务（`scan_task_id` 匹配，`:86-92`）且任务配置了 `output_file_field`（否则 400），然后复用 `_import_child_outputs_to_record`，返回 `{'imported': n}`——幂等，重复调用只补新文件。
- **删除任务**（`ai_scan_repo.py:125-139`）：先把该任务在途（running_value）记录回翻 pending_value，再删任务行（子会话/批上的 `scan_task_id` 由 ON DELETE SET NULL 悬空，历史会话保留）。
- **单条重跑 `claim_one`**（`ai_scan_engine.py:399-427`）：与 `claim_records` 唯一语义差别是**不带 pending 谓词**——手动重跑必须能对「已处理」的行再来一次；同样 `FOR UPDATE SKIP LOCKED`，行被锁/不存在返回 None。数据页行操作按钮的 AI 分支复用它 + `build_context_dir` + `create_batch`（`utils/row_action_engine.py:5,23,362`）。

## 7. 设计决策

1. **跨表副作用交给 skill 经 MCP、仅同行结构化回写内建**。引擎内建的回写只碰**本任务绑定记录本身**的字段（映射列 + 状态列，SQL 恒带 `collection + branch_id` 谓词）；要写别的表/造新记录，由子会话里的 skill 走 MCP 写工具（经门禁与 `/ai/data-internal` 白名单，分册 05/01 口径）。这样内建面始终「一行一事务、可校验、可回滚」，开放面则纳入统一的门禁+账本安全网。
2. **复用批引擎而非另起执行器**。扫描不自己跑 OpenCode，只负责「选行 → 造上下文 → create_batch」；并发控制、审计、取消/暂停、容灾全部白嫖批通路（特例仅 4.3 的三处）。`run_task` 失败时回翻认领记录 + 清双根暂存，保证「失败即回滚到下轮可重试」。
3. **认领即状态机**。pending → running（认领，SKIP LOCKED 防互抢）→ done/failed（终态回调）；running 卡死由启动孤儿清扫兜底回 pending。`claim_one` 刻意不带 pending 谓词以支持手动重跑已处理行——两个认领函数的语义差异是特性不是疏漏。
4. **回写一条 UPDATE、全参数化**。映射列 + 状态列合成嵌套 `jsonb_set` 单语句落库（原子、`version+1` 可被乐观锁感知），列名/值全走占位符；随后**写后读**比对，不信任 rowcount 单一信号。
5. **账本 best-effort、校验 fail-closed**。effect 登记/收口异常不阻断回写（可用性优先）；但 TV-03/TV-04 违例会把记录落 `failed_value` 并入审计（正确性优先）——两条铁律分工明确。
6. **产出文件导入走账本旁路补漏**（P1-A2b）：直接 INSERT `data_files` 的路径逐文件登记 `file_import` effect 即时收口，恢复对账不漏这批副作用；文件列表用 `||` 追加保持幂等。
7. **调度多实例语义**：启动门 + tick 租约两级防双跑，tick 级租约在基建不可用时退化为单实例互斥而不是停摆；任务级非阻塞锁让「上一轮没跑完」的任务本轮直接跳过。
8. **扫描子会话不发铃铛**：量级（每轮几十上百）× 频率（按计划反复）会把通知中心刷爆；结果界面是数据表状态本身。
9. `output_file_field` 目前是**后端先行**能力：repo/引擎/迁移/手动导入端点齐备，管理界面与 TS 类型（`src/types/aiScanTask.ts`）尚未暴露该字段——配置需走 API。
