## 1. 模块职责

批任务把「一个 prompt × N 个文件」变成 N 个无人值守运行的 OpenCode 子会话：用户上传文件暂存、创建批次，进程内 worker（`BatchWorker`）认领 pending 子会话、准备工作区、派发 OpenCode 回合、协作式收集中断/暂停、按 CAS+Fencing 写回终态，批次终态后经 outbox 可靠投递 HMAC 回调。HTTP 边与引擎彻底分离——路由文件（`ai_chat_batches.py:3`）只做参数校验与调 `batch_repo`/`get_worker().notify()`，全部 SQL 在 `batch_repo.py`，全部执行在 `batch_engine.py`。

按职责分五块：

| 职责 | 说明 | 证据 |
| --- | --- | --- |
| 用户面 | 批 CRUD、staging 暂存上传、子会话级 cancel/resume/continue/reexecute、命令平面、事件流 SSE、attempt 链查询、门禁期望编写辅助 | `server/routes/ai_chat_batches.py`（874 行，26 端点） |
| 管理面 | 跨用户批次列表/详情/消息、retry/reexecute/软删、产出文件预览下载导入、工具调用时间线、attempt 时间线、outbox 投递状态与重放 | `server/routes/ai_batch_admin.py`（465 行，17 端点） |
| 引擎 | 单例 `BatchWorker`：LISTEN/NOTIFY 唤醒的 dispatcher、claim CTE、`_run_one` 执行回合、CAS 终态写回、自动重试/对账 | `server/utils/batch_engine.py`（3555 行）；SQL 层 `server/utils/batch_repo.py`（1614 行）；事件流 `server/utils/batch_events.py`（105 行） |
| 持久化执行 | 执行器租约（多实例互斥 + fencing token）、命令幂等平面、checkpoint、副作用账本、预算与用量 | `server/utils/execution_lease.py`、`execution_commands.py`、`execution_checkpoint.py`、`execution_effect.py`、`execution_budget.py` |
| 交付 | 批次终态回调的 outbox 可靠投递（退避/死信/人工重放） | `server/utils/delivery_outbox.py`（396 行） |

同一套引擎还有两个**非 UI 消费方**：开放 API（`/v1/ai-batches`，契约细节归分册 12）与定时扫描/AI 定时任务（`ai_scan_tasks`，归分册 07）——三者共用 `create_batch`/`BatchWorker`，`api_key_id`/`scan_task_id` 列区分来源（`batch_repo.py:296-300`）。

### 3.8 状态机

**批次**（重算逻辑 `batch_repo.py:21-57` 与引擎侧 `_recompute_batch_status`，`batch_engine.py:377-468`，同一条规则）：`pending`（无终态且无 paused）→ `running`（有子任务在跑）/`paused`（有 paused 且未全终态）→ 终态三选一：`completed`（done=total）/`failed`（failed=total）/`partial`（混合）。**子任务**：`pending → running →（completed | failed | cancelled | paused）`；`paused` 可回 `pending`（resume）；`cancelled` 计入批次 `failed` 计数，`paused` 不占计数（`batch_engine.py:1204-1215`）。

## 4. 核心流程

### 4.1 端到端主链：创建 → 暂存 → 认领 → 执行 → 终态 → 交付

1. **暂存**：前端逐文件 `POST /ai/chat/batches/staging/upload`（`ai_chat_batches.py:66-89`）落到 `batch-staging/<user>/<upload_session_id>/`，返回 `{name, path}`。
2. **创建**：`POST ''`（`:92-143`）校验文件数上限（可配置，`get_max_files_per_batch`）、路径遏制（`validate_staged_files` 防跨用户/绝对路径，`:110-115`）、门禁期望可编译性（`agent_ledger.validate_checks`，非法 400 不带病入库 `:121-126`）、复用名单合法性；`create_batch`（`batch_repo.py:245-313`）**单事务**插入批次行 + N 条 `pending` 子会话；创建后 `get_worker().notify()`（`:141-142`）。
3. **唤醒**：除 `notify()` 事件置位外，子会话入 `pending` 瞬间由行级触发器 `pg_notify('batch_claim_ready')` 推送（`2026_09_26_batch_notify_trigger.py:33-37`），dispatcher 专用 LISTEN 连接 select 唤醒，断线退避重连、轮询兜底（`batch_engine.py:726-735`）。
4. **认领（claim）**：`_claim_pending_sessions`（`batch_engine.py:1116-1201`）单条 CTE 完成——`FOR UPDATE SKIP LOCKED` 按 `created_at, batch_seq` 取 pending 行，**同一 UPDATE 里**写 `status='running'`、`lease_owner`、`lease_until=NOW()+ttl`、`heartbeat_at=NOW()`、`fencing_token=fencing_token+1`（`:1150-1157`）；claim 前先做预算闸（见 §4.5）与批级 max_concurrency 闸（`concurrency_blocked_batches`，`execution_budget.py:238-256`）；随后开 turn 并回写 `active_turn_id`（`:1163-1189`），批次 `pending → running` 即刻反映（`:1190-1199`）。
5. **执行**：`_run_one`（`batch_engine.py:1289-1736`）——continue 判定（有 `opencode_session_id`+`continue_prompt` 即原会话续跑，`:1338-1353`）；新会话则 `_prepare_workspace`（staged 输入恢复，`:289`）→ `provision_repo` 克隆进 `.opencode/`（失败降级不挂任务，`:1399-1404` 与 `_provision_workspace :2360`）→ 全局技能注入 → `_check_agent` fail-fast（未知/subagent 当主 agent 会静默挂起，`:1418-1430`）→ `create_session`；无人值守指令 `_BATCH_DIRECTIVE`（禁提问/不许放弃，`:60-66`）+ 记忆块 + 输入提示拼进 prompt；注册门禁期望（入口 A/B，`:1331-1336`，机制归分册 05）；audit attempt 创建（`:1434-1476`）；`send_message` 失败走 `_recover_session` 原地重建会话（`:1501-1517`，恢复细节归分册 11）；轮询 `_await_finished` 期间边攒边持久化对话（进度去抖 2.5s，`PROGRESS_PERSIST_SEC :742`）与 progress checkpoint。
6. **终态**：回合收敛后等子代理收敛（`wait_subtasks_drained :1551`）→ 动作门禁核对（fail-closed：登记不可证实/inconclusive 一律不得 completed，`:1553-1608`；机制归分册 05）→ `transition_child` CAS 写回（§下文）。异常路径分派：`_SessionCancelled`→`_mark_cancelled`、`_SessionPaused`→`_mark_paused`、`_LeaseLost`→**直接放手不写回**（fencing 会拒，`:1642-1649`）、可重试失败→auto-retry（§4.3）。finally 里 best-effort 收尾：工作区文件记录、复用违规审计、编排推进通知、usage 累计 + 预算判定 + turn_complete checkpoint（`:1673-1736`）。
7. **交付**：`transition_child` 命中后同事务完成「计数 +1 → 批次状态重算 → child.status 事件 → active turn 收口」（`batch_repo.py:142-167`）；批次落终态时同事务追加 `batch.status` 事件并把回调投入 outbox（`recompute_batch_status_tx :58-81`；引擎兜底路径 `_recompute_batch_status :440-462`，outbox 关闭时回退直发 `_notify_callback :509`）→ 投递线程消费（§4.7）。

**CAS 与 fencing（写回正确性的两道闸）**：`transition_child`（`batch_repo.py:85-178`）的 WHERE 同时带 `status='running'` + `execution_generation=<claim 快照>` + cancel/pause 标志期望 + `fencing_token=<claim 时 token>`（`:117-141`）；rowcount=0 即过期写，调用方不得改状态/计数（`_on_transition_miss :3026-3053` 按 cancel/pause 标志重定向或忽略）。fencing_token 必填——worker 路径传 claim 捕获值，「无 claim 权威」的对账路径传决策查询刚读出的当前值（`:107-109`）；`_require_fencing :711` 强制。实例级互斥由 `execution_lease.acquire` 提供：仅租约过期或自持可占，token 每次 +1（`execution_lease.py:31-70`）；worker 持 lease 才跑 dispatcher，心跳连丢 3 次停整个 dispatcher 宁让位不双跑（`batch_engine.py:877-895`）。

### 4.2 控制平面与命令平面

**协作式控制标志**：`cancel_requested`/`pause_requested` 置位后，排队中的在 claim 前被 `_cancel_pending_requests` 直接转化（cancelled 计入 failed / paused 静默停靠，`batch_engine.py:1203-1253`），运行中的在轮询循环里抛 `_SessionCancelled`/`_SessionPaused` 协作收口。批级操作各有明确语义（路由 docstring 即语义声明）：`cancel`（中断，可 resume）、`pause`（温和的停，不占 failed）、`resume`（paused+cancelled 回 pending，原会话续跑）、`retry-failed`（2026-09-29 起与重新执行同语义：先清工作区再重排，任一工作区重置失败整体放弃 `ai_chat_batches.py:465-475`）、`force-stop`（管理员强制通道：fencing+1 使旧执行体写回全失效、非终态立即落 cancelled、批次置 failed，`batch_repo.py:1400-1466`）。删除保护：非终态批次须 `stop=1` 走「停止并删除」，drain 上限 10s（`DRAIN_TIMEOUT_SEC :63`），超时 409 保留任务与工作区（`BATCH_DRAIN_TIMEOUT`，`:384-401`）。

**命令平面（幂等）**：`POST /<batch_id>/commands`（`ai_chat_batches.py:602-675`）把控制意图先落 `ai_execution_commands` 再同步应用（保持既有 HTTP 语义——pause 立即生效；异步化是有意推迟的取舍，`execution_commands.py:8-10`）。幂等键：`Idempotency-Key` 头优先，缺省由 `(type, batch, requester)` 派生自然键（`execution_commands.py:37-39`），同键重复提交返回既有命令且**不重复执行**（`:43-50`）；应用结果回写命令行（`finish_command` 只更新 `status='accepted'` 行，`:80`），形成完整命令历史。失败分类回写：CAS 冲突 → `rejected/VERSION_CONFLICT` 409，工作区重置失败 → `rejected/WORKSPACE_RESET_FAILED` 500（fs 先于库 fail-closed，`ai_chat_batches.py:648-664`）。命令历史与单条状态查询 `:678-712`。

### 4.3 失败分类、自动重试与 gate_retry

- **可重试判定** `_is_retryable`（`batch_engine.py:3161-3176`）：停滞（`stalled (no progress)`，`STALL_TIMEOUT_SEC=180 :748`）与工具卡死（`TOOL_STALL_TIMEOUT_SEC=900 :755`）两个 watchdog 原因、`RETRYABLE_TURN_FAILED` 白名单（`APIError/UnknownError/MessageOutputLengthError/StructuredOutputError :762-763`）、网络异常；硬超时上限、密钥错、用户中断、上下文超限与一切未知失败**保守不重试**。
- **自动重排** `_maybe_auto_retry`（`:3178-3214`）：预算 `MAX_AUTO_RETRY`（env `AI_BATCH_MAX_AUTO_RETRY`，默认 2，`:758`）内状态回 pending、`retry_count+1`、generation+1；已开跑过的置 `AUTO_RETRY_CONTINUE_PROMPT` 原会话续跑；重排前旧 attempt 收口为 `recovering` 并串 `parent_attempt_id` 链（`_close_attempt_for_requeue :1842-1851`）。
- **gate_retry**（`_maybe_gate_retry :1853-1897`）：门禁不过时带「缺失明细」定向修复提示在原会话 continue 续跑；开关优先级：批级 `gate_retry` 列 > 全局 env `AI_BATCH_GATE_RETRY`（默认 0）；批级开启时预算至少 1 次，与 auto-retry 共用 `retry_count`。
- **看门狗只杀真死的**：工具/子代理活动计为进度（`_progress_signature`/`_subagent_progressing`），正常长任务不会被时钟杀掉（`:736-755` 注释）。

### 4.4 对账与恢复（概览；决策表与压测口径详见分册 11）

`_reconcile_stale_running`（`batch_engine.py:3264-3368`）与 dispatcher 同线程运行，对未跟踪且租约已过期/NULL 的 running 行按恢复决策表分流：租约未过期 → 等待（可能是另一实例）；存在 unknown 副作用 → `needs_review` 禁自动重放；OpenCode 会话 404 → 带准确原因失败；整体不可达 → 跳过本轮不误杀；有 checkpoint → 原会话续跑；无 oc 会话 → 原样重排。每次接管写 `child.recovered` 事件（`_emit_recovered :3370`）。重启路径不再无条件重放（H8）：`_start_with_lease`/`_acquire_retry_loop` 只起线程，遗留 running 行交给对账器（`:842-875`；L856、L1514 的 `_recover_session` 派发失败重建属该机制，详归分册 11）。

### 4.5 预算两判定点

预算是**显式启用**的能力：无预算行 = 不限制（`execution_budget.py:11`）。两个判定点：

1. **claim 前**（`_claim_pending_sessions` 内联 SQL，`batch_engine.py:1121-1146`）：批次达 `max_concurrency` → 整批本轮不认领；`on_exceed ∈ (drain, abort)` 且 tokens/cost 累计已超限 → 该批 pending 行不认领（drain 语义：运行中的自然收敛，不再发新）。
2. **子任务终态**（`_run_one` finally，`:1691-1719`）：`accumulate_usage` upsert 用量（`execution_budget.py:66-97`）→ `evaluate_batch_budget` 五维判定（tokens/cost/wall_clock_ms/tool_calls/subagents，`:131-157`）→ 超限写 `budget.exceeded` 事件并 `apply_budget_action`（`:160-176`）：`warn` 仅事件；`drain` 靠判定返回值驱动 dispatcher 跳过；`abort` 给全部 pending/running 置 `cancel_requested`。user/api_key scope 维度同口径但**恒 drain**（不 abort 他批正在跑的子任务，`evaluate_scope_budget :217-235`）。

### 4.6 事件流

事实源是 `ai_batch_events` 表；worker 不承担推送职责，SSE 与轮询都查表（`batch_events.py:1-9`）。**seq 分配**禁止无锁 MAX+1：`append_event` 以事务级 advisory lock `pg_advisory_xact_lock(hashtext(batch_id))` 串行化同批次追加——seq 严格单调，不同批次互不阻塞（`:34-47`）；在调用方事务内追加时以 `SAVEPOINT be_evt` 包裹，失败只回滚事件本身（「事件绝不打断业务」，`:50-66`）。事件写入与状态写入同事务（`transition_child` 里的 `child.status`，`batch_repo.py:153-159`）。消费侧两路：用户面单批分页 `GET /<id>/events`（游标过旧 410 `CURSOR_EXPIRED`）与多批 SSE `GET /events`（`ids` ≤20、帧 `batch_event`/`batch_done`、`Last-Event-ID` 断点补发、15s ping、30min 硬上限，`ai_chat_batches.py:806-874`）；对外同源端点见 §5.3。前端 `BatchEventStream` 订阅 + 轮询降级（§2.2）。

### 4.7 回调交付 outbox

批次终态提交与 outbox 插入**同事务**（`recompute_batch_status_tx :58-81`；`(event_id, target_url)` 唯一去重幂等），H7 回修后 effect 与入队同事务登记，不留孤儿 planned。投递器是持 `lease_kind='delivery'` 租约的独立线程（`OutboxDeliveryLoop :297`，5s 轮询；抢占失败后台重试，旧租约过期即接管）——多进程只有一个投递者；长 drain 期间每行投递后续租，杜绝租约过期窗口内的同进程双投递者（`drain_due_once` 的 `heartbeat_fn :232-235`）。领取条件：`pending/failed` 且到期，或 `sending` 超过 10 分钟（进程被 kill 的回收，claim 时把 `next_retry_at` 锚到 NOW()+10min，`:91-117`）。单行投递复用 `webhook_engine` 的 HMAC 签名与 HTTP（`deliver_one :183-215`），返回值三分类：`True`（2xx）/`False`（确定性失败 → 退避）/`'uncertain'`（无响应 → effect 落 unknown 触发 fail-safe）。**退避序列 1s/5s/30s/5m/30m（`BACKOFF_SECONDS :22`），最多 8 次（`MAX_ATTEMPTS :23`）后 `dead_letter`**；每次投递结果写 `delivery.sent/delivery.failed` 事件（批次已删则跳过，`:157-176`）；人工重放 `replay_dead_letter`（failed/dead_letter → pending，attempt 归零，`:243-254`）。开关 `AI_DELIVERY_OUTBOX_ENABLED=0` 回退旧直接 POST 路径（`:26-28`）。退避与死信口径被分册 11/12 引用。

## 7. 设计决策

1. **管理员蓝图独立成文件**（`ai_batch_admin.py:3-6`）：`ai_chat_batches.py` 的 `url_prefix` 钉死 `/ai/chat/batches`，装不下 `/ai/chat/admin/batches`；且管理面每个端点的安全假设与普通端点**相反**（跨用户查 vs 按归属过滤），物理隔开让边界一眼可见。管理面写路径纪律：先 `admin_get_batch_owner` 再调按归属过滤的写函数——「系统里干脆不存在不按归属过滤的写函数」（`:115-118`）。
2. **命令平面同步应用**（`execution_commands.py:8-10`）：与 spec 的差异——内部/外部路由同步应用命令（保持 pause 立即生效的既有 HTTP 语义），不引入异步 worker 消费；命令表只承担幂等与审计，异步化留给需要时再开。幂等键缺省由 `(type, batch, requester)` 派生（`ai_chat_batches.py:604-607`），对外 API 则强制 `Idempotency-Key` 头。
3. **预算两判定点**（`execution_budget.py:7-10`）：claim 前（含 max_concurrency 与 drain/abort 超限闸，直接内联在 claim CTE 的 NOT EXISTS 里，`batch_engine.py:1137-1146`）+ 子任务终态（usage 落库后判定）。预算行缺省 = 不限制——预算是显式启用的能力，不是默认约束。
4. **CAS + fencing 双闸**：`transition_child` 是终态写入唯一入口，WHERE 同时校验 running 态、claim 代数、控制标志期望与 fencing token（`batch_repo.py:95-112`）；「不再提供未传则现读自比的恒真兜底」（`:107-109`）——fencing token 必填是 M6 回修的硬要求。实例级租约丢失时 worker 宁可整实例停 dispatcher 也不与接管者双跑（`batch_engine.py:877-895`）。
5. **事件 seq 用 advisory lock 而非无锁 MAX+1**（`batch_events.py:5-9`）：P1-5 根因修复，并发写同批次时后到者等待，seq 严格单调；事件追加整体 best-effort（SAVEPOINT 隔离，「事件绝不打断业务」）。
6. **outbox 与终态同事务 + 三分类投递结果**：回调不丢（同事务入队）；HTTP 失败必须区分「确定性失败」与「无响应 uncertain」（12 号 §3.1 回修：此前无条件按成功记），uncertain 落 unknown effect 触发恢复决策的 needs_review。
7. **无人值守护栏前移**：`_BATCH_DIRECTIVE` 提示词约束（禁提问/不许放弃）+ 系统级兜底（question 自动拒绝 + 工具卡死看门狗）双保险（`batch_engine.py:56-66,744-755`）。
8. **与旧文档的关系**：`AI批任务容灾与恢复机制.md`、`AI批任务实时进度与编排设计.md` 等历史文档中的 claim/恢复/事件流描述与本册冲突处，以代码与本册为准；容灾细节归分册 11。
