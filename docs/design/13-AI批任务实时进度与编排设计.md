## 1. 文档概述

### 1.1 背景与痛点

批任务引擎（`utils/batch_engine.py`）目前具备完整的认领/超时/取消/重试链路，但编排与可观测层有四个结构性短板：

| # | 痛点 | 现状证据 |
|---|------|----------|
| P1 | **进度纯轮询**：批详情 5s、列表 10s、子会话消息 2.5s 盲轮询，状态变化最坏延迟 10s，且绝大多数轮询是空转 | [aiChatBatches.ts:9-10](../../src/stores/aiChatBatches.ts) 、[AiChatView.vue:562](../../src/views/ai-chat/AiChatView.vue) |
| P2 | **并发度硬编码 3**：所有用户共享一个 3 线程池，无法按部署规模/负载调整，调整必须改代码重启 | [batch_engine.py:476](../../server/utils/batch_engine.py) `MAX_CONCURRENT = 3` |
| P3 | **无优先级**：认领严格按 `created_at, batch_seq` FIFO，紧急批任务只能排在所有历史 pending 之后 | [batch_engine.py:598](../../server/utils/batch_engine.py) 认领 CTE |
| P4 | **无暂停**：误创建/需让路的批次只能逐个取消或等它跑完，没有"先让路、回头续跑"的语义 | `ai_chat_batches` 无 paused 维度 |

### 1.2 目标

- 子任务状态变化 **≤ 2s 内可见**（P95），轮询退化为降级兜底而非主通道
- 并发度**运行时可调**（环境变量兜底 + `ai_settings` 全局配置），调整无需重启
- 批任务支持**优先级**，插队语义在认领排序层生效
- 批任务支持**暂停/恢复**：暂停挡住新认领，运行中子任务自然跑完

### 1.3 非目标（本期不做）

- 子会话**对话内容**的流式推送（维持 2.5s 轮询；见 §9 后续演进）
- 会话级（batch 内单个子任务）优先级与暂停——编排粒度统一为批
- 跨进程分布式队列（单实例部署为当前约定形态，见 §3.1）
- 开放 API（`/v1/ai-batches`）的暂停/优先级——协议面预留，见 §6.4

## 2. 现状与约束

### 2.1 现有链路（设计必须兼容的事实）

1. **完成判定不走 SSE 事件**：worker 以 REST 轮询 `finish + time.completed` 为准（`opencode_client.list_messages`，[batch_engine.py:100-121](../../server/utils/batch_engine.py)），历史上事件窗口丢 `session.idle` 曾导致子任务挂 running 30 分钟。**本设计不改变这一判定**，推送只是把已落库的状态变化更早告知前端。
2. **worker 是唯一写入方**：批子会话的消息/状态/计数全部由 worker 落库（[ai_chat.py:811-817](../../server/routes/ai_chat.py) 注释明确禁止 SSE 代理侧写批子会话）。进度推送也必须以 worker 的落库为唯一事件源。
3. **取消已是"标志位 + 轮询"模式**：`cancel_requested` 由路由置位，dispatcher/`_await_finished` 轮询消费（[batch_engine.py:620-650](../../server/utils/batch_engine.py)、[batch_repo.py:150-216](../../server/utils/batch_repo.py)）。暂停沿用同一模式，认知成本最低。
4. **鉴权与 SSE 形态有现成范式**：`login_required_sse`（EventSource 不能带 header，走 `?access_token=`，[auth.py:63](../../server/auth.py)）+ `_format_sse` + `Response(stream_with_context(...), mimetype='text/event-stream')`（[ai_chat.py:762-836](../../server/routes/ai_chat.py)）。
5. **批次状态是派生值**：`status` 永远由 `done/failed/total` 重算（`_recompute_batch_status`，[batch_engine.py:274-312](../../server/utils/batch_engine.py)）。**新增编排状态不能塞进 status 枚举**，否则每次重算都会把"暂停"覆盖掉（见 §5.4 决策）。

### 2.2 部署形态约束

开发（`python app.py`, threaded=True）与生产（`proxy.py` 拉起后端）均为**单进程 Flask**，worker 与 web 同进程。跨进程推送（gunicorn 多 worker）不是当前形态，但设计上**不依赖进程内总线**——推送通道以 DB 为事实源（§3.1），多进程部署天然可用。

## 3. 总体设计

### 3.1 推送通道选型：DB 版本号 + 服务端条件推送（signal-by-DB）

三个候选的取舍：

| 方案 | 实时性 | 跨进程 | 新依赖 | 结论 |
|------|--------|--------|--------|------|
| A. 进程内事件总线（worker → queue → SSE generator） | 零延迟 | ❌ 多进程失效 | 无 | 与当前部署匹配，但把推送正确性绑定在单进程假设上 |
| B. **DB 版本号条件推送**：批次加 `progress_version`，SSE generator 每秒差量检查，变了就推 | ≤1.5s | ✅ | 无 | **采用**。worker 落库时顺手 `+1`（改动点收敛在既有 UPDATE 语句），检查是一次主键轻查询 |
| C. PG LISTEN/NOTIFY / Redis | 零延迟 | ✅ | 长驻监听连接 / 新中间件 | 违背项目"不引入额外服务进程"哲学（参考记忆层选型，[09-AI智能助手.md §9](./09-AI智能助手.md)），收益不足以覆盖复杂度 |

选 B 的核心论据：**批任务的实时性需求是"秒级可见"，不是"毫秒级"**。worker 本身就以 2.5s 周期落库（`PROGRESS_PERSIST_SEC`，[batch_engine.py:484](../../server/utils/batch_engine.py)），事件源的天然频率就是 2.5s——推送通道做到 1.5s 检查周期已经快于事件源，方案 A 的零延迟优势体现不出来，而 B 换来了部署无关性和极小的代码面。

```
┌────────────┐  每2.5s落库+version+1   ┌──────────┐
│ BatchWorker │ ──────────────────────▶ │ PostgreSQL │◀─── REST detail（降级/首载）
└────────────┘                         └────┬─────┘
                                            │ SELECT version（每1.5s，主键轻查询）
                                     ┌──────▼───────────────┐
                                     │ GET /batches/<id>/events │  变了→推 batch_progress 帧
                                     │ (login_required_sse)     │  终态→推 batch_done 并关流
                                     └──────┬───────────────┘
                                            │ EventSource（?access_token=）
                                     ┌──────▼────────┐
                                     │ aiChatBatches store │ SSE 主通道，断流降级轮询
                                     └───────────────┘
```

### 3.2 并发、优先级、暂停的统一模型

三者都作用在 **dispatcher 认领环节**（`_dispatch_tick` → `_claim_pending_sessions`），互相正交：

```
                ┌─ paused=true 的批次 ──→ 整体跳过，不认领
认领 SQL 谓词 ──┤
                └─ 排序: b.priority DESC, s.created_at, s.batch_seq  ← 优先级插队
认领数量: free = effective_concurrency - len(running)                ← 并发上限可配
```

## 4. 数据库变更（幂等 DDL，追加进 `init_db.py`）

```sql
-- 批次编排三字段（AI_CHAT_BATCHES_DDL 内追加）
ALTER TABLE ai_chat_batches ADD COLUMN IF NOT EXISTS progress_version BIGINT NOT NULL DEFAULT 0;
ALTER TABLE ai_chat_batches ADD COLUMN IF NOT EXISTS paused  BOOLEAN NOT NULL DEFAULT FALSE;
ALTER TABLE ai_chat_batches ADD COLUMN IF NOT EXISTS priority INT    NOT NULL DEFAULT 0;

-- 全局并发配置（AI_SETTINGS_DDL 内追加；NULL = 用默认值 3）
ALTER TABLE ai_settings ADD COLUMN IF NOT EXISTS batch_max_concurrent INT NULL;
```

- `progress_version`：BIGINT 防溢出，单调递增，**只加不减**，语义是"该批次任何可见状态变化过的次数"。
- `paused`：独立布尔，与 `status` 正交（§5.4）。
- `priority`：整数，约定 `0`（默认）/`5`（高）/`-5`（低），不做成枚举以便后续自由插档；UI 用三档下拉映射。
- `ai_settings.batch_max_concurrent`：NULL 视为默认 3；上限 clamp 到 [1, 16]（16 = 线程池容量，见 §5.3）。

## 5. 后端设计

### 5.1 progress_version 的递增点（改动点收敛于既有 UPDATE）

原则：**凡是会让前端看到变化的写，都递增版本**；递增方式一律是往既有 UPDATE 的 SET 子句加 `progress_version = progress_version + 1`，不新建函数、不建触发器（触发器隐式、易在后续维护中遗漏，与项目显式 SQL 风格相悖）。

| 写入点 | 位置 | 说明 |
|--------|------|------|
| `_recompute_batch_status` | [batch_engine.py:302](../../server/utils/batch_engine.py) | status/ completed_at 变化（done/failed 计数变化后必经此处） |
| `_recompute_batch_status_for` | [batch_repo.py:296](../../server/utils/batch_repo.py) | 同上（repo 侧镜像） |
| `_mark_done` / `_mark_failed` / `_mark_cancelled` 中的计数 UPDATE | [batch_engine.py:1404/1422/1444](../../server/utils/batch_engine.py) | 计数先变、重算后变，两处都加保证无窗口 |
| `_cancel_pending_requests` 的批次计数 UPDATE | [batch_engine.py:644](../../server/utils/batch_engine.py) | 批量取消 pending 的计数变化 |
| `_persist_conversation` | [batch_engine.py:1319](../../server/utils/batch_engine.py) | **周期性进度落库也递增**——这是"运行中对话在推进"的信号源；由 §5.2 的推送节流兜住频率 |
| pause/resume 的 UPDATE | 新增 | 见 §5.4 |

> 注意：`update_batch_config`（agent/model 改动）**不**递增版本——配置不影响已展示的进度数据，推了反而制造无意义刷新。

### 5.2 批任务 SSE 通道

新增路由（挂在 `ai_chat_batches_bp`）：

```
GET /ai/chat/batches/events?ids=<id1>,<id2>&access_token=<jwt>
```

- **鉴权**：`@login_required_sse`；对 `ids` 逐个校验 `user_id` 归属，非归属 id 静默剔除（不报错，避免探测）；`ids` 为空 = 订阅该用户**全部非终态**批次（上限 20 个，超出按最近创建截断）。
- **事件协议**（复用 `_format_sse` 格式）：

```
event: batch_progress        # 任一订阅批次 version 变化
data: {"batchId": "...", "detail": { <get_batch_detail 同构快照> }}

event: batch_done            # 批次进入终态（completed/partial/failed）
data: {"batchId": "...", "status": "completed"}
（推送本帧后服务端主动结束该批次的订阅；全部批次终态/被删则关流）

: ping                       # 心跳注释帧，每 15s，防代理空闲断连
```

- **推送快照直接采用 `get_batch_detail` 同构 payload**：前端 `applyDetail()` 零改造复用（`aiChatBatches.ts:51-54`）。50 子会话的 detail 约数十 KB，推送频率被双重节流控制在可接受范围（下）。
- **服务端主循环**（generator 内）：

```python
POLL_SEC = 1.5          # version 检查周期（≤ 事件源 2.5s 落库周期，实时性够）
MIN_PUSH_GAP = 2.0      # 同一批次两次推送最小间隔（节流周期性落库）
HEARTBEAT_SEC = 15
last_sent: dict[str, int] = {}      # batch_id -> 已推送的 version
last_push_at: dict[str, float] = {}

while not stop and subscribed_ids:
    for bid in subscribed_ids:
        ver, status = fetch_version_and_status(bid)   # 单行主键查询
        if ver == last_sent.get(bid):
            continue
        if status in TERMINAL:
            push batch_done; unsubscribe(bid)
        elif time - last_push_at.get(bid, 0) >= MIN_PUSH_GAP:
            push batch_progress(detail=get_batch_detail(...))
            last_sent[bid], last_push_at[bid] = ver, now()
        else:
            last_sent[bid] = ver    # 跳过推送但记账，下个周期补推最新态
    yield ping if due
    time.sleep(POLL_SEC)
```

- **连接生命周期**：批次全部终态或被删除 → 服务端发完最终帧后关流；客户端 EventSource 收到 close 后按 §7 的降级逻辑处理。服务端加硬上限（如 30 分钟）强制关流，防泄漏。
- **审计**：连接建立/关闭各记一条 debug 日志（对齐 `ai_chat.py:786/830` 的日志习惯）。

### 5.3 并发度可配置

**分层取值**：`ai_settings.batch_max_concurrent`（运行时可改）> 环境变量 `AI_BATCH_MAX_CONCURRENT`（部署兜底）> 默认 3。clamp 到 `[1, 16]`。

实现要点（[batch_engine.py](../../server/utils/batch_engine.py)）：

1. **线程池容量与实际上限解耦**：`ThreadPoolExecutor(max_workers=16)` 固定容量（子任务全是 I/O 等待型循环，冗余线程零开销），dispatcher 每次 tick 动态计算 `free = effective_concurrency() - len(self._running_session_ids)`。这样调大/调小都即时生效，无需重建线程池。
2. `effective_concurrency()` 每 tick 读一次缓存值（后台每 30s 刷新自 `ai_settings`，避免每 tick 一次配置查询；调小后已在运行的子任务**不回收**，只影响新认领——与暂停的语义一致）。
3. 设置入口：`ai.py` 的 `GET/PUT /ai/settings`（`admin.ai_settings` 权限）透传该字段；管理端 AI 设置页加一个数字输入。

### 5.4 优先级与暂停（认领 SQL 改造）

改造 `_claim_pending_sessions`（[batch_engine.py:588-618](../../server/utils/batch_engine.py)）——注意三点：**必须 `LEFT JOIN`**（standalone `/v1/ai-sessions` 子会话 `batch_id IS NULL`，无批次行）；**`FOR UPDATE ... OF s`**（JOIN 下只锁会话行，锁批次行会放大锁竞争）；paused 谓词过滤：

```sql
WITH picked AS (
  SELECT s.id
    FROM ai_chat_sessions s
    LEFT JOIN ai_chat_batches b ON b.id = s.batch_id
   WHERE s.status = 'pending'
     AND (s.batch_id IS NOT NULL OR s.api_key_id IS NOT NULL)
     AND COALESCE(b.paused, FALSE) = FALSE          -- 暂停：不认领
   ORDER BY COALESCE(b.priority, 0) DESC,           -- 优先级插队
            s.created_at, s.batch_seq               -- 同级保持 FIFO（现状不变）
   FOR UPDATE SKIP LOCKED OF s LIMIT %s
)
UPDATE ai_chat_sessions s SET status = 'running'
FROM picked WHERE s.id = picked.id RETURNING s.*
```

**暂停语义边界**（写入 `batch_repo.pause_batch` / `resume_batch`，镜像 `cancel_batch` 的"只置标志、worker 消费"模式）：

| 场景 | 行为 |
|------|------|
| 暂停时 pending 子任务 | 留在 pending，不认领；取消检查（`_cancel_pending_requests`）**不受暂停影响**，显式取消仍生效 |
| 暂停时 running 子任务 | **不中断**，自然跑完并计数（避免半截产物，对齐"取消 running 是显式动作"的既有哲学） |
| 暂停时批次 status | 派生逻辑零改动：`_recompute_batch_status` 不感知 paused，status 照常走 pending/running |
| 恢复 | `paused=false` + `get_worker().notify()` 立即唤醒认领 |
| retry-failed / append / reexecute | 允许在暂停批次上执行（置 pending/继续计数），但调度仍被暂停挡住，恢复后统一放出 |
| 定时扫描批次 | 复用同一机制（`ai_scan_engine` 走 `create_batch`，天然继承）；暂停中的扫描批次到期时照常创建**新**批次，由 `ai_scan_engine` 现有的失败回滚逻辑兜底，文档注释说明即可 |

**为什么 paused 不进 status 枚举**：status 是由 done/failed/total 派生并频繁重算的值，若加 'paused' 枚举值，`_recompute_batch_status` 的所有调用点（每子任务终态必经）都要加"若 paused 则保持 paused"的分支，且 `reset_failed_to_pending` 等直接写 status 的 SQL 也会覆盖它——正交布尔列让这些风险全部消失。前端徽标叠加展示（`运行中/已暂停`）。

## 6. 前端设计

### 6.1 store 改造（`src/stores/aiChatBatches.ts`）

`startDetailPolling` 升级为 **SSE 主通道 + 轮询降级**：

```
selectBatch(id)
  ├─ 首载: REST getBatch（保持现状，立即渲染）
  ├─ 订阅: EventSource(`/api/ai/chat/batches/events?ids=${id}&access_token=…`)
  │    ├─ batch_progress → applyDetail(e.data.detail)         ← 主通道
  │    ├─ batch_done → applyDetail + 关流 + 停一切
  │    └─ onerror → 关流，startDetailPolling(id)（现有 5s 轮询原样兜底）
  └─ 降级轮询期间收到任何 REST detail 且非终态 → 尝试重新订阅 SSE（指数退避，1s/5s/30s 封顶）
```

- 轮询代码**不删除**，角色从主通道转为降级通道（SSE 连不上的部署环境、代理缓冲异常等场景仍可用）。
- 列表轮询（10s）**本期保留**：列表是多批次聚合视图，SSE 化需要服务端跨批次聚合通道，收益/成本比不高（§9 演进项）。
- `visibilitychange` 处理对齐现状：hidden 时关流并记录，visible 时重连 + REST 补拉一次。
- `aiChatBatch` 类型（`src/types/aiChatBatch.ts`）补 `paused: boolean`、`priority: number` 字段。

### 6.3 交互文案要点

- 暂停确认弹窗明示语义：「运行中的子任务会继续完成，剩余子任务暂停认领」。
- 批次列表行内 paused 徽标 + 恢复按钮直达，避免用户进详情页找。

## 7. 边界情况与兼容性

| 场景 | 处理 |
|------|------|
| Flask 重启 | SSE 全部断开，前端 onerror 降级轮询 + 重连退避；`progress_version` 持久在 DB，重连后首个周期即推最新态，无状态丢失 |
| 旧数据迁移 | 三个新列均 `NOT NULL DEFAULT`，存量批次自动 `version=0/paused=false/priority=0`，无回填脚本 |
| 版本不回退 | delete 批次后 SSE 查不到行 → 视为终态剔除订阅；version 永远单调，不存在乱序 |
| EventSource 连接数 | 浏览器对同域 HTTP/1.1 限 6 连接；详情页同时最多 1 条批 SSE + 1 条会话 SSE，安全；文档提示生产建议 HTTP/2 |
| 代理缓冲 | 响应头已带 `X-Accel-Buffering: no` + 心跳帧，与交互式 SSE 同配置（[ai_chat.py:835](../../server/routes/ai_chat.py)） |
| 暂停期间 cancel | `_cancel_pending_requests` 不检查 paused（显式取消优先级最高），无需改动——测试需覆盖 |
| `update_batch_config` 整体替换 | PATCH 前端必须回传 priority 当前值，遗漏会重置为 0——在 `EditBatchConfigDialog` 内收敛（提交体总是全量构造），并在 `update_batch_config` 注释里同步说明 |
| 并发调小 | 已运行的子任务不回收，仅减少新认领；UI 保存后提示「对正在运行的子任务不生效」 |

## 8. 验收标准

**进度推送**
- [ ] 子任务终态落库后，前端批次计数 ≤2s 更新（SSE 正常时），不再依赖 5s 轮询
- [ ] 断开 SSE（杀后端）后自动降级为 5s 轮询且不丢更新；恢复后重新订阅
- [ ] 运行中子任务的对话推进（工具气泡增加）≤4s 可见于详情页
- [ ] 全部批次终态后服务端主动关流，无连接泄漏（30 分钟硬上限兜底）
- [ ] 非归属批次的 ids 被静默剔除，401/404 行为与现有 SSE 一致

**并发可配**
- [ ] `ai_settings.batch_max_concurrent=6` 保存后，无需重启，下一 tick 起并发认领数变为 6
- [ ] 调回 3 后，已运行的 6 个子任务继续跑完，新认领不超过 3
- [ ] 值 clamp 到 [1,16]；非法输入 422

**优先级**
- [ ] 高优先级（5）批次的 pending 子任务先于普通批次被认领（构造 FIFO 逆序场景验证）
- [ ] standalone `/v1/ai-sessions` 子会话（无批次行）认领行为与现状一致
- [ ] 创建与 PATCH 均可设置 priority，越界值 clamp/422

**暂停/恢复**
- [ ] 暂停后新 pending 子任务不被认领，running 子任务跑完并正常计数
- [ ] 恢复后 pending 子任务被立即认领（notify 生效，≤10s）
- [ ] 暂停批次上 retry-failed/append/reexecute 可执行但不出队，恢复后统一放出
- [ ] 暂停批次内显式取消 pending 子任务仍然生效
- [ ] 前端暂停/恢复操作后徽标即时变化，刷新页面状态正确
- [ ] 终态批次调用 pause/resume 返回 409
